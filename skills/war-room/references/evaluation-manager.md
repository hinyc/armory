# 평가 롤 운영 (매니저)

일이 끝나면 임시 검증 에이전트 대신 평가 롤이 판정한다 (상 등급. 하는 기계 검사만으로 판정하고, 중은 평가 롤이 켜져 있어도 다섯 갈래 없이 `verify-loop.md` 2절의 기준별 판정만 한다. 등급은 `verify-loop.md` 1절). 이 문서의 흐름·프롬프트·진행 파일·스냅숏은 상 등급 이야기다. 이번 일에 붙인 기준만이 아니라 **지난 결정·부작용·개념·수치**까지 보게 한다. 평가 롤은 코드를 고치지 않고 판정만 한다. 평가 에이전트는 읽기 전용 `armory:evaluator`로 띄운다.

판정 규칙(다섯 갈래·종합 판정·보고 형식·진행 파일 계약)은 `evaluation.md`에 있고 평가 에이전트가 그 문서를 읽는다. 평가 에이전트는 이 문서를 읽지 않는다. 판정에 필요한 값은 6절 프롬프트로 준다.

## 0. 켜짐·꺼짐·없음

| 상태 | 판단 | 동작 |
|---|---|---|
| 꺼짐 | `roles.evaluator: false` (롤 파일 유무 무관) | 평가 롤을 쓰지 않는다. `verify-loop.md` 2절 기존 방식(검증·QA 롤 → 임시 검증 에이전트. 검증·QA 롤을 띄울 때도 플러그인이 있으면 `armory:evaluator` 종류로 띄우고 그 롤 파일을 프롬프트에 넣는다. 임시 검증 에이전트도 `armory:evaluator`)으로 돌아간다. 진행 파일을 쓰지 않으므로 띠도 안 뜬다 |
| 켜짐 | `false`가 아니고(`true`이거나 키 없음) `roles/evaluator.md`가 있음 | 상은 이 문서대로 평가한다. 중은 이 문서의 7절(스냅숏)만 따르고 나머지는 `verify-loop.md` 2절 기준별 판정이다 |
| 없음 (기존 설치) | `false`가 아니고(`true`이거나 키 없음) `roles/evaluator.md`가 없음 | 경고하고(SKILL.md 배정 3번의 평가 롤 꺼짐·파일 없음 규칙) 그 배정은 꺼짐과 같이 기존 방식으로 마친다. 파일이 없는 것을 처음 안 그 배정에서 한 번 "평가 롤을 추가할 수 있어요"라고 알리고, 승인하면 템플릿에서 `roles/evaluator.md`를 복사하고 config에 `"evaluator": true`, `.gitignore`에 `war-room/.eval/`를 넣는다. 거절하면 `DECISIONS.md`에 적고 다시 묻지 않는다 |

- `evaluator`는 `manager`와 달리 끄기·삭제할 수 있다.
- **두 축은 별개다.** 평가 롤이 켜졌는지(config와 롤 파일)와 평가 에이전트 종류(armory 플러그인 유무)는 따로 본다.
  - 플러그인이 있으면 평가 롤이 꺼졌거나 없어도 검증·기준 검토 에이전트는 `armory:evaluator`로 띄운다. 이때는 다섯 갈래 대신 기준별로 판정한다.
  - 플러그인이 없으면(다른 도구로 설치) `general-purpose`로 되돌리고 그렇다고 알린다. 이때 읽기 전용은 프롬프트 규칙과 스냅숏 비교(7절)에만 기댄다.
  - 플러그인 유무는 사용 가능한 에이전트 종류에 `armory:evaluator`가 있는지로 본다.
- 기존 설치에 추가할 때 검증·QA 롤이 있으면, 두 롤의 경계를 양쪽 `하지 않는 일`에 적자고 함께 제안한다.

## 1. 흐름

```
요청 → 매니저 배정 ─→ (상) 기준 검토: 새 검증 에이전트 한 번 (verify-loop.md 1절)
                         │  매니저: 기준선·변경 전 수치 재기, 한계값 정하기, 볼 갈래 고르기
                         │  사용자가 정할 것 있으면 확인
                         ↓
                    ② 담당 롤 작업 (시도 n, 커밋 없음)
                         ↓
                    오래 걸리는 명령이 있으면 매니저가 한 번 돌려 기록 (verify-loop.md 2절)
                         ↓
                    STATUS 진행 중 줄 갱신 → 스냅숏 (7절)
                         ↓
                    ③ 평가 롤: 평가 실행 (띠 표시) → 스냅숏 비교 (7절)
                         ├ 통과 → ⚠ 있으면 사용자 확인 → 문서 갱신 (STATUS·DECISIONS·LESSONS) → 이어받기 점검 → 커밋 (사용자가 요청하면)
                         └ 실패 → verify-loop 3절대로 다시 맡김 → ② (띠의 "이전"에 이번 결과)
```

- ③은 시도마다 새 평가 에이전트다. `subagent_type: armory:evaluator`, `description: evaluator: <작업 요약>`. 플러그인이 없을 때만 `general-purpose`로 되돌리고 그렇다고 알린다 (0절).
- 등급별로 돈다: 하 등급은 평가 롤을 띄우지 않는다. 중은 ③ 없이 `verify-loop.md` 2절의 기준별 판정 한 번이다 (평가 롤 켜짐·꺼짐 무관. 매니저가 맡기기 전에 기준선을 뜨고, 수치 확인은 기준 하나 `명령 → 기대 결과`로 넣고, 진행 파일·띠는 없다).
- 상 등급의 평가 에이전트는 구현 뒤 시도마다 한 번(③)만 띄운다. 평가 계획 ①은 없다. 기준선(원래 실패하던 테스트)과 수치 갈래의 변경 전 값·한계값은 매니저가 맡기기 전에 명령으로 재고 정한다. 한계값을 사용자가 정해야 하면 맡기기 전에 묻는다.
- 기준 검토는 ③과 따로 한다: 상 등급의 기준 검토는 맡기기 전에 새 검증 에이전트 한 번이 한다 (`verify-loop.md` 1절).
- 상 등급 에이전트 수는 기준 검토 1 + 시도마다 ③ 1이다 (평가 롤 켜짐). 꺼짐·없음이면 기준 검토 1 + 시도마다 기준별 검증 1이다.
- `model`은 Agent 호출의 `model`로 넘긴다: 중은 `haiku`, 상은 롤 파일의 `model`이다. 평가 롤 model 기본값은 `sonnet`이다. 비용을 줄이려면 롤 파일의 `model`만 내린다. 이하 1~7절은 상 등급 기준이다.
- ③은 기준·히스토리·부작용을 항상 보고, 개념은 conceptpowers가 켜져 있을 때, 수치는 수치 기준이 있을 때만 본다. 매니저가 ③ 프롬프트 `## 볼 갈래`에 갈래와 이유를 적고, 뺀 갈래는 `na`(해당 없음: 이유)로 적는다. 평가 에이전트가 뺀 갈래가 필요하다고 보면 판정에 더하고 보고에 적는다.
- 수치 갈래 준비 (매니저, 맡기기 전)
  - 잴 것은 이번 변경과 관계있는 것만 고르고 위임 `## 요구 기준`에 넣는다. 응답 시간, 빌드 시간, 번들·파일 크기, 메모리, 특정 출력값 등이다.
  - **한계값 출처 순서**: (1) 사용자가 말한 값 → (2) 롤 문서나 `DECISIONS.md`에 적힌 값 → (3) 둘 다 없으면 매니저가 초안(변경 전 값에 여유를 둔 값)을 내고 **맡기기 전에 사용자에게 묻는다**. 앞 출처가 있으면 뒤 출처는 보지 않는다. 사용자 확인으로 확정한 한계값은 매니저가 `DECISIONS.md`에 적어 다음 평가가 (2)로 쓴다.
  - 변경 전 값은 매니저가 명령으로 재서 위임과 ③의 `## 기준선`에 넣는다.
- 매니저가 직접 처리한 일도 같은 흐름이다.
- 예외: 답만 하는 질문과 문서 상태 갱신만 하는 일(STATUS·LESSONS 정리)은 평가하지 않는다. 판단 근거는 바뀌는 코드·동작이 없어 히스토리·부작용·수치를 볼 대상이 없기 때문이다.
- 중·상은 한 파일 몇 줄짜리라도 평가 에이전트를 띄운다. 상의 수치 갈래는 수치 기준이 없으면 `## 볼 갈래`에서 뺀다 (`na`). 하 등급 일은 기계 검사 결과로 끝내고, 사후 점검에서 바뀐 내용에 검증 신호나 무조건 상 조건이 생겼으면 올려서 평가한다.
- 사용자가 정할 것(한계값 미정, 결정끼리 충돌 등)이 있을 때만 맡기기 전에 확인받는다. 그 밖에는 묻지 않고 진행한다.
- 2번째 시도부터 같은 기준선·같은 볼 갈래로 ③만 새로 띄운다.
- STATUS `진행 중` 줄은 이어받기를 위해 시도마다, 스냅숏 전에 갱신한다. 다른 상태 문서는 통과 뒤에 쓴다 (`state-docs.md` 5절).
- 뒤집는 결정이 있으면 ③ 프롬프트 `## 관련 결정`의 `이번 일이 뒤집는 결정` 줄에 적는다. 평가 에이전트는 그 결정을 히스토리 ✗로 세지 않고 결정 점검에서 본다. 뒤집는 DECISIONS 항목은 평가 통과 뒤 문서 갱신 때 쓴다.

### 여러 롤에 나눈 일

- 여러 롤 병렬은 등급 상이다. 평가는 롤마다 따로 한다. 롤마다 ③이 따로 돈다. 기준선은 모든 구현을 맡기기 전에 한 번 떠서 모든 롤의 ③에 같이 넣는다. 롤마다 다른 변경 전 수치는 `## 기준선`에 롤별로 적는다. 스냅숏은 모든 롤의 구현이 돌아온 뒤 한 번에 뜬다 (7절).
- 진행 파일과 오래 걸리는 명령 기록도 롤마다 따로 둔다 (`war-room/.eval/<롤 id>.json`, `<롤 id>.long-run.txt`). 동시에 돌아도 서로 덮어쓰지 않는다.
- 병렬 뒤 매니저의 전체 테스트 재실행은 평가 롤이 켜져 있으면 하지 않는다 (각 ③이 모든 구현이 돌아온 뒤 부작용 갈래로 전체 테스트를 돌려 중복이다). 꺼졌거나 없으면 롤별 판정이 모두 통과한 뒤 롤 사이 부작용을 보려고 매니저가 전체 테스트를 한 번 더 돌린다. 병렬로 맡기기 전의 공유 약속은 `delegation.md` 4절.

### 이미 검증·QA 롤이 있는 프로젝트

- evaluator가 켜져 있으면 평가는 evaluator가 맡는다. `verify-loop.md` 2절의 "검증·QA 롤에 맡긴다"는 evaluator가 꺼져 있거나 없을 때만 적용한다.
- 사용자가 만든 QA 롤의 `완료 기준`·`일하는 방식`은 evaluator가 기준 갈래에 더해 쓴다. 평가 에이전트는 롤 파일을 `refs`로 읽지 않으므로 매니저가 그 두 절을 ③ 프롬프트 `## 대상`의 QA 롤 줄에 옮겨 넣는다.

## 3. 판정 뒤 처리

- ✗가 하나라도 있으면 실패. `verify-loop.md` 3절 표대로 다시 맡긴다. 실패 원인 칸에 갈래를 적는다 (예: "히스토리: DECISIONS 2026-11-05 위반").
- ✗ 없고 ⚠만 있으면 통과. 보고 뒤 사용자에게 ⚠ 항목을 보여주고 받아들일지 묻는다. 안 받아들이면 그 항목을 ✗로 보고 다시 맡긴다 (시도 횟수는 이어서 센다).
- 멈춤 조건·끝까지 모드·못 미칠 때 보고는 `verify-loop.md` 그대로. 다만 진척을 세는 수를 바꾼다.
  - **진척 수 = 다섯 갈래 전체의 ✗ 개수.** 두 번 연속 ✗ 개수가 줄지 않으면 "나아지지 않는 반복"이다.
  - **최고 결과** = ✗가 가장 적은 시도. 같으면 ✓가 많은 시도, 그것도 같으면 나중 시도.
  - `verify-loop.md` 3·4절의 "통과한 기준 수"는 이 수로 바꿔 읽는다.
- 결정 점검(`judgment.md` 4절)은 ✗ 개수에 더하지 않는다.
- 통과하면 스냅숏 비교(7절)가 같은지 먼저 확인한다. 같으면 ⚠ 확인을 받고, STATUS·DECISIONS·LESSONS를 갱신하고, 이어받기 점검을 한 뒤 커밋한다 (사용자가 요청한 경우. `state-docs.md` 5절). 보고의 `재실행 생략` 줄은 매니저가 대조 근거를 한 번 읽는다.

## 5. 진행 파일 정리

- 평가 에이전트가 돌아올 때마다(정상·오류·중단 모두) 그 롤의 진행 파일(`war-room/.eval/<롤 id>.json`)을 열어 `state`가 아직 `running`(예전 파일이면 `planning`도)이면 `aborted`로 고친다.
- 일이 완전히 끝나면(통과 확정 또는 멈춤) 그 롤의 진행 파일, 스냅숏(`<롤 id>.snapshot`), 오래 걸리는 명령 기록(`<롤 id>.long-run.txt`)을 지운다.
- 오래 걸리는 명령 기록은 시도마다 새로 돌려 다시 쓴다. 이전 시도의 기록은 남기지 않는다.

## 6. 평가 에이전트 프롬프트

서브에이전트는 이 대화를 모른다. 필요한 것을 모두 넣는다. `<…>`는 매니저가 채운다. 구현 에이전트의 "잘 됐다" 설명은 넣지 않는다.

### ③ 평가 실행

```
너는 이 프로젝트의 evaluator 롤이다. 아래 롤 정의를 따른다. 코드를 고치지 말고 판정만 한다. 판정용 읽기 스킬만 쓰고 파일을 바꾸는 스킬은 부르지 않는다. 작업 폴더 밖에는 아무것도 쓰지 않는다. 진행 파일은 Bash로 쓴다.

<roles/evaluator.md 본문 전체>

## 관련 결정

- 검색어: <바뀐 기능·모듈·설정 키·용어 3~6개. 없으면 "–">

## 할 일
1. 시작하자마자 진행 파일을 다시 쓴다: 직전 current가 state "done"이면 previous로 옮기고, current = { attempt: <n>, state: "running", focus: "<이번에 볼 것>", items: `## 볼 갈래`의 갈래는 status "pending", na 갈래는 status "na"·summary "해당 없음: <이유>" }, updatedAt = 지금(ISO 8601, `date -Iseconds`).
2. 볼 갈래를 기준 → 히스토리 → 부작용 → 개념 → 수치 순서로 하나씩 판정한다. 시작하는 갈래는 status "running"으로, 끝낸 갈래는 판정(pass·fail·warn·na)과 summary(수치는 metrics 배열)로 고쳐 쓰고 updatedAt을 갱신한다. 30분 넘게 걸릴 작업은 시작 전에 updatedAt을 한 번 더 갱신한다.
3. 판정 규칙은 <skills/war-room/references/evaluation.md 의 2절 경로>를 읽고 따른다. 히스토리는 DECISIONS·LESSONS 전체를 읽지 않고 거기 적힌 대로 grep한다.
4. na로 뺀 갈래가 이번 변경에 필요하다고 보면 더해 판정하고(진행 파일의 그 항목을 na에서 판정값으로 고친다) 보고의 `더한 갈래`에 이유를 적는다. 볼 갈래 안에서 기준에 없던 확인이 필요하면 그 갈래에 더해 판정하고 보고에 적는다.
5. 결정 점검: `## 매니저가 정한 것`의 결정마다 `유지 | 재검토 — 근거`로 판정한다. `이번 일이 뒤집는 결정`도 여기서 본다. 재검토 조건은 셋이다: 그 결정이 이번 ✗·⚠의 원인이다, 요청·DECISIONS·LESSONS와 어긋난다, 되돌리기 어려운 결정(`judgment.md` 1절)인데 되돌릴 수 있다고 분류했다. 결정 점검은 ✗ 개수에 더하지 않는다.
6. 끝나면 진행 파일의 current.state를 "done"으로, verdict를 "pass"(✗ 없음) 또는 "fail"로 고치고 updatedAt을 갱신한다.
```

## 7. 읽기 전용 확인: 평가 전후 스냅숏

적용 범위는 평가·검증 에이전트를 띄울 때마다다 (중·상, 평가 롤 켜짐·꺼짐 모두). 하 등급은 에이전트를 띄우지 않으므로 스냅숏도 없다.

평가 에이전트는 Bash를 가지므로 도구만으로는 파일 쓰기가 완전히 막히지 않는다. 구현 결과가 이미 작업 폴더에 있어서 "바뀐 파일이 없는지"로는 판정할 수 없으니, 평가를 띄우기 직전에 매니저가 스냅숏을 남기고 돌아오면 같은 방법으로 다시 떠서 비교한다.

```bash
mkdir -p war-room/.eval
snap() {
  git status --porcelain | grep -v ' war-room/\.eval/'
  git diff | shasum
  git diff --cached | shasum
  git ls-files --others --exclude-standard | grep -v '^war-room/\.eval/' | while IFS= read -r f; do shasum -- "$f"; done
}
snap > war-room/.eval/<롤 id>.snapshot      # 평가 직전
snap | diff - war-room/.eval/<롤 id>.snapshot  # 평가 직후, 출력이 없어야 한다
```

- 남기는 것: `git status --porcelain`, `git diff`와 `git diff --cached`의 해시, 추적 안 되는 파일 각각의 해시. 저장 위치는 `war-room/.eval/<롤 id>.snapshot`이고 커밋하지 않는다.
- 진행 파일이 있는 `.eval/`은 평가 에이전트가 쓰면 달라지므로 비교에서 뺀다. 무시 파일(`--ignored`)은 테스트·빌드 부산물 때문에 거짓 무효가 나므로 넣지 않는다.
- 하나라도 다르면 그 평가는 무효다. 바뀐 내용을 사용자에게 알리고, 바뀐 파일을 되돌릴지 정한 뒤 평가를 다시 띄운다.
- 순서는 구현 → STATUS 진행 중 줄 갱신 → 스냅숏 → 평가 → 스냅숏 비교 → (통과하면) 문서 갱신이다. 비교는 문서 갱신보다 앞에 한다. 문서 변경이 평가 중 변경으로 잡히지 않게 하려는 것이다.
- 병렬로 맡긴 일은 모든 롤의 구현이 돌아온 뒤 한 번에 스냅숏을 뜨고 평가를 띄운다. 롤별 평가는 동시에 돌려도 된다 (모두 읽기 전용이라 서로 영향이 없다).
- 한계: 무시 경로(.env, node_modules 등)에 쓴 것은 잡지 못한다. 저장소 밖(홈 설정, 다른 폴더) 변경은 이 비교로 못 잡는다. 그 범위는 프롬프트 규칙("작업 폴더 밖을 쓰지 않는다")에 맡긴다. 별도 worktree에서 평가하는 방식은 비용이 커서 쓰지 않는다.
- 평가가 끝나면 진행 파일과 함께 스냅숏도 지운다 (5절).

### 작업 상태 해시 (오래 걸리는 명령 기록용)

오래 걸리는 명령(`verify-loop.md` 2절)의 결과가 지금 작업 상태에서 나온 것인지 대조하는 값이다. `war-room/` 문서는 제외하고, 변경·스테이징·추적 안 되는 파일을 모두 합쳐 해시 하나로 만든다. 명령이 끝난 직후 계산해 기록하고, 검증·평가 에이전트가 같은 명령으로 다시 계산해 비교한다. 어느 폴더에서 돌려도 값이 같다.

```bash
( cd "$(git rev-parse --show-toplevel)" && { git status --porcelain -- . ':(top,exclude)war-room'; git diff -- . ':(top,exclude)war-room'; git diff --cached -- . ':(top,exclude)war-room'; git ls-files --others --exclude-standard -- . ':(top,exclude)war-room' | while IFS= read -r f; do shasum -- "$f"; done; } | shasum )
```
