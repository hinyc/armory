# 상태 문서 (STATUS · DECISIONS · LESSONS)

SKILL.md 배정 7번의 세부다. 쓰는 내용, 크기 정리, 문서를 쓰는 순서와 커밋을 다룬다. 이 파일들은 매니저만 쓴다.

## 1. STATUS.md (바뀐 절만 고친다)

작업이 끝날 때마다 **바뀐 절만** Edit로 고친다. 파일을 통째로 다시 쓰지 않는다 (출력이 파일 크기만큼 늘어난다). 맨 위 `갱신:` 줄도 함께 고친다. 갱신 시각은 `date '+%Y-%m-%d %H:%M'`으로 얻는다.

- **진행 중**: `<롤 id> · 작업 · 시도 n/최대 · 남은 실패 기준`. 이어받기를 위해 시도마다, 스냅숏 전에 고친다 (5절)
- **다음 할 일**: 사용자가 말했거나 보고의 "남은 일"에서 나온 것. 10개까지 둔다. 넘으면 이슈 트래커에 있는 항목은 이슈 키와 한 줄 요약으로 줄이고, 그래도 넘으면 다음 보고 때 사용자에게 정리를 묻는다
- **막힌 것**: 사용자 결정이 필요한 것
- **롤 후보**: 새 롤·분리·갱신 신호(`[종류]` 표시). 다시 쓸 때도 이어서 남긴다 (`references/role-split.md`)
- **점검할 결정**: 중·상 일에서 매니저가 정한 결정. 형식 `날짜 · 작업 · 결정 · 이유 · 되돌리는 법`. 다시 쓸 때도 이어서 남기고, 10KB 넘침 때 옮기거나 자르지 않는다. 점검 뒤 처리는 `references/judgment.md` 4절
- **최근 완료**: `날짜 · 롤 · 한 줄`, 최신이 위. STATUS.md를 다시 쓴 뒤 파일 전체를 `wc -c`로 재서(`wc -m` 아님: 한글은 글자 수와 바이트 수가 다르다) 10KB(10,240바이트)를 넘으면 아래쪽(오래된 것)부터 옮겨 10,240바이트 이하가 될 때까지 반복한다
  - 옮기는 곳은 항목 날짜의 달별 `archive/STATUS-YYYY-MM.md`다. 여러 달이 나오면 달마다 나누고, 파일이 없으면 `mkdir -p archive`로 폴더를 만든 뒤 `# 지난 완료 (YYYY-MM)` 제목으로 만든다. 파일 안에서도 최신이 위다
  - 맨 위 항목 1개는 옮기지 않는다. 예외: 옮길 수 있는 항목을 다 옮겨도 넘으면(진행 중·다음 할 일·롤 후보가 큼) 더 옮기지 않고 다른 절도 자르지 않는다. 자르면 현재 상태를 잃기 때문이다. "막힌 것"에 적고 사용자에게 알린다

"지금 뭐 하고 있어", "다음 뭐 해" 같은 질문은 이 파일로 답한다.

## 2. DECISIONS.md (쌓임)

- 되돌리기 어렵거나 나중에 이유가 궁금할 결정만 적는다. 작업 결과("버튼 추가함")는 적지 않는다.
- 롤이 정한 것은 `references/judgment.md` 1절로 나눈다. 되돌릴 수 있는 것은 `정한 것:`·`점검할 결정` 대상이고, 그중 나중에 이유가 궁금할 것만 여기에 적는다 (`정한 사람: 매니저 판단`). 되돌리기 어려운 것은 사용자에게 묻고 정한 뒤 적는다.
- 새 항목은 위에 추가하고, 지난 항목은 고치지 않는다. 결정이 바뀌면 "YYYY-MM-DD 결정을 뒤집음"이라고 새 항목을 쓴다. 확정된 항목의 제목은 바꾸지 않는다. 같은 날 같은 제목이면 제목 끝에 `(2)`를 붙인다.
- 쓰는 주체: `STATUS.md`·`DECISIONS.md`·`LESSONS.md`·`roles/`·`config.json`은 매니저만 쓴다. 서브에이전트는 보고의 `정한 것`·`겪은 문제`·`가정한 것`으로 제안만 한다. 예외: 릴리즈 담당 롤은 승인 뒤 매니저가 갱신한 문서를 릴리즈 커밋에 넣기만 하고 (내용은 고치지 않는다), 평가 에이전트는 자기 진행 파일만 쓴다.
- 300줄을 넘으면 지난달 이전 항목을 `archive/DECISIONS-YYYY.md`(해당 연도)로 옮긴다.

## 3. LESSONS.md (반영하면 비움)

- 같은 실수를 막는 데 필요한 것만 적는다. 한 번뿐인 사고는 적지 않는다.
- 비우는 방법
  - "롤 문서 반영 후보"가 쌓이면 사용자에게 보여주고, 승인받은 것을 `roles/<id>.md`의 해당 절(`일하는 방식`, `하지 않는 일`, `완료 기준`)에 넣는다.
  - 반영했거나 더는 맞지 않는 항목은 `archive/LESSONS-YYYY.md`로 옮긴다.
- 정리 주기
  - 같은 종류 교훈이 두 번째로 나오면 그 자리에서 롤 문서·스킬 규칙 반영을 제안한다.
  - 항목이 5개를 넘거나 가장 오래된 항목이 14일을 넘으면 다음 보고 뒤에 반영·정리를 제안한다. 먼저 닿는 쪽을 따른다.

## 4. 공통

- 비밀값·토큰·개인정보는 적지 않는다.
- `archive/`는 읽기만 한다. 과거를 물을 때("지난달 뭐 했어", "그때 왜 그렇게 정했어") 찾아본다.

## 5. 문서를 쓰는 순서와 커밋 (모든 등급)

문서는 검증·평가를 통과한 뒤 한 번만 쓴다. 통과 전에 결과를 적으면 실패했을 때 지우고 다시 써야 하고, 평가가 문서 변경을 구현 변경과 섞어 본다.

순서: 구현(커밋 없음) → 검증·평가 → **스냅숏 비교** → 통과 → 매니저가 STATUS·DECISIONS·LESSONS 갱신 → 이어받기 점검 → 커밋 (사용자가 요청한 경우). 스냅숏 비교는 문서 갱신보다 앞에 한다 (`verify.md` 4절).

- 등급별: 상·중은 평가·검증 에이전트의 통과와 스냅숏 비교 뒤, 하는 기계 검사와 사후 점검(SKILL.md 하 등급)을 거친 뒤 문서를 갱신한다. 중 명령 판정은 명령 결과와 `git diff` 점검 뒤에 갱신한다. 어느 등급이든 통과 전에는 `진행 중` 줄(시도 n/최대·남은 실패 기준) 말고 쓰지 않는다. 이 줄은 세션이 끊겨도 이어받도록 시도마다, 스냅숏 전에 고친다.
- 점검할 결정은 지금처럼 기록한다 (`judgment.md` 3절). 이번 일이 뒤집는 결정은 평가 프롬프트의 `이번 일이 뒤집는 결정` 줄로 알리고, 뒤집는 DECISIONS 항목은 통과 뒤에 쓴다.
- 이어받기 점검: 문서 갱신 뒤 매니저가 STATUS.md(`점검할 결정` 포함)와 DECISIONS.md만 읽고 지금 상태와 다음 할 일, 이번 일의 결정을 말할 수 있는지 본다. 결과물 판정이 아니라 매니저 자신의 기록이 충분한지 보는 문서 점검이라 매니저가 한다 (`verify.md` 2절). 못 하면 문서를 보충한 뒤 커밋한다.
- 커밋 주체: 사용자가 커밋을 요청했으면 매니저가 구현과 문서를 한 커밋으로 묶는다. 구현 롤은 커밋하지 않는다. 예외는 릴리즈 담당 롤이 승인 뒤 하는 릴리즈 커밋뿐이다. 세션 지휘의 작업 세션은 이 규칙이 아니라 `multi-session.md`대로 자기 브랜치에 커밋한다.
- 실패하거나 멈추면 결과가 정해지지 않았으므로 `진행 중`·`막힌 것`·`LESSONS.md`에 실제 상태만 적는다. 지울 것이 없다.

### 릴리즈 (커밋·push·태그·릴리즈로 끝나는 일)

정형 릴리즈(변경이 이미 검증·커밋돼 있고 버전 올림·릴리즈만 하는 일)는 `verify-high.md` 7절을 따른다. 아래는 정형이 아닌 릴리즈다.

1. 담당 롤이 준비한다 (버전 올리기 등. 커밋하지 않는다).
2. 평가·검증과 스냅숏 비교를 통과한다.
3. 매니저가 문서를 갱신한다. 검증까지 확인된 사실과 "릴리즈 승인 대기·진행"만 적는다. 릴리즈 성공·URL은 적지 않는다 (아직 일어나지 않았다).
4. 사용자가 승인한다.
5. 새 롤 에이전트가 `## 범위`에 적힌 커밋·push·태그·릴리즈를 한다. 3번에서 고친 문서 변경도 그 커밋에 넣는다.
6. 릴리즈 결과(성공·URL)는 다음 문서 갱신 때 STATUS에 반영한다. 릴리즈가 실패하면 STATUS를 실제 결과로 고쳐 다음 커밋에 넣는다.
