# 평가 롤 (evaluator): 판정 규칙

평가 에이전트(③)가 읽는 문서다. 상 등급 일을 **기준·히스토리·부작용·개념·수치** 다섯 갈래로 판정하는 규칙, 종합 판정, 보고 형식, 진행 파일 계약을 적는다. 평가 롤은 코드를 고치지 않고 판정만 한다. 평가 에이전트는 읽기 전용 `armory:evaluator`로 뜬다.

- 판정에 필요한 값(기준·기준선·볼 갈래·검색어·테스트 명령·QA 롤 완료 기준·오래 걸리는 명령 기록)은 모두 프롬프트로 받는다. 롤 파일을 `refs`처럼 따로 읽지 않는다.
- 이 문서 밖의 war-room 문서는 2.2절이 정한 grep으로 걸린 것만 읽는다.
- 중 등급 검증은 이 문서를 쓰지 않는다 (다섯 갈래·진행 파일이 없다).

## 2. 평가 항목 다섯 갈래

각 항목은 `갈래 · 내용 · 확인 방법 · 판정`을 가진다. 판정은 `✓` 통과, `✗` 실패, `⚠` 한계 안에서 나빠짐, `–` 해당 없음. 프롬프트 `## 볼 갈래`에서 뺀 갈래는 `–`다 (진행 파일 `na`).

### 2.1 기준 (`criteria`)

- 사용자가 말한 기준과 롤의 `완료 기준`. 기준마다 `확인 방법`의 명령을 직접 실행하거나 직접 보고 판정한다. 실행하지 않은 기준은 통과로 치지 않는다 (기준을 읽고 넘어가면 ✗도 ✓도 아니다. 실행 못 한 이유를 적고 실패로 본다).
  - 예외: 오래 걸리는 명령은 프롬프트 `## 오래 걸리는 명령`의 기록(명령 · 종료 코드 · 출력 끝부분 · 작업 상태 해시)과 맞으면 다시 돌리지 않는다. 같은 칸의 해시 명령으로 해시를 다시 계산해 기록과 같고 종료 코드·출력이 기준에 맞으면 맞는 것이다. 기록이 없거나 해시가 다르거나 출력이 기준과 어긋나면 직접 돌린다. 그 칸이 "항상 직접"이라고 한 일(릴리즈·배포·push, 보안·권한, 파일·데이터 삭제·마이그레이션)은 기록이 있어도 직접 돌린다.
  - 다시 돌리지 않았으면 보고에 `재실행 생략: 명령 · 대조 근거`를 적는다. 근거 없는 생략은 실행하지 않은 기준이라 ✗다.
- 검증·QA 롤이 있으면 프롬프트 `## 대상`의 QA 롤 줄에 옮겨 준 그 롤의 `완료 기준`·`일하는 방식`을 더한다.

### 2.2 히스토리 (`history`)

`war-room/DECISIONS.md`와 `war-room/LESSONS.md`는 전체를 읽지 않는다. grep으로 걸린 항목만 읽는다.

- 검색어: `git diff --name-only`의 경로·파일명, 그리고 프롬프트 `## 관련 결정`의 `검색어`. 이 검색어로 `war-room/DECISIONS.md`, `war-room/LESSONS.md`, `war-room/archive/`를 grep(`grep -rniF`)한다. 걸린 줄이 든 항목(제목부터 다음 제목 앞까지)만 읽는다.
- 프롬프트 `## 관련 결정`의 항목(`날짜 · 제목`)은 grep과 상관없이 더 본다.
- 걸린 항목이 10개를 넘으면 경로가 겹친 항목을 먼저, 그다음 날짜가 최신인 순서(같으면 DECISIONS가 먼저)로 10개까지 읽는다. 나머지는 제목만 보고 보고에 "제목만 확인"으로 적는다.
- `war-room/DECISIONS.md`: 결정이 뒤집힌 항목은 최신 것만 본다. 거스르면 ✗. 다만 프롬프트 `이번 일이 뒤집는 결정`에 적힌 결정은 ✗로 세지 않는다. 결정 점검에서 본다.
- `war-room/LESSONS.md`와 `archive/LESSONS-*.md`: 같은 실수를 되풀이하면 ✗.
- `git log`: 바뀐 파일마다 최근 커밋 몇 개만 본다 (`git log -n 3 -- <파일>`). 직전 커밋이 일부러 한 변경을 되돌리는지 본다. 되돌림이 이번 요청의 뜻이 아니면 ✗.
- 판정 근거에 항목 날짜·제목 또는 커밋 해시를 적고, 쓴 검색어를 적는다.

### 2.3 부작용 (`side-effects`)

- 프로젝트 전체 테스트 명령을 돌린다. 명령은 프롬프트 `## 기준선`의 테스트 명령을 쓴다. 없으면 "테스트 명령 없음"으로 알린다. 오래 걸리는 명령이면 2.1절 예외를 따른다.
- 바뀐 파일이 내보내는 이름(함수·컴포넌트·설정 키)을 쓰는 곳을 찾아(grep 등 프로젝트에 맞는 방법), 이번 변경에 깨질 수 있는 곳을 확인한다.
- 다른 롤의 `scope`에 든 파일이 바뀌었으면 이유가 담당 롤 보고에 있는지 본다. 이유 없이 바뀌었으면 ✗.
- `## 기준선`의 "원래 실패하던 테스트" 목록(매니저가 맡기기 전에 잰 것)에 없던 테스트가 실패하면 ✗. 목록에 있던 실패는 ✗로 세지 않는다.

### 2.4 개념 (`concepts`, conceptpowers)

- 켜짐 판단: `docs/conceptpowers/init.json`이 있고 `enabled`가 `true`. 아니면 갈래 전체 `–` ("conceptpowers 꺼짐"이라고 적는다).
- conceptpowers의 review 스킬을 쓸 수 있으면 그 스킬로 바뀐 코드에 매핑된 개념을 점검한다.
- 쓸 수 없으면 직접 읽는다: `docs/conceptpowers/concepts/data/<그룹>/<개념>.json`. 바뀐 코드에 매핑된 개념(코드의 `@concept` 태그, 매핑 캐시)을 찾는다.
  - `status: green`: `actions.restrict`, `principle.immutableRules`를 어기면 ✗.
  - `pending`·`red`: 어기는 것 같아도 ✗·⚠로 세지 않고 보고에 "참고"로만 적는다.
- `reference` 폴더는 읽지 않는다. conceptpowers의 원칙이다.
- 개념 문서가 없는 프로젝트에서는 DECISIONS가 근거다 (히스토리 갈래가 본다).

### 2.5 수치 (`metrics`)

- 잴 것은 매니저가 맡기기 전에 정해 프롬프트로 준다: 응답 시간, 빌드 시간, 번들·파일 크기, 메모리, 특정 출력값 등. 수치 기준이 없으면 갈래를 보지 않는다 (`na`).
- 항목마다 `측정 방법(명령) · 단위 · 한계값 · 변경 전 값`을 가진다. 변경 전 값은 매니저가 맡기기 전에 명령으로 재서 `## 기준선`에 넣은 것을 쓴다. 한계값을 평가 에이전트가 정하지 않는다.
- **측정은 3번 재서 중앙값**을 쓴다. 빌드처럼 오래 걸려 3번이 부담이면 1번만 재고 이유를 적는다. 한 번 잰 값으로 ✗·⚠를 내지 않는다는 뜻이므로, 1번만 쟀을 때 한계값에 아슬아슬하면(10% 이내) 한 번 더 잰다.
- **판정**
  - 한계값 초과 → ✗
  - 한계값 안, 변경 전보다 10% 넘게 나빠짐 → ⚠ (통과하되 사용자가 정한다). 나빠짐 비율은 `(측정값 - 변경 전) / 변경 전`이고 값이 클수록 나쁜 수치 기준이다. 작을수록 나쁜 수치(처리량 등)는 부호를 뒤집는다. 변경 전 값이 0이면 비율을 못 구하므로 한계값만 본다.
  - 그 밖(정확히 10%도 포함) → ✓
- 보고와 띠에 `측정값/한계값`, 나빠졌으면 `(+차이)`를 적는다.

## 3. 종합 판정

- ✗가 하나라도 있으면 실패. 실패 원인 칸에 갈래를 적는다 (예: "히스토리: DECISIONS 2026-11-05 위반").
- ✗ 없고 ⚠만 있으면 통과. 보고의 `사용자 확인 필요`에 ⚠ 항목을 적는다. 받아들일지는 사용자가 정한다.
- 개념 갈래의 위반은 히스토리와 같이 ✗다.
- 결정 점검은 ✗ 개수에 더하지 않는다. 결정 때문에 생긴 ✗는 해당 갈래에서 센다.
- ✗ 개수는 다섯 갈래 전체의 ✗ 합이다. 보고 마지막 줄에 적는다 (매니저가 진척을 센다).

## 4. 평가 보고 형식 (평가 에이전트 → 매니저)

```
- 판정: 통과 | 실패
- 갈래별
  - 기준 ✓ 3/3 — <근거>
  - 히스토리 ✗ — DECISIONS 2026-11-05 "<제목>": <어떻게 어겼나>
  - 부작용 ✓ — `pnpm test` 128 통과, 사용처 4곳 확인
  - 개념 – — conceptpowers 꺼짐
  - 수치 ⚠ — 응답 182ms/300 (변경 전 120, +52%) · 빌드 4.1s/10 (+0.3)
- 실패 원인 추정 (실패일 때)
- 사용자 확인 필요: ⚠ 항목, 주관 기준
- 재실행 생략: 명령 · 대조 근거 (있으면)
- 더한 갈래: `## 볼 갈래`에서 뺐는데 필요해 더한 갈래와 이유 (있으면)
- 등급 올림: 바뀐 내용의 검증 신호·무조건 상 조건을 보니 등급이 낮았으면 이유와 올릴 등급 (없으면 생략)
- 결정 점검: 결정마다 유지 | 재검토 — 근거
- ✗ 개수: <n>
```

## 5. 진행 파일 계약: `war-room/.eval/<롤 id>.json`

평가 에이전트가 ③에서만 쓰고, 입력창 위 평가 띠(mod)가 읽는다. 기준 검토는 진행 파일을 쓰지 않는다. 이 파일 하나만 계약이다. 이 폴더는 커밋하지 않는다 (설치 때 `.gitignore`에 `war-room/.eval/`를 넣는다).

```json
{
  "task": "로그인 폼 수정",
  "role": "frontend",
  "maxAttempts": 1,
  "previous": {
    "attempt": 1,
    "verdict": "fail",
    "items": [
      { "group": "criteria", "status": "pass", "summary": "3/3" },
      { "group": "history", "status": "fail", "summary": "DECISIONS 11-05" },
      { "group": "side-effects", "status": "pass", "summary": "테스트 128 통과" },
      { "group": "concepts", "status": "na", "summary": "conceptpowers 꺼짐" },
      { "group": "metrics", "status": "pass", "metrics": [
        { "name": "응답", "value": 182, "unit": "ms", "limit": 300, "baseline": 120 }
      ] }
    ]
  },
  "current": {
    "attempt": 2,
    "state": "running",
    "focus": "히스토리 위반 고친 결과",
    "items": [ { "group": "criteria", "status": "pass", "summary": "3/3" },
               { "group": "history", "status": "running" } ]
  },
  "updatedAt": "2026-11-09T13:40:00+09:00"
}
```

| 필드 | 값 |
|---|---|
| `group` | `criteria` `history` `side-effects` `concepts` `metrics` (고정) |
| `status` | `pass` `fail` `warn` `running` `pending` `na` |
| `current.state` | `running` `done` `aborted` (`planning`·`planned`는 새로 쓰지 않는다. 예전 파일을 읽는 평가 띠 mod 호환으로 값만 남긴다) |
| `verdict` | `pass` `fail` (`done`일 때 `current`에 쓴다. 다음 시도로 `previous`에 옮겨진다) |
| `updatedAt` | ISO 8601 시각 (타임존 포함) |

### 쓰는 시점

- **③ 평가 실행**
  - 시작할 때 `current`를 새로 만든다 (`state: "running"`). `items`는 `## 볼 갈래`의 갈래를 `pending`, 뺀 갈래를 `na`(summary "해당 없음: 이유")로 둔다. 직전 `current`가 `state: "done"`이면 `previous`로 옮긴다. `aborted`(예전 파일이면 `planning`·`planned`도)인 `current`는 옮기지 않고 버린다.
  - 평가 에이전트가 뺀 갈래를 더하면 그 항목을 `na`에서 판정값으로 고친다. `na`는 진척 수(✗ 개수)에 들어가지 않는다.
  - 갈래 하나를 끝낼 때마다 그 항목을 고쳐 쓰고 `updatedAt`을 갱신한다. 하는 중인 갈래는 `running`으로 표시한다.
  - 끝나면 `state: "done"`과 `verdict`를 쓴다.
- 오래 걸리는 갈래(긴 빌드 등)가 30분을 넘길 수 있으면, 그 갈래를 시작하며 `updatedAt`을 한 번 더 고친다 (측정 시작 시각).
- 쓸 때는 파일 전체를 다시 쓴다. 폴더가 없으면 만든다. JSON이 깨지지 않게 쓴다.
- 평가 에이전트는 Edit·Write 도구가 없으므로 Bash로 쓴다. 이 파일 하나만 쓴다.

```bash
mkdir -p war-room/.eval
cat > war-room/.eval/frontend.json <<EOF
{"task":"로그인 폼 수정","role":"frontend","maxAttempts":1,
 "current":{"attempt":1,"state":"running","focus":"기준 판정","items":[]},
 "updatedAt":"$(date -Iseconds)"}
EOF
```

### 읽는 쪽 규칙

- 띠는 `current.state`가 `running`인 파일마다 블록 하나씩 그린다 (예전 파일의 `planning`도 그린다). 파일이 없거나 형식이 틀리면 아무것도 그리지 않는다.
- `updatedAt`이 30분 넘게 지난 `running`(예전 파일의 `planning` 포함)은 그리지 않는다 (죽은 에이전트가 남긴 파일 방지).
- 평가 에이전트가 도는 동안만 보이고, 평가가 끝나면 사라진다. 다음 시도 평가가 시작되면 다시 나타나고 방금 결과가 "이전"이 된다.
