# 평가 롤 (evaluator)

일이 끝나면 임시 검증 에이전트 대신 평가 롤이 판정한다 (중·상 등급. 하는 기계 검사만으로 판정하고 평가 롤을 띄우지 않는다. 등급은 `verify-loop.md` 1절). 이번 일에 붙인 기준만이 아니라 **지난 결정·부작용·개념·수치**까지 본다. 평가 롤은 코드를 고치지 않고 판정만 한다. 평가 에이전트는 읽기 전용 `armory:evaluator`로 띄운다.

## 0. 켜짐·꺼짐·없음

| 상태 | 판단 | 동작 |
|---|---|---|
| 꺼짐 | `roles.evaluator: false` (롤 파일 유무 무관) | 평가 롤을 쓰지 않는다. `verify-loop.md` 2절 기존 방식(검증·QA 롤 → 임시 검증 에이전트. 검증·QA 롤을 띄울 때도 플러그인이 있으면 `armory:evaluator` 종류로 띄우고 그 롤 파일을 프롬프트에 넣는다. 임시 검증 에이전트도 `armory:evaluator`)으로 돌아간다. 진행 파일을 쓰지 않으므로 띠도 안 뜬다 |
| 켜짐 | `false`가 아니고(`true`이거나 키 없음) `roles/evaluator.md`가 있음 | 이 문서대로 평가한다 |
| 없음 (기존 설치) | `false`가 아니고(`true`이거나 키 없음) `roles/evaluator.md`가 없음 | 경고하고(SKILL.md의 "파일 없는 롤" 규칙) 그 배정은 꺼짐과 같이 기존 방식으로 마친다. 파일이 없는 것을 처음 안 그 배정에서 한 번 "평가 롤을 추가할 수 있어요"라고 알리고, 승인하면 템플릿에서 `roles/evaluator.md`를 복사하고 config에 `"evaluator": true`, `.gitignore`에 `war-room/.eval/`를 넣는다. 거절하면 `DECISIONS.md`에 적고 다시 묻지 않는다 |

- `evaluator`는 `manager`와 달리 끄기·삭제할 수 있다.
- **두 축은 별개다.** 평가 롤이 켜졌는지(config와 롤 파일)와 평가 에이전트 종류(armory 플러그인 유무)는 따로 본다.
  - 플러그인이 있으면 평가 롤이 꺼졌거나 없어도 검증·기준 검토 에이전트는 `armory:evaluator`로 띄운다. 이때는 다섯 갈래 대신 기준별로 판정한다.
  - 플러그인이 없으면(다른 도구로 설치) `general-purpose`로 되돌리고 그렇다고 알린다. 이때 읽기 전용은 프롬프트 규칙과 스냅숏 비교(7절)에만 기댄다.
  - 플러그인 유무는 사용 가능한 에이전트 종류에 `armory:evaluator`가 있는지로 본다.
- 기존 설치에 추가할 때 검증·QA 롤이 있으면, 두 롤의 경계를 양쪽 `하지 않는 일`에 적자고 함께 제안한다.

## 1. 흐름

```
요청 → 매니저 배정 ─→ (상) 기준 검토 → ① 평가 롤: 평가 계획 (항목 초안 + 변경 전 수치 측정)
                         │  사용자가 정할 것 있으면 확인
                         ↓
                    ② 담당 롤 작업 (시도 n)
                         ↓
                    (상) 문서 미리 쓰기 → 스냅숏 (7절)
                         ↓
                    ③ 평가 롤: 평가 실행 (띠 표시)
                         ├ 통과 → ⚠ 있으면 사용자 확인 → 끝
                         └ 실패 → verify-loop 3절대로 다시 맡김 → ② (띠의 "이전"에 이번 결과)
```

- ①과 ③은 각각 새 평가 에이전트다. `subagent_type: armory:evaluator`, `description: evaluator: <작업 요약>`. 플러그인이 없을 때만 `general-purpose`로 되돌리고 그렇다고 알린다 (0절).
- 등급별로 돈다: 하는 평가 롤을 띄우지 않는다. 중은 ③만 (① 계획은 수치 갈래가 필요할 때만, 없으면 매니저가 맡기기 전에 기준선을 뜬다). 상은 기준 검토(`verify-loop.md` 1절) + ① + ③이다.
- `model`은 Agent 호출의 `model`로 넘긴다: 중은 `haiku`, 상은 롤 파일의 `model`(없으면 `sonnet`).
- ①의 결과(평가 계획)는 매니저가 ③에 그대로 넘긴다. ③이 계획에 없는 항목을 발견하면 추가하고 보고에 적는다.
- 매니저가 직접 처리한 일도 같은 흐름이다.
- 예외: 답만 하는 질문과 문서 상태 갱신만 하는 일(STATUS·LESSONS 정리)은 평가하지 않는다. 판단 근거는 바뀌는 코드·동작이 없어 히스토리·부작용·수치를 볼 대상이 없기 때문이다.
- 중·상은 한 파일 몇 줄짜리라도 평가 롤을 띄운다. 다만 수치 갈래는 성능·크기에 영향이 없으면 `–`로 둔다. 하 등급 일은 기계 검사 결과로 끝내고, 사후 점검에서 3개 이상 바뀌었거나 상 조건에 걸리면 올려서 평가한다.
- 사용자가 정할 것(한계값 미정, 결정끼리 충돌 등)이 있을 때만 ① 뒤에 확인받는다. 그 밖에는 항목 초안을 묻지 않고 진행한다.
- 시도 2번째부터는 ①을 다시 하지 않고 같은 평가 계획으로 ③만 새로 띄운다.

### 여러 롤에 나눈 일

- 여러 롤 병렬은 등급 상이다. 평가는 롤마다 따로 한다. 롤마다 ①·③이 따로 돈다. 스냅숏은 모든 롤의 구현이 돌아온 뒤 한 번에 뜬다 (7절).
- 진행 파일도 롤마다 따로 둔다 (`war-room/.eval/<롤 id>.json`). 동시에 돌아도 서로 덮어쓰지 않는다.
- 롤별 평가가 모두 통과한 뒤, 롤 사이 부작용을 보려고 매니저가 전체 테스트를 한 번 더 돌린다 (부작용 갈래와 같은 명령). 병렬로 맡기기 전의 공유 약속은 `delegation.md` 4절.

### 이미 검증·QA 롤이 있는 프로젝트

- evaluator가 켜져 있으면 평가는 evaluator가 맡는다. `verify-loop.md` 2절의 "검증·QA 롤에 맡긴다"는 evaluator가 꺼져 있거나 없을 때만 적용한다.
- 사용자가 만든 QA 롤의 `완료 기준`·`일하는 방식`은 evaluator가 기준 갈래에 더해 쓴다 (롤 파일을 `refs`처럼 읽는다).

## 2. 평가 항목 다섯 갈래

각 항목은 `갈래 · 내용 · 확인 방법 · 판정`을 가진다. 판정은 `✓` 통과, `✗` 실패, `⚠` 한계 안에서 나빠짐, `–` 해당 없음.

### 2.1 기준 (`criteria`)

- 사용자가 말한 기준과 롤의 `완료 기준` (`verify-loop.md` 1절 그대로). 기준마다 `확인 방법`의 명령을 직접 실행하거나 직접 보고 판정한다. 실행하지 않은 기준은 통과로 치지 않는다 (기준을 읽고 넘어가면 ✗도 ✓도 아니다. 실행 못 한 이유를 적고 실패로 본다).
- 검증·QA 롤이 있으면 그 롤의 `완료 기준`·`일하는 방식`을 더한다.

### 2.2 히스토리 (`history`)

- `war-room/DECISIONS.md`: 바뀐 파일의 경로와 겹치거나 주제가 같은 항목을 고른다. 결정이 뒤집힌 항목은 최신 것만 본다. 거스르면 ✗.
- `war-room/LESSONS.md`와 `archive/LESSONS-*.md`: 같은 실수를 되풀이하면 ✗.
- `git log` (바뀐 파일마다 최근 커밋 몇 개): 직전 커밋이 일부러 한 변경을 되돌리는지 본다. 되돌림이 이번 요청의 뜻이 아니면 ✗.
- 판정 근거에 항목 날짜·제목 또는 커밋 해시를 적는다.

### 2.3 부작용 (`side-effects`)

- 프로젝트 전체 테스트 명령을 돌린다. 명령은 `roles/manager.md`의 프로젝트별 규칙에서 읽는다. 없으면 평가 계획에서 찾아 적고, 못 찾으면 "테스트 명령 없음"으로 알린다.
- 바뀐 파일이 내보내는 이름(함수·컴포넌트·설정 키)을 쓰는 곳을 찾아(grep 등 프로젝트에 맞는 방법), 이번 변경에 깨질 수 있는 곳을 확인한다.
- 다른 롤의 `scope`에 든 파일이 바뀌었으면 이유가 담당 롤 보고에 있는지 본다. 이유 없이 바뀌었으면 ✗.
- 계획의 "원래 실패하던 테스트" 목록에 없던 테스트가 실패하면 ✗. 목록에 있던 실패는 ✗로 세지 않는다.

### 2.4 개념 (`concepts`, conceptpowers)

- 켜짐 판단: `docs/conceptpowers/init.json`이 있고 `enabled`가 `true`. 아니면 갈래 전체 `–` ("conceptpowers 꺼짐"이라고 적는다).
- conceptpowers의 review 스킬을 쓸 수 있으면 그 스킬로 바뀐 코드에 매핑된 개념을 점검한다.
- 쓸 수 없으면 직접 읽는다: `docs/conceptpowers/concepts/data/<그룹>/<개념>.json`. 바뀐 코드에 매핑된 개념(코드의 `@concept` 태그, 매핑 캐시)을 찾는다.
  - `status: green`: `actions.restrict`, `principle.immutableRules`를 어기면 ✗.
  - `pending`·`red`: 어기는 것 같아도 ✗·⚠로 세지 않고 보고에 "참고"로만 적는다.
- `reference` 폴더는 읽지 않는다. conceptpowers의 원칙이다.
- 개념 문서가 없는 프로젝트에서는 DECISIONS가 근거다 (히스토리 갈래가 본다).

### 2.5 수치 (`metrics`)

- 평가 계획에서 잴 것을 정한다: 응답 시간, 빌드 시간, 번들·파일 크기, 메모리, 특정 출력값 등. 이번 변경과 관계있는 것만. 없으면 갈래 `–`.
- 항목마다 `측정 방법(명령) · 단위 · 한계값 · 변경 전 값`을 가진다. 변경 전 값은 ①에서 작업 전에 잰다.
- **한계값 출처 순서**: (1) 사용자가 말한 값 → (2) 롤 문서나 `DECISIONS.md`에 적힌 값 → (3) 둘 다 없으면 평가 롤이 초안(변경 전 값에 여유를 둔 값)을 내고 **사용자에게 확인받는다**. 앞 출처가 있으면 뒤 출처는 보지 않는다. 사용자 확인으로 확정한 한계값은 매니저가 `DECISIONS.md`에 적어 다음 평가가 (2)로 쓴다.
- **측정은 3번 재서 중앙값**을 쓴다. 빌드처럼 오래 걸려 3번이 부담이면 1번만 재고 이유를 적는다. 한 번 잰 값으로 ✗·⚠를 내지 않는다는 뜻이므로, 1번만 쟀을 때 한계값에 아슬아슬하면(10% 이내) 한 번 더 잰다.
- **판정**
  - 한계값 초과 → ✗
  - 한계값 안, 변경 전보다 10% 넘게 나빠짐 → ⚠ (통과하되 사용자가 정한다). 나빠짐 비율은 `(측정값 - 변경 전) / 변경 전`이고 값이 클수록 나쁜 수치 기준이다. 작을수록 나쁜 수치(처리량 등)는 부호를 뒤집는다. 변경 전 값이 0이면 비율을 못 구하므로 한계값만 본다.
  - 그 밖(정확히 10%도 포함) → ✓
- 보고와 띠에 `측정값/한계값`, 나빠졌으면 `(+차이)`를 적는다.

## 3. 종합 판정

- ✗가 하나라도 있으면 실패. `verify-loop.md` 3절 표대로 다시 맡긴다. 실패 원인 칸에 갈래를 적는다 (예: "히스토리: DECISIONS 2026-11-05 위반").
- ✗ 없고 ⚠만 있으면 통과. 보고 뒤 사용자에게 ⚠ 항목을 보여주고 받아들일지 묻는다. 안 받아들이면 그 항목을 ✗로 보고 다시 맡긴다 (시도 횟수는 이어서 센다).
- 멈춤 조건·끝까지 모드·못 미칠 때 보고는 `verify-loop.md` 그대로. 다만 진척을 세는 수를 바꾼다.
  - **진척 수 = 다섯 갈래 전체의 ✗ 개수.** 두 번 연속 ✗ 개수가 줄지 않으면 "나아지지 않는 반복"이다.
  - **최고 결과** = ✗가 가장 적은 시도. 같으면 ✓가 많은 시도, 그것도 같으면 나중 시도.
  - `verify-loop.md` 3·4절의 "통과한 기준 수"는 이 수로 바꿔 읽는다.
- 개념 갈래의 위반은 히스토리와 같이 실패로 처리해 다시 맡긴다.

## 4. 평가 보고 형식 (평가 에이전트 → 매니저)

```
- 판정: 통과 | 실패
- 갈래별
  - 기준 ✓ 3/3 — <근거>
  - 히스토리 ✗ — DECISIONS 2026-11-05 "<제목>": <어떻게 어겼나>
  - 부작용 ✓ — `pnpm test` 128 통과, 사용처 4곳 확인
  - 개념 – — conceptpowers 꺼짐
  - 수치 ⚠ — 응답 182ms/300 (변경 전 120, +52%) · 빌드 4.1s/10 (+0.3)
- 실패 원인 추정 (실패일 때)
- 사용자 확인 필요: ⚠ 항목, 주관 기준
- 계획에 없던 항목 추가: (있으면)
- 등급 올림: 바뀐 파일 수·종류를 보니 등급이 낮았으면 이유와 올릴 등급 (없으면 생략)
- 이어받기 점검 (상): STATUS·DECISIONS만 읽고 이번 일의 상태와 결정을 말할 수 있는가. 못 하면 갈래 히스토리의 ✗로 같이 다룬다
```

- 상 등급의 ③은 이어받기 점검도 한다: `war-room/STATUS.md`와 `DECISIONS.md`만 읽고 이번 일의 상태와 결정을 말할 수 있는지 본다. 매니저가 미리 써 둔 `(검증 대기)` 항목이 있으면 그것도 대상이다. 말할 수 없으면 기준 실패와 같이 다룬다 (갈래: 히스토리). 통과하면 매니저가 `(검증 대기)`를 뗀다.

## 5. 진행 파일 계약: `war-room/.eval/<롤 id>.json`

평가 에이전트가 쓰고, 입력창 위 평가 띠(mod)가 읽는다. 이 파일 하나만 계약이다. 이 폴더는 커밋하지 않는다 (설치 때 `.gitignore`에 `war-room/.eval/`를 넣는다).

```json
{
  "task": "로그인 폼 수정",
  "role": "frontend",
  "maxAttempts": 3,
  "previous": {
    "attempt": 1,
    "verdict": "fail",
    "items": [
      { "group": "criteria", "status": "pass", "summary": "3/3" },
      { "group": "history", "status": "fail", "summary": "DECISIONS 11-05" },
      { "group": "side-effects", "status": "pass", "summary": "테스트 128 통과" },
      { "group": "concepts", "status": "na", "summary": "conceptpowers 꺼짐" },
      { "group": "metrics", "status": "pass", "metrics": [
        { "name": "응답", "value": 182, "unit": "ms", "limit": 300, "baseline": 120 }
      ] }
    ]
  },
  "current": {
    "attempt": 2,
    "state": "running",
    "focus": "히스토리 위반 고친 결과",
    "items": [ { "group": "criteria", "status": "pass", "summary": "3/3" },
               { "group": "history", "status": "running" } ]
  },
  "updatedAt": "2026-11-09T13:40:00+09:00"
}
```

| 필드 | 값 |
|---|---|
| `group` | `criteria` `history` `side-effects` `concepts` `metrics` (고정) |
| `status` | `pass` `fail` `warn` `running` `pending` `na` |
| `current.state` | `planning` `planned` `running` `done` `aborted` |
| `verdict` | `pass` `fail` (`done`일 때 `current`에 쓴다. 다음 시도로 `previous`에 옮겨진다) |
| `updatedAt` | ISO 8601 시각 (타임존 포함) |

### 쓰는 시점

- **① 평가 계획**: 시작할 때 `current.state: "planning"`, `focus: "변경 전 측정"`으로 쓴다. 띠는 "지금 (계획) … 변경 전 측정 중" 한 줄을 보인다. 끝나면 `state: "planned"`로 두고 띠는 사라진다. 이때는 `previous`로 옮기지 않는다 (계획은 평가 결과가 아니다).
- **① 변경 전 전체 테스트**: 변경 전 수치와 함께 전체 테스트도 미리 돌려 원래 실패하던 테스트 목록을 계획에 적는다. ③은 그 목록에 없던 실패만 부작용 ✗로 본다.
- **③ 평가 실행**
  - 시작할 때 `current`를 새로 만든다 (`state: "running"`, `items`는 다섯 갈래 모두 `pending`). 직전 `current`가 `state: "done"`이면 `previous`로 옮긴다. `planned`·`aborted`인 `current`는 옮기지 않고 버린다.
  - 갈래 하나를 끝낼 때마다 그 항목을 고쳐 쓰고 `updatedAt`을 갱신한다. 하는 중인 갈래는 `running`으로 표시한다.
  - 끝나면 `state: "done"`과 `verdict`를 쓴다.
- 오래 걸리는 갈래(긴 빌드 등)가 30분을 넘길 수 있으면, 그 갈래를 시작하며 `updatedAt`을 한 번 더 고친다 (측정 시작 시각).
- 쓸 때는 파일 전체를 다시 쓴다. 폴더가 없으면 만든다. JSON이 깨지지 않게 쓴다.
- 평가 에이전트는 Edit·Write 도구가 없으므로 Bash로 쓴다. 이 파일 하나만 쓴다.

```bash
mkdir -p war-room/.eval
cat > war-room/.eval/frontend.json <<EOF
{"task":"로그인 폼 수정","role":"frontend","maxAttempts":3,
 "current":{"attempt":1,"state":"running","focus":"기준 판정","items":[]},
 "updatedAt":"$(date -Iseconds)"}
EOF
```

### 읽는 쪽 규칙

- 띠는 `current.state`가 `running` 또는 `planning`인 파일마다 블록 하나씩 그린다. 파일이 없거나 형식이 틀리면 아무것도 그리지 않는다.
- `updatedAt`이 30분 넘게 지난 `running`·`planning`은 그리지 않는다 (죽은 에이전트가 남긴 파일 방지).
- 평가 에이전트가 도는 동안만 보이고, 평가가 끝나면 사라진다. 다음 시도 평가가 시작되면 다시 나타나고 방금 결과가 "이전"이 된다.

### 매니저가 정리한다

- 평가 에이전트가 돌아올 때마다(정상·오류·중단 모두) 그 롤의 진행 파일을 열어 `state`가 아직 `running`·`planning`이면 `aborted`로 고친다.
- 일이 완전히 끝나면(통과 확정 또는 멈춤) 그 파일을 지운다.

## 7. 읽기 전용 확인: 평가 전후 스냅숏

적용 범위는 평가·검증 에이전트를 띄울 때마다다 (중·상, 평가 롤 켜짐·꺼짐 모두). 하 등급은 에이전트를 띄우지 않으므로 스냅숏도 없다.

평가 에이전트는 Bash를 가지므로 도구만으로는 파일 쓰기가 완전히 막히지 않는다. 구현 결과가 이미 작업 폴더에 있어서 "바뀐 파일이 없는지"로는 판정할 수 없으니, 평가를 띄우기 직전에 매니저가 스냅숏을 남기고 돌아오면 같은 방법으로 다시 떠서 비교한다.

```bash
mkdir -p war-room/.eval
snap() {
  git status --porcelain --ignored | grep -v ' war-room/\.eval/'
  git diff | shasum
  git diff --cached | shasum
  git ls-files --others --exclude-standard | grep -v '^war-room/\.eval/' | while IFS= read -r f; do shasum -- "$f"; done
}
snap > war-room/.eval/<롤 id>.snapshot      # 평가 직전
snap | diff - war-room/.eval/<롤 id>.snapshot  # 평가 직후, 출력이 없어야 한다
```

- 남기는 것: `git status --porcelain --ignored`, `git diff`와 `git diff --cached`의 해시, 추적 안 되는 파일 각각의 해시. 저장 위치는 `war-room/.eval/<롤 id>.snapshot`이고 커밋하지 않는다.
- `.eval/`은 `.gitignore` 대상이라 `--ignored` 결과에 항상 나오고 평가 에이전트가 진행 파일을 쓰면 달라진다. 그래서 비교에서 `.eval/`을 뺀다.
- 하나라도 다르면 그 평가는 무효다. 바뀐 내용을 사용자에게 알리고, 바뀐 파일을 되돌릴지 정한 뒤 평가를 다시 띄운다.
- 순서는 문서 미리 쓰기(상 등급의 STATUS·DECISIONS) → 스냅숏 → 평가다. 문서 변경이 평가 중 변경으로 잡히지 않게 하려는 것이다.
- 병렬로 맡긴 일은 모든 롤의 구현이 돌아온 뒤 한 번에 스냅숏을 뜨고 평가를 띄운다. 롤별 평가는 동시에 돌려도 된다 (모두 읽기 전용이라 서로 영향이 없다).
- 한계: 저장소 밖(홈 설정, 다른 폴더) 변경은 이 비교로 못 잡는다. 그 범위는 프롬프트 규칙("작업 폴더 밖을 쓰지 않는다")에 맡긴다. 별도 worktree에서 평가하는 방식은 비용이 커서 쓰지 않는다.
- 평가가 끝나면 진행 파일과 함께 스냅숏도 지운다.
