# 롤 에이전트에게 맡기기 (위임 프롬프트)

서브에이전트는 이 대화를 모른다. 매니저가 아는 것을 칸에 나눠 모두 넣는다. 롤 에이전트, 롤 없는 일의 임시 작업 에이전트, 재시도 모두 같은 칸을 쓴다.

## 1. 고정 칸

- 칸을 빼지 않는다. 확인해 보니 넣을 것이 없으면 "없음 (확인함)"이라고 쓴다. 확인하지 않고 "없음"만 채우면 칸이 있는 의미가 없다.
- 칸마다 매니저가 실제로 찾아본 것을 쓴다 (파일 목록은 `ls`·grep으로, 결정은 `DECISIONS.md`에서).
- `## 기준선`은 중·상 등급일 때만, `## 공유 약속`은 병렬일 때만, `## 지난 시도`는 재시도일 때만 쓴다. 해당하지 않으면 칸 자체를 뺀다.
- 기준선은 반드시 구현을 맡기기 전에 뜬 값이다. 구현 뒤에 뜬 실패 목록·수치는 이미 이번 변경이 섞여 있어 기준선으로 쓰지 않는다 (명령 결과라 매니저가 직접 돌려도 된다).

```
너는 이 프로젝트의 <id> 롤이다. 아래 롤 정의를 따른다.

<롤 파일 본문 전체>

## 목표
<한 문장: 무엇이 되어야 하나>

## 범위
<할 일. 사용자 요청 + 매니저가 정리한 범위>

## 범위 밖
<하지 않을 일, 건드리지 않을 경로>

## 관련 파일
<경로 목록>

## 요구 기준 (검증·평가 에이전트가 이 기준으로 따로 판정한다)
1. <기준> · 확인 방법: <명령 → 기대 결과>
2. <사람이 봐야 하는 기준> · 확인 방법: 사람이 본다 (<볼 것>)

## 알려진 예외
<경계값·특수 경우·예외 처리. 매니저가 아는 것>

## 관련 결정
<DECISIONS.md `날짜 · 제목` 목록. `(검증 대기)`는 확정된 결정이 아니므로 표시한다>

## 기준선
<(중·상) 매니저가 맡기기 전에 잰 원래 실패 테스트 목록·테스트 명령, 변경 전 수치 (상은 수치 갈래의 측정 명령·한계값 포함, 병렬이면 롤별)>

## 공유 약속
<(병렬) 다른 롤과 함께 쓰는 형식·필드 이름·함수·타입 이름과 위치·경로. 글자 그대로>

## 지난 시도
<(재시도) 3절 규칙대로>

## 맥락
- 프로젝트 루트: <경로>
- 이 롤의 교훈: <LESSONS.md에서 이 롤 항목, 없으면 "없음 (확인함)">

## 규칙
- 담당 범위(scope) 밖 파일은 꼭 필요할 때만 고치고, 고쳤으면 이유를 보고에 적는다.
- war-room/ 문서는 고치지 않는다 (진행 파일 제외). 정한 것·겪은 문제·가정한 것은 보고에 적어 제안만 한다.
- 사용할 스킬: <롤의 skills, 없으면 생략>
- 먼저 읽을 것: <롤의 refs, 없으면 생략>
- 커밋·push·배포처럼 되돌리기 어려운 일은 하지 않는다. 필요하면 보고에 적는다. 예외: `## 범위`에 커밋(·push·릴리즈)이 적혀 있으면(사용자 승인) 적힌 것만 하고, 커밋에는 매니저가 미리 갱신한 `war-room/` 문서 변경도 넣는다 (내용은 고치지 않는다).

## 보고 형식
- 결과: 완료 | 일부 | 실패
- 바뀐 파일: 경로 목록
- 확인한 것: 돌린 명령과 결과
- 가정한 것: 지시에 없어서 스스로 정한 것 (없으면 "없음 (확인함)")
- 모호했던 것: 두 가지 이상으로 읽힌 지시와 어느 쪽으로 했는지 (없으면 "없음 (확인함)")
- 남은 일·막힌 점, 정한 것 (작업 중 내린 결정과 이유), 겪은 문제 (막혔던 것, 롤 문서에 넣으면 좋을 것)
```

## 2. 보고를 받으면 (검증 전에)

1. 보고의 `가정한 것`과 `모호했던 것`을 **검증 전에** 먼저 읽는다.
2. 기준·범위에 걸리는 가정이면 검증하기 전에 `judgment.md` 1절로 나눈다. 되돌릴 수 있으면 매니저가 정하고 `정한 것:`·`점검할 결정`에 기록하고, 어려우면 사용자에게 묻는다. 기준을 고쳤으면 고친 기준으로 평가한다. 기준과 상관없는 가정은 보고에 옮기기만 한다.
3. `정한 것`도 같은 기준으로 나눈다. `정한 것`·`겪은 문제`는 매니저가 `DECISIONS.md`·`LESSONS.md`에 옮길지 정한다. 서브에이전트는 이 파일들을 쓰지 않는다.

## 3. 재시도 때 넘길 것

- `## 지난 시도`에는 평가·검증 에이전트가 찾은 실패 내용(실패한 기준·갈래, 근거)만 넣는다. 구현 에이전트의 설명이나 자기 평가는 넣지 않는다. 구현이 "이렇게 했다"고 한 말은 판정 근거가 아니다.
- 매니저가 덧붙이는 것은 `이번에 바꿀 것` 한 줄뿐이다 (고칠 부분 | 다른 접근).
- 형식은 `- 시도 n: <실패한 기준·갈래> — <판정 에이전트의 근거>` 줄을 시도마다 쓰고, 마지막에 `- 이번에 바꿀 것: …`을 쓴다.
- 시도 횟수는 STATUS 진행 중의 `시도 n/최대`로 센다. 같은 일이 2번 실패하면 3번째를 맡기기 전에 "기준·설계 다시 보기"를 한다 (`verify-loop.md` 3절).

## 4. 병렬로 맡기기 (공유 약속)

여러 롤을 동시에 맡기면 둘이 같은 형식·이름을 따로 정해 부딪힐 수 있다 (예: 한 롤이 서버 응답 형식을, 다른 롤이 화면 타입을 따로 정해 필드 이름이 어긋난다).

1. 동시에 맡기기 전에 매니저가 두 롤 사이의 약속을 먼저 정한다: 파일 형식, 필드 이름, 함수·타입 이름과 위치, 경로.
2. 정한 약속을 양쪽 프롬프트의 `## 공유 약속`에 **글자 그대로** 넣는다. 한쪽에만 요약해서 넣지 않는다.
3. 맡기기 전에 약속을 정할 수 없으면 동시에 맡기지 않고 순서대로 맡긴다. 먼저 하는 롤이 약속을 만들고, 그 결과를 뒤 롤의 `## 공유 약속`에 넣는다.
4. 병렬은 등급 "상"이다. 평가 순서와 스냅숏은 `evaluation.md` 7절을 따른다.

## 5. 임시 작업 에이전트 (롤 없는 일)

- 맞는 롤이 없고 하 등급이 아닌 구현은 매니저가 직접 하지 않고 임시 작업 에이전트(`general-purpose`)에 이 템플릿으로 맡긴다. 롤 정의 자리에는 "롤 없이 맡기는 일이다. 요청 범위만 한다"는 한 줄을 쓴다.
- 담당은 `manager`로 적고, 롤 제안의 "자주" 신호에 센다 (`role-split.md`).
- 조사·분석 중 파일을 3개 이상 읽어야 하는 것은 읽기 전용 `Explore`에 맡기고 결론만 받는다. 이때는 `## 목표`·`## 범위`·`## 범위 밖`만 써도 된다 (고치는 일이 아니라서 기준 칸은 필요 없다).
