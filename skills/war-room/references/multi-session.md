# 여러 세션 지휘 (감독 세션)

한 일을 저장소·워크트리별로 나눠 여러 세션이 함께 하고, 한 세션이 감독할 때 감독 세션이 따른다. 세션 하나 안에서 롤에 맡기는 절차(SKILL.md "배정")는 그대로다. 작업 세션 규칙과 보고 형식은 `work-session.md`에 있다. 세션에서 두 문서를 한 번 읽었으면 다시 읽지 않는다.

```
사용자 ── 되돌리기 어려운 결정은 여기서만 정한다
  │
감독 세션 ── [감독 지시] ──▶ 작업 세션 A (서버 저장소 워크트리) ─ 자기 war-room 롤
  │       ◀── [작업 보고] ──  작업 세션 B (화면 저장소 워크트리) ─ 자기 war-room 롤
  │                          작업 세션 C (통합 검증)
  ├ 감독 롤 po(요구 분석) · pm(보드 기록) · tpm(진행 검토)
  └ 지휘 보드(COMMAND.md) · 감독 결정(commander/DECISIONS.md) · 감독 교훈(commander/LESSONS.md) · 장소 목록(commander/PLACES.md)
```

## 1. 역할과 지시 ID

- 감독 세션은 배분·사용자 대화·위임만 한다. 구현·조사는 하 등급이라도 직접 하지 않는다. 요구 분석은 po, 보드 기록은 pm, 기계 확인·진행 검토는 tpm, 교차 판정은 `armory:evaluator`에 맡기고 결론만 받는다 (`war-room/commander/commander.md`).
- 지시, 교차 판정 배정, 머지 관문은 감독이 정한다. 기록은 pm이 한다.
- 메시지를 어떻게 옮기든(사용자가 붙여넣기, 세션 간 메시지 도구 `SendMessage`(열린 세션은 `ListAgents`, 사용자는 `/list-agents`), 이슈 댓글) 형식은 같다.
- 새 작업 세션은 감독이 띄우지 않는다. 사용자에게 여는 명령을 안내한다 (`commander/commander.md` "세션이 없을 때").
- 지시 ID: `<이슈 키 또는 작업 이름>-<세션 약칭>-<번호>`. 예: `ORDER-12-API-3`. 보고·판정·기록은 이 ID로 잇는다.

## 2. 위치와 이어받기

- 감독 세션은 작업 세션과 같은 작업 폴더(체크아웃)를 쓰지 않는다. 작업 세션은 저장소마다 별도 워크트리·브랜치에서 일한다.
- 감독 세션은 `war-room/roles/`의 롤(manager 포함)을 쓰지 않는다. 감독 롤(`war-room/commander/roles/`)만 쓴다. 감독 쪽에 매니저는 없다.
- 감독 자리는 지휘 보드 `war-room/COMMAND.md`에 둔다. 지정·이어받기·해제와 보드 갱신 시점은 `war-room-commander` 스킬을 따른다.
- 세션마다 한 줄(`세션 · 맡은 범위 · 위치(워크트리·브랜치) · 마지막 지시 ID · 마지막 보고 커밋 · 상태`)은 pm이 보드 `## 작업 세션`에 적는다. STATUS에는 적지 않는다. 새 감독 세션은 보드로 이어받는다.

## 3. 문서와 기록 위치

- 지휘 보드 `COMMAND.md`와 `war-room/commander/DECISIONS.md`·`war-room/commander/LESSONS.md`·`war-room/commander/PLACES.md`는 감독 롤 pm만 쓴다 (예외: 지정·이어받기·해제 때 `## 감독 자리`·`## 자리 이력`은 그 요청을 받은 세션). 누가 어느 절·파일을 언제 읽는지는 `war-room-commander` 스킬 6절. 작업 세션은 쓰지 않는다.
- 감독 교훈을 `war-room/commander/commander.md` `# 프로젝트별 규칙` 절이나 `war-room/commander/roles/*.md`에 반영하는 일도 pm이 한다. 감독이 사용자에게 보여주고 승인받은 것만, 승인 줄을 위임 프롬프트에 넣어 넘긴다 (`war-room-commander` 스킬 5·6절). 감독 세션은 직접 고치지 않는다.
- 감독 쪽은 작업 세션 매니저의 `war-room/STATUS.md`·`war-room/DECISIONS.md`·`war-room/LESSONS.md`를 쓰지 않는다. 감독 쪽 결정은 `war-room/commander/DECISIONS.md`, 교훈은 `war-room/commander/LESSONS.md`에 pm이 쓴다. 예외: 감독을 지정할 때 STATUS `## 진행 중`에 예전 형식 세션 줄(`세션 · 맡은 범위 · 위치 · …`)이 있으면, 보드로 옮긴 뒤 지정 요청을 받은 세션이 그 줄을 한 번 지운다 (`war-room-commander` 스킬 2절 8단계). 연결 워크트리 작업 세션도 쓰지 않는다 (`work-session.md` 2절).
- 같은 내용을 두 군데 원본으로 두지 않는다.

| 무엇 | 어디 |
|---|---|
| 할 일·완료 조건 | 이슈 트래커 (이슈 키) |
| 감독 자리, 세션 사이 진행·판정·위험·결정 ID, 이어받기 상태 | 지휘 보드 `COMMAND.md`. 화면이 필요하면 `status-dashboard` 진행판(JSON)으로 세션·지시 절을 옮기고 보드에는 경로만 둔다 |
| 감독 쪽 결정 원문(사용자·감독 결정, 위임 범위) | `war-room/commander/DECISIONS.md` (pm). 점검이 남은 결정 ID만 보드 `## 점검할 결정` |
| 감독 쪽 교훈(감독·감독 롤의 시행착오, 연결 워크트리 보고의 `겪은 문제` 중 남길 것) | `war-room/commander/LESSONS.md` (pm). `war-room/LESSONS.md`가 아니다 |
| 반복해 쓰는 위치(파일·폴더, 깃 저장소·이슈, 지라 사이트·키·보드, 문서 URL, 자주 쓰는 명령) | `war-room/commander/PLACES.md` (pm, 사용자가 확인한 위치만). 작업 세션은 읽지 않는다 |
| 세션 안의 시도·평가 | 작업 세션 보고 |

- 보고를 기록에 옮길 때는 한 줄로 요약한다. 보고 원문을 옮기지 않는다.
- 단계가 끝나거나 사용자 결정이 나오면 이슈에 요약 한 줄을 남긴다. 밖으로 보내는 일이라(`judgment.md` 1절 5번) 사용자가 이 일에서 허락했을 때만 한다.

## 4. 감독 지시 고정 칸

`delegation.md` 1절과 같다. 칸을 빼지 않고, 확인해 보니 없으면 "없음 (확인함)"이라고 쓴다. 조건부 칸(`기준선`은 중·상, `공유 약속`은 다른 세션과 맞물릴 때, `지난 시도`는 재시도·보완일 때)은 해당하지 않으면 칸 자체를 뺀다. 문서 내용은 옮겨 적지 않고 경로와 절만 쓴다.

위치는 실제 값으로 쓴다. 요청에 "그 파일"·"그 이슈"·"지라"처럼 위치가 빠져 있으면 po가 `war-room/commander/PLACES.md`에서 찾은 경로·저장소·이슈 키·지라 프로젝트 키를 `## 범위`·`## 기준 문서` 등 맞는 칸에 그대로 넣는다 (`war-room-commander` 스킬 5절). 작업 세션은 PLACES.md를 읽지 않는다. 지시에 넣은 위치가 없거나 접근되지 않으면 보고의 `겪은 문제`에 적는다.

```
[감독 지시] <지시 ID>
## 목표          <한 문장>
## 범위
## 범위 밖       <건드리지 않을 저장소·경로, 다른 세션 몫>
## 작업 위치     <워크트리 경로 · 브랜치 · push 여부>
## 기준 문서     <설계·계획·계약 문서 경로와 절. 공유 약속의 기준은 한 곳>
## 요구 기준     <최소 등급(정했을 때만)> / 번호 · 기준 · 확인 방법: 명령 → 기대 결과
## 관련 결정     <`war-room/commander/DECISIONS.md`의 `날짜 · 제목`, 결정 ID>
## 기준선        <(중·상) 지시 전 커밋 해시, 원래 실패하던 테스트>
## 공유 약속     <맞물리는 형식·필드·경로·오류 코드. 글자 그대로>
## 지난 시도     <판정 근거와 이번에 바꿀 것만. delegation.md 3절>
## 사람 승인     <이번 지시 범위에서 사용자가 승인한 되돌리기 어려운 일. 늘 쓴다>
## 보고 방법     <보고를 둘 곳. 길면 파일 경로만>
```

## 5. 교차 판정 (비용을 정해진 때로 묶는다)

- 작업 세션 판정을 다시 돌리지 않는다. 작업 세션 코드를 직접 읽어 판정하지도 않는다.
- **보고마다 하는 것은 기계 확인뿐이다** (tpm이 한다. 감독은 결과만 받는다): `git -C <워크트리> rev-parse HEAD`가 보고 커밋과 같은지, 기준마다 판정 근거(명령·결과)가 있는지, `git -C <워크트리> diff --stat <기준선>..HEAD`가 범위 안인지 (기준선은 보드 `## 지시` 줄의 기준선 칸. pm이 지시의 `## 기준선`에서 옮긴다. `–`면 보고 `커밋:`의 시작). 어긋나면 그 기준만 보완 지시한다.
- **평가 에이전트(`armory:evaluator`)는 아래 때에만 띄운다.** 한 때에 한 번이고, 보완 뒤에는 보완 범위만 다시 본다.
  - 공유 약속 일치: 보고에 `공유 약속 영향: 있음`이 오거나, 공유 약속에 걸친 단계가 양쪽 세션에서 모두 끝났을 때
  - 보안·권한 심층 검토: 상 등급 일의 구현 단계가 끝났을 때
  - 통합 검증 결과 대조: 통합 검증 세션 보고가 왔을 때 (커밋 짝이 최신 보고 커밋과 같은지는 기계 확인으로 먼저 본다. 다르면 판정하지 않고 다시 돌리게 한다)
  - 머지 관문: 7절
- 대상이 작업 세션 워크트리면 그 워크트리에서 스냅숏을 남기고 비교한다 (`verify.md` 4절).
- 교차 판정 평가 에이전트의 진행 파일 이름은 `war-room/.eval/cross-<지시 ID>.json`(감독 체크아웃)이다. 롤 id 자리에 `cross-<지시 ID>`를 쓴다.
- 기록할 때 출처를 나눈다: `보고`(작업 세션 판정을 옮김) · `감독 확인`(tpm 기계 확인) · `평가`(감독이 띄운 평가 에이전트).

## 6. 승인 권한

- `judgment.md` 1절의 되돌리기 어려운 결정은 사용자만 정한다. 감독은 사용자 대신 승인하지 않는다.
- 사용자가 넘긴 포괄 권한("알아서 진행", "전권" 등)은 처음에 항목으로 풀어 확인받고 pm이 `war-room/commander/DECISIONS.md`에 적는다. 예: `위임됨: 이 브랜치 커밋, 워크트리 생성 · 위임 안 됨: push·머지, 공유 약속 변경, 보안 위험 수용, 범위 확대`. 위임 안 된 항목은 감독도 사용자에게 묻는다.
- 사용자가 승인한 것만 지시의 `## 사람 승인`에 적는다.
- 감독이 정한 되돌릴 수 있는 결정에는 결정 ID(예: `M-3`)를 붙여 pm이 `war-room/commander/DECISIONS.md`에 원문을, 보드 `## 점검할 결정`에 결정 ID를 적고, 5절의 교차 판정 때 함께 점검받는다 (`judgment.md` 4절).
- 공유 약속 변경 보고가 오면 감독이 판단한다. 이미 쓰이는 형식이면 사용자에게 묻는다. 정해지면 기준 문서를 먼저 고치게 하고, 관련된 모든 작업 세션에 같은 문구를 새 지시로 보낸다.

## 7. 머지 관문 (마지막 머지·push 전 한 번)

하나씩 대조하고 결과를 보고한다. 하나라도 남으면 남은 것을 보여주고 사용자에게 묻는다.

1. 중 이상 위험(보안 포함) 미해소 0
2. 사용자 확인 대기 0, 보드 `## 점검할 결정` 남은 것 0
3. 외부 확인 항목 처리 (남은 것은 사용자가 머지 뒤로 미루기로 정했는지)
4. 통합 검증이 최종 커밋 짝으로 통과
5. 작업 세션마다 미커밋 변경 0, 보고 커밋 = 브랜치 HEAD
6. 머지·push는 사용자 승인 뒤에 한다

## 하지 않는 것

- 작업 세션 범위의 코드를 직접 고치거나 `war-room/roles/` 롤에 맡기기
- 감독 세션이 구현·조사(하 등급 포함)·보드 갱신·git 확인을 직접 하기
- 보고마다 평가 에이전트를 띄우기, 작업 세션 판정을 다시 돌리기
- 작업 세션끼리 공유 약속을 정하게 두기
- 사용자 대신 되돌리기 어려운 결정을 승인하기
