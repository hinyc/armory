# 맡기기 → 검증 → 다시 맡기기

맡긴 일은 요구 수준에 맞을 때까지 시키고, 검증하고, 반복한다. 다만 끝없이 돌리지 않는다. 해 본 것 중 가장 좋은 결과도 수준에 못 미치면 **안 된다고 말하고 대안을 낸다.**

```
수준 정하기 → (평가 계획) → 맡기기(시도 n) → 검증 ─ 통과 → (주관 기준은 사용자 확인) → 끝
                  ↑                └ 실패 → 계속할지 판단 ─ 계속 → 다음 시도
                  └────────────────────────────────────────┘     └ 멈춤 → 못 미침 보고 + 대안
```

평가 계획은 evaluator 롤이 켜져 있고 등급이 상일 때(중은 수치 갈래가 필요할 때만) 있다. 켜짐·꺼짐·없음(기존 설치)은 `evaluation.md` 0절을 따른다. 아래 "평가 롤"은 evaluator 롤이다. 검증 비용은 위험도 등급(1절)으로 나눈다.

## 1. 요구 수준 정하기 (맡기기 전에)

- **사용자가 수준을 말했으면** 그대로 쓴다. 측정할 수 있게만 다듬는다.
- **말하지 않았으면** 매니저가 기준 초안을 만든다.
  - 재료: 롤의 `완료 기준`, 요청 내용, 관련 `DECISIONS.md` 항목
  - 작은 일(한두 파일, 정답이 분명한 일)은 초안대로 바로 진행하고 알리기만 한다.
  - 그 밖의 일은 기준을 알리고 진행한다 (`judgment.md` 2절). 예외: 기준이 되돌리기 어려운 결정(`judgment.md` 1절)을 담으면 묻는다 (AskUserQuestion).
- 기준마다 **확인 방법**을 붙이고, 확인할 수 없는 기준은 쓰지 않는다. 가능한 한 실행 가능한 검사로 쓴다: `명령 → 기대 결과` ("이 명령 → 이 출력").
  - 객관 기준: 명령·측정으로 판정한다. 예: `pnpm test` → 실패 0건, 응답 200ms 이하, 콘솔 에러 0
  - 주관 기준: 사람이 봐야 한다. 예: 디자인, 문구 톤, 사용감. 검증 통과 뒤 사용자에게 확인받는다고 표시한다
- `config.json`의 `maxAttempts`(기본 3)를 시도 횟수 상한으로 쓴다. 사용자가 이번 일에 따로 정했으면 그 값을 쓴다.
- **평가 계획 (evaluator 켜짐일 때)**: 상 등급이면 기준을 정한 뒤 맡기기 전에 평가 롤을 한 번 띄워 평가 항목 초안과 변경 전 수치를 만든다 (`evaluation.md` 1절 ①). 중 등급은 수치 갈래가 필요할 때만 ①을 한다. 사용자가 정할 것(한계값 미정, 결정끼리 충돌)이 있을 때만 확인받는다. 답만 하는 질문과 문서 상태 갱신만 하는 일은 건너뛴다. 2번째 시도부터는 같은 계획을 쓴다.
- **기준선 (평가 계획 ①이 없는 중·상)**: 구현을 맡기기 전에 매니저가 전체 테스트 명령을 돌려 원래 실패하던 테스트 목록(기준선)을 남기고 위임 `## 기준선`과 ③ 프롬프트에 넣는다. 구현 뒤에 뜬 목록은 기준선으로 쓰지 않는다 (명령 결과라 매니저가 돌려도 된다).

### 위험도 등급

매니저가 배정 3번에서 정하고 알리기 줄에 적는다. 사용자가 바꿀 수 있다. 애매하면 높은 쪽으로 한다. 사용자가 정한 등급은 그대로 따르되, 하이면 끝난 뒤 사후 점검을 거치고 걸리면 알린 뒤 묻는다 (아래 표).

| 등급 | 어떤 일 | 검증 |
|---|---|---|
| 하 | 동작이 바뀌지 않는 일: 오타·문구, 주석, 한 파일 몇 줄 설정, 승인된 교훈을 롤 문서에 넣기, 상태 문서 정리 | 기계 검사만. 명령(테스트·린트·validate·grep)을 돌리고 그 결과로 판정한다. 매니저가 돌려도 된다 (판단이 아니라 명령 결과라서). 평가 롤을 띄우지 않는다 |
| 중 | 기능 추가·수정, 여러 파일, 동작이 바뀌는 일 | 평가 ③만 (① 계획은 수치 갈래가 필요할 때만). 평가 에이전트 model은 `haiku`. 기준선은 위 1절 규칙 |
| 상 | 배포·릴리즈·push, 구조·인터페이스 변경, 데이터 삭제·마이그레이션, 공개 노출, 보안·권한, 여러 롤 병렬 | 기준 검토 + 평가 ① + ③. 평가 에이전트 model은 롤 파일 값(기본 `sonnet`). 되돌리기 어려운 단계 전에 사람 승인 |

**무조건 상** (매니저 판단으로 낮추지 않는다. 아래 중 하나라도 걸리면 상이다)
- 릴리즈·push·배포
- war-room 지침·롤 파일·config·스킬 절차 수정. 예외: 사용자가 승인한 문장을 그대로 넣는 롤 문서 수정은 하다. 근거는 문장이 정해져 있어 판단이 끼지 않기 때문이고, 확인은 그 문장이 해당 절에 있는지 grep으로 한다. 문장을 바꾸거나 새 규칙을 쓰면 상이다.
- 시스템 프롬프트에 들어가는 문구(mod 지침) 수정
- 여러 롤 병렬
- 바뀌는 파일 5개 이상
- 삭제·마이그레이션
- 공개 노출
- 권한·보안

**하 조건** (모두 맞아야 한다)
1. 동작이 바뀌지 않는다.
2. 바뀌는 파일이 2개 이하다.
3. 돌릴 기계 검사가 있다. 기계 검사가 하나도 없으면(돌릴 명령이 없으면) 중으로 올린다.
4. 위 무조건 상 조건에 하나도 걸리지 않는다.

**어느 단계를 거치나** (입력마다)

| 입력 | 거치는 단계 |
|---|---|
| 새 요청 | 무조건 상 조건 → 하 조건 4개 → 하가 아니면 위 표로 중·상 (둘 다 맞으면 높은 쪽) |
| 롤 없이 직접 하는 일 | 새 요청과 같다. 하가 아니면 평가 에이전트가 판정한다 (매니저 자기 검토 금지) |
| 하 일을 끝낸 직후 (사후 점검) | `git diff --stat`으로 바뀐 파일 수를 센다. 3개 이상이거나 무조건 상 조건에 걸리면 그 자리에서 등급을 올려 평가한다. 2개 이하면 하로 끝낸다 |
| 평가 보고의 `등급 올림` 칸 | 평가 에이전트가 실제 변경 범위(바뀐 파일 수·종류)를 보고 등급이 낮았다고 적은 것이다. 올린 등급의 검증을 다시 한다 (중 → 상이면 기준 검토와 사람 승인을 더한다) |
| 사용자가 바꾼 등급 | 위 단계를 건너뛰고 그 등급으로 한다. 알리기 줄에 사용자가 정했다고 적는다. 예외: 사용자가 정하거나 낮춘 등급이 하이면 끝낸 직후 위 사후 점검은 거친다. 근거는 낮춘 등급이 실제 변경 범위와 맞는지 확인할 방법이 그것뿐이기 때문이다. 기준에 걸리면(바뀐 파일 3개 이상이거나 무조건 상) 매니저가 혼자 올리지 않고 결과를 알리고 올릴지 묻는다 |

- 매니저가 직접 한 하 일은 STATUS 최근 완료에 등급과 바뀐 파일 수를 적어 나중에 확인할 수 있게 한다.
- 평가 롤이 꺼졌거나 없어도 플러그인이 있으면 중·상의 판정은 `armory:evaluator`로 한다 (다섯 갈래 대신 기준별 판정). 플러그인이 없을 때만 `general-purpose`로 되돌리고 알린다.

### 기준 검토 (상 등급만)

기준이 틀리거나 빠지면 구현과 검증이 둘 다 통과한다. 그래서 상은 맡기기 전에 기준을 따로 검토한다. 중 이하는 하지 않는다 (작은 일까지 느려지지 않게).

- 맡는 것: 평가 ① 계획 에이전트. 매니저와 대화를 공유하지 않는 새 에이전트라 독립적이다. 평가 롤이 꺼졌거나 없으면 읽기 전용 에이전트(`armory:evaluator`) 하나에 같은 질문만 따로 묻는다.
- 받는 것: 요청 원문 요지, 목표·범위·범위 밖, 기준, 관련 결정.
- 묻는 것: "이 기준에서 빠진 경우(예외, 경계값, 다른 롤 영향, 실패 경로)가 무엇인가".
- 보고 칸 `기준에 빠진 것`을 받으면 하나씩 셋 중 하나로 처리한다.
  - 받아들임: 요청 범위 안이고 확인 방법을 붙일 수 있으면 기준에 넣는다.
  - 보류: 범위를 넓히거나 사용자만 정할 수 있는 것이면 묻는다 (`judgment.md` 1절 7·8번과 같은 기준). 답이 올 때까지 맡기지 않는다. 사용자가 나중에 정하겠다고 하면 `## 알려진 예외`에 "미정"으로 적고 맡긴다.
  - 거절: 범위 밖이거나 확인할 수 없는 것은 한 줄 이유와 함께 보고에 적고 넘어간다.
  - 받아들임·거절은 매니저가 정하는 결정이라 `정한 것:`·`점검할 결정` 대상이다.

## 2. 검증

- **구현한 에이전트와 매니저가 자기 결과를 판정하지 않는다.** 예외는 하 등급이다. 하는 판단이 아니라 기계 검사의 명령 결과로 판정하므로 매니저가 명령을 돌려 결과를 읽어도 된다. 하 등급 일은 평가 롤을 띄우지 않는다.
- 중·상은 두 축으로 고른다. 두 축은 서로 독립이다.
  - **평가 롤 켜짐 여부** (config `roles.evaluator`와 롤 파일): 켜짐이면 평가 롤이 평가 계획대로 다섯 갈래(기준·히스토리·부작용·개념·수치)를 판정한다. 절차·프롬프트·보고 형식·종합 판정은 `evaluation.md`를 따르고, 아래 검증 에이전트 프롬프트는 쓰지 않는다. 평가 에이전트에게도 구현 에이전트의 "잘 됐다" 설명은 주지 않는다. 사용자가 만든 QA 롤이 있어도 평가는 평가 롤이 맡고, QA 롤의 완료 기준은 기준 갈래에 더한다. 꺼짐·없음이면 기준별로 판정한다. 켜진 롤 중 검증·QA를 맡는 롤이 있으면 그 롤에 맡기고(플러그인이 있으면 `armory:evaluator` 종류로), 없으면 아래 프롬프트로 새 서브에이전트를 검증 전용으로 띄운다.
  - **에이전트 종류** (armory 플러그인 유무): 플러그인이 있으면(사용 가능한 에이전트 종류에 `armory:evaluator`가 있으면) 위 어느 경우든 검증·기준 검토 에이전트는 `armory:evaluator`로 띄운다. Edit·Write 도구가 없는 읽기 전용 에이전트다. 플러그인이 없고 war-room 폴더만 있으면(다른 도구로 설치) `general-purpose`로 되돌리고 그렇다고 알린다.
  - 등급별 model은 Agent 호출의 `model`로 넘긴다: 중은 `haiku`, 상은 롤 파일의 `model`(없으면 `sonnet`).
- 검증 에이전트에게 주는 것: 요구 기준, 확인 방법, 바뀐 파일 목록. 구현 에이전트의 "잘 됐다"는 설명은 주지 않는다. 결과물만 보고 판정하게 한다.
- 검증 에이전트는 코드를 고치지 않는다. 판정만 한다. 기준을 읽고 넘어가지 않고 **확인 방법을 직접 실행한다.** 실행하지 않은 기준은 통과로 치지 않는다.
- 도구로 완전히 막히지 않는 부분(Bash로 파일 쓰기)은 평가 전후 스냅숏 비교가 막는다 (`evaluation.md` 7절).

검증 에이전트 프롬프트 (evaluator 꺼짐·없음일 때):

```
너는 검증 담당이다. 코드를 고치지 말고 판정만 한다. 판정용 읽기 스킬만 쓰고, 작업 폴더 밖에는 아무것도 쓰지 않는다.
```

## 3. 실패 뒤 다시 맡기기

다음 시도는 **같은 에이전트에게 "다시 해"라고 하지 않는다.** 실패 원인에 따라 고른다.

| 실패 원인 | 다음 시도 |
|---|---|
| 일부 기준만 못 맞춤, 접근은 맞음 | 같은 롤의 **새 에이전트**에게 현재 결과 + 검증 보고(판정 근거)를 주고 고치게 한다 |
| 접근 자체가 틀림 | 같은 롤의 새 에이전트에게 **다른 접근**을 지시한다. 지난 시도에서 무엇을 해 봤고 왜 안 됐는지 적는다 |
| 롤이 맞지 않았음 (범위 밖 지식 필요) | 맞는 다른 롤에 맡긴다. 없으면 매니저가 직접 하거나 롤 추가를 제안한다 |
| 요구가 모호해 판정이 갈림 | 시도하지 말고 사용자에게 기준을 다시 묻는다 |

- `## 지난 시도`에 넣는 것은 평가·검증 에이전트가 찾은 실패 내용(실패 기준·갈래, 근거)뿐이다. 구현 에이전트의 설명·자기 평가는 넣지 않는다. 매니저가 덧붙이는 것은 `이번에 바꿀 것` 한 줄이다 (`delegation.md` 3절).
- 판정 1번이 실패면 실패 1번으로 센다.
- 다른 접근으로 다시 할 때는 Agent를 `isolation: "worktree"`로 띄워 지금까지 가장 좋은 결과를 지킨다. 통과한 쪽만 작업 폴더에 반영한다.
- 시도할 때마다 `STATUS.md` 진행 중에 `시도 n/최대 · 남은 실패 기준`을 적는다.
- 시도마다 기준별 통과 수를 기록해 두고, 가장 많이 통과한 시도를 "최고 결과"로 둔다.
  - 예외: evaluator 켜짐이면 통과 수 대신 **다섯 갈래의 ✗ 개수**를 기록하고, ✗가 가장 적은 시도를 최고 결과로 둔다. 같으면 ✓가 많은 시도, 그것도 같으면 나중 시도. 갈래 전체를 한 번에 세므로 기준 수가 시도마다 달라도 비교할 수 있기 때문이다. `STATUS.md`에는 `남은 ✗ n개(갈래)`로 적는다.

### 2번 실패하면: 기준·설계 다시 보기

같은 일이 **2번 실패하면** 3번째를 맡기기 전에 매니저가 기준과 설계를 다시 본다. 다음 셋을 확인한다.
- 두 실패의 원인이 같은 기준·같은 갈래인가
- 기준끼리 부딪히는가
- 기준이 모호해 판정이 갈렸는가

결과는 둘 중 하나다.
- 기준·설계 문제로 보인다 → 재시도하지 않고 사용자에게 묻는다. 무엇이 왜 막혔는지와 고칠 안 2개를 낸다.
- 실행 문제(구현 실수)로 보인다 → 3번째를 맡기고 이유를 한 줄 알린다.

끝까지 모드에서도 이 다시 보기는 한다. 다만 묻지 않고 접근을 바꾼다. 예외: 다시 보기 결과가 "기준끼리 부딪힘"이나 "기준이 모호함"이면 사용자만 정할 수 있는 것이므로 묻는다. 근거는 구현을 아무리 바꿔도 기준이 풀리지 않기 때문이다.

## 4. 멈출 때를 판단한다

아래 중 하나면 더 시키지 않고 멈춘다.

- 시도 횟수가 `maxAttempts`에 닿았다.
- 두 번 연속 통과한 기준 수가 늘지 않았다 (나아지지 않는 반복). 예외: evaluator 켜짐이면 ✗ 개수가 줄지 않은 것을 뜻한다.
- 실패 원인이 시도로 풀 수 없는 것이다: 라이브러리·플랫폼의 한계, 없는 API·권한, 서로 부딪히는 기준.
- 한 시도가 예상보다 훨씬 오래 걸리고 끝이 보이지 않는다. 이때는 진행 상황을 알리고 계속할지 사용자에게 묻는다.

### 끝까지 모드

정해진 문구를 맞추지 않고 **뜻으로 판단한다.** "시간·횟수가 얼마나 들든 결과를 내라"는 뜻이면 끝까지 모드다. 이때는 위 멈춤 조건을 쓰지 않고 결과가 나올 때까지 반복한다.

- 해당하는 예 (이것만이 아니다)
  - "될 때까지", "무조건 완성해", "끝까지 해", "포기하지 마"
  - "몇 번이 걸리든", "시간 걸려도 괜찮아", "완성될 때까지 돌려"
  - "안 되면 될 때까지 다시", "결과 나올 때까지 멈추지 마"
- 해당하지 않는 예: "꼭 해줘", "잘 해줘", "급해". 강조이거나 일정에 대한 말이고, 횟수 제한을 풀라는 뜻은 아니다.
- 애매하면 기본 규칙으로 한다. 멈출 때 내는 대안에 "끝까지 계속 시도"를 하나로 넣어, 사용자가 고를 수 있게 한다.
- 끝까지 모드로 판단했으면 시작할 때 알린다. 예: `→ 끝까지 모드: 통과할 때까지 반복합니다`

- `maxAttempts`를 무시한다. 시도 횟수 제한이 없다.
- 오래 걸려도 계속할지 묻지 않는다.
- 나아지지 않는 반복이나 한계에 부딪히면, 멈추는 대신 **접근을 바꾼다**. 같은 접근을 그대로 되풀이하지 않는다.
  - 다른 구현 방식, 다른 라이브러리, 다른 롤, 문제를 더 작게 나누기
  - 해 본 접근은 `STATUS.md` 진행 중에 목록으로 남겨 같은 길로 돌아가지 않는다
- 사용자만 줄 수 있는 것(권한, 비밀값, 서로 부딪히는 기준 중 무엇을 고를지, 모호한 기준의 뜻)이 필요할 때만 묻는다. 2번 실패 뒤 다시 보기(3절)는 끝까지 모드에서도 한다. 답을 받으면 바로 이어서 반복한다.
- 시도 3번마다 한 줄로 진행 상황을 알린다: `시도 n · 통과 기준 j/m · 지금 접근`. evaluator 켜짐이면 `시도 n · 남은 ✗ k개 · 지금 접근`. 알리기만 하고 멈추지 않는다.
- 사용자가 멈추라고 하거나 기준을 바꾸면 그 지시를 따른다.
- 이 지시는 그 일에만 적용한다. 다음 일은 다시 기본 규칙으로 한다.

## 5. 못 미칠 때 보고 (대안 필수)

통과 못 했는데 "거의 됐다"고 포장하지 않는다. 아래를 모두 적는다.

```
요구 수준을 맞추지 못했어요. (시도 n번)

- 최고 결과: 시도 k — 기준 m개 중 j개 통과 (evaluator 켜짐이면 ✗ n개, 갈래별 판정). 현재 작업 폴더에 반영됨 | worktree <경로>에 있음
- 못 맞춘 기준: <기준> — 이유: <검증 근거로 확인한 원인>
- 더 시도해도 안 될 거라고 보는 이유: <같은 원인 반복 / 한계 근거>

대안
1. (추천) <기준을 이렇게 낮추면 지금 결과로 충족>
2. <다른 방식: 무엇을 바꾸면 되는지, 드는 비용>
3. <사용자가 정해야 할 것 / 필요한 자원>
```

- 대안은 최소 2개, 그중 하나를 추천한다. 대안마다 무엇을 포기하거나 더 들이는지 적는다.
- 사용자가 대안을 고르면 그것을 `DECISIONS.md`에 적고, 정해진 기준으로 다시 반복을 시작한다.
- 같은 이유로 막힌 일은 `LESSONS.md`에 적는다.

## 6. 통과 뒤

- evaluator 켜짐이고 ⚠ 항목이 있으면 사용자에게 보여주고 받아들일지 묻는다. 안 받아들이면 그 항목을 ✗로 보고 다시 맡긴다 (시도 횟수는 이어서 센다). 확정한 수치 한계값은 `DECISIONS.md`에 적는다.
- 상 등급이 통과하면 미리 써 둔 DECISIONS 항목 제목 끝의 `(검증 대기)`를 뗀다 (매니저가 한다). 실패해 결정이 바뀌면 그 항목을 지우고 새로 쓴다.
- 일이 끝나면(통과 확정 또는 멈춤) 그 롤의 `war-room/.eval/<롤 id>.json`을 지운다. 평가 에이전트가 돌아올 때마다 `running`·`planning`이 남아 있으면 `aborted`로 고친다 (`evaluation.md` 5절).
- 주관 기준이 있으면 사용자에게 보여주고 확인받는다. 사용자가 모자라다고 하면 그 말을 기준에 넣어 다시 반복한다 (시도 횟수는 이어서 센다).
- 통과까지 여러 번 걸렸으면 무엇이 막혔는지 `LESSONS.md`에 적는다.
