# 맡기기 → 검증 → 다시 맡기기

맡긴 일은 요구 수준에 맞을 때까지 시키고, 검증하고, 반복한다. 다만 끝없이 돌리지 않는다. 해 본 것 중 가장 좋은 결과도 수준에 못 미치면 **안 된다고 말하고 대안을 낸다.**

```
수준 정하기 → (평가 계획) → 맡기기(시도 n) → 검증 ─ 통과 → (주관 기준은 사용자 확인) → 끝
                  ↑                └ 실패 → 계속할지 판단 ─ 계속 → 다음 시도
                  └────────────────────────────────────────┘     └ 멈춤 → 못 미침 보고 + 대안
```

평가 계획은 evaluator 롤이 켜져 있을 때만 있다. 켜짐·꺼짐·없음(기존 설치)은 `evaluation.md` 0절을 따른다. 아래 "평가 롤"은 evaluator 롤이다.

## 1. 요구 수준 정하기 (맡기기 전에)

- **사용자가 수준을 말했으면** 그대로 쓴다. 측정할 수 있게만 다듬는다.
- **말하지 않았으면** 매니저가 기준 초안을 만든다.
  - 재료: 롤의 `완료 기준`, 요청 내용, 관련 `DECISIONS.md` 항목
  - 작은 일(한두 파일, 정답이 분명한 일)은 초안대로 바로 진행하고 알리기만 한다.
  - 그 밖의 일은 시작 전에 사용자에게 기준을 보여주고 확인받는다 (AskUserQuestion).
- 기준마다 **확인 방법**을 붙이고, 확인할 수 없는 기준은 쓰지 않는다.
  - 객관 기준: 명령·측정으로 판정한다. 예: `pnpm test` 통과, 응답 200ms 이하, 콘솔 에러 0
  - 주관 기준: 사람이 봐야 한다. 예: 디자인, 문구 톤, 사용감. 검증 통과 뒤 사용자에게 확인받는다고 표시한다
- `config.json`의 `maxAttempts`(기본 3)를 시도 횟수 상한으로 쓴다. 사용자가 이번 일에 따로 정했으면 그 값을 쓴다.
- **평가 계획 (evaluator 켜짐일 때)**: 기준을 정한 뒤 맡기기 전에 평가 롤을 한 번 띄워 평가 항목 초안과 변경 전 수치를 만든다 (`evaluation.md` 1절 ①). 사용자가 정할 것(한계값 미정, 결정끼리 충돌)이 있을 때만 확인받는다. 답만 하는 질문과 문서 상태 갱신만 하는 일은 건너뛴다. 2번째 시도부터는 같은 계획을 쓴다.

## 2. 검증

- **구현한 에이전트가 자기 결과를 검증하지 않는다.**
  - **evaluator 켜짐**: 평가 롤이 평가 계획대로 다섯 갈래(기준·히스토리·부작용·개념·수치)를 판정한다. 절차·프롬프트·보고 형식·종합 판정은 `evaluation.md`를 따르고, 아래 검증 에이전트 프롬프트와 "매니저가 직접 검증" 예외는 쓰지 않는다. 평가 에이전트에게도 구현 에이전트의 "잘 됐다" 설명은 주지 않는다. 사용자가 만든 QA 롤이 있어도 평가는 평가 롤이 맡고, QA 롤의 완료 기준은 기준 갈래에 더한다.
  - **evaluator 꺼짐·없음**: 지금 방식으로 한다. 켜진 롤 중 검증·QA를 맡는 롤이 있으면 그 롤에 맡기고, 없으면 새 서브에이전트(`general-purpose`)를 검증 전용으로 띄운다.
- 검증 에이전트에게 주는 것: 요구 기준, 확인 방법, 바뀐 파일 목록. 구현 에이전트의 "잘 됐다"는 설명은 주지 않는다. 결과물만 보고 판정하게 한다.
- 검증 에이전트는 코드를 고치지 않는다. 판정만 한다.
- 아주 작은 일(한 파일 몇 줄)은 매니저가 직접 명령을 돌려 검증해도 된다.

검증 에이전트 프롬프트 (evaluator 꺼짐·없음일 때):

```
너는 검증 담당이다. 코드를 고치지 말고 판정만 한다.

## 요구 기준
1. <기준> — 확인 방법: <명령·측정·관찰>
2. ...

## 대상
- 바뀐 파일: <목록>
- 프로젝트 루트: <경로>

## 보고 형식
- 판정: 통과 | 실패
- 기준별: 번호 · 통과/실패 · 근거(돌린 명령과 출력, 본 위치)
- 실패 원인 추정: 무엇이 왜 모자란가
- 주관 기준: 사람이 확인할 것 (스샷·경로 등 볼 수 있게)
```

## 3. 실패 뒤 다시 맡기기

다음 시도는 **같은 에이전트에게 "다시 해"라고 하지 않는다.** 실패 원인에 따라 고른다.

| 실패 원인 | 다음 시도 |
|---|---|
| 일부 기준만 못 맞춤, 접근은 맞음 | 같은 롤의 **새 에이전트**에게 현재 결과 + 검증 보고를 주고 고치게 한다 |
| 접근 자체가 틀림 | 같은 롤의 새 에이전트에게 **다른 접근**을 지시한다. 지난 시도에서 무엇을 해 봤고 왜 안 됐는지 적는다 |
| 롤이 맞지 않았음 (범위 밖 지식 필요) | 맞는 다른 롤에 맡긴다. 없으면 매니저가 직접 하거나 롤 추가를 제안한다 |
| 요구가 모호해 판정이 갈림 | 시도하지 말고 사용자에게 기준을 다시 묻는다 |

- 다른 접근으로 다시 할 때는 Agent를 `isolation: "worktree"`로 띄워 지금까지 가장 좋은 결과를 지킨다. 통과한 쪽만 작업 폴더에 반영한다.
- 시도할 때마다 `STATUS.md` 진행 중에 `시도 n/최대 · 남은 실패 기준`을 적는다.
- 시도마다 기준별 통과 수를 기록해 두고, 가장 많이 통과한 시도를 "최고 결과"로 둔다.
  - 예외: evaluator 켜짐이면 통과 수 대신 **다섯 갈래의 ✗ 개수**를 기록하고, ✗가 가장 적은 시도를 최고 결과로 둔다. 같으면 ✓가 많은 시도, 그것도 같으면 나중 시도. 갈래 전체를 한 번에 세므로 기준 수가 시도마다 달라도 비교할 수 있기 때문이다. `STATUS.md`에는 `남은 ✗ n개(갈래)`로 적는다.

## 4. 멈출 때를 판단한다

아래 중 하나면 더 시키지 않고 멈춘다.

- 시도 횟수가 `maxAttempts`에 닿았다.
- 두 번 연속 통과한 기준 수가 늘지 않았다 (나아지지 않는 반복). 예외: evaluator 켜짐이면 ✗ 개수가 줄지 않은 것을 뜻한다.
- 실패 원인이 시도로 풀 수 없는 것이다: 라이브러리·플랫폼의 한계, 없는 API·권한, 서로 부딪히는 기준.
- 한 시도가 예상보다 훨씬 오래 걸리고 끝이 보이지 않는다. 이때는 진행 상황을 알리고 계속할지 사용자에게 묻는다.

### 끝까지 모드

정해진 문구를 맞추지 않고 **뜻으로 판단한다.** "시간·횟수가 얼마나 들든 결과를 내라"는 뜻이면 끝까지 모드다. 이때는 위 멈춤 조건을 쓰지 않고 결과가 나올 때까지 반복한다.

- 해당하는 예 (이것만이 아니다)
  - "될 때까지", "무조건 완성해", "끝까지 해", "포기하지 마"
  - "몇 번이 걸리든", "시간 걸려도 괜찮아", "완성될 때까지 돌려"
  - "안 되면 될 때까지 다시", "결과 나올 때까지 멈추지 마"
- 해당하지 않는 예: "꼭 해줘", "잘 해줘", "급해". 강조이거나 일정에 대한 말이고, 횟수 제한을 풀라는 뜻은 아니다.
- 애매하면 기본 규칙으로 한다. 멈출 때 내는 대안에 "끝까지 계속 시도"를 하나로 넣어, 사용자가 고를 수 있게 한다.
- 끝까지 모드로 판단했으면 시작할 때 알린다. 예: `→ 끝까지 모드: 통과할 때까지 반복합니다`

- `maxAttempts`를 무시한다. 시도 횟수 제한이 없다.
- 오래 걸려도 계속할지 묻지 않는다.
- 나아지지 않는 반복이나 한계에 부딪히면, 멈추는 대신 **접근을 바꾼다**. 같은 접근을 그대로 되풀이하지 않는다.
  - 다른 구현 방식, 다른 라이브러리, 다른 롤, 문제를 더 작게 나누기
  - 해 본 접근은 `STATUS.md` 진행 중에 목록으로 남겨 같은 길로 돌아가지 않는다
- 사용자만 줄 수 있는 것(권한, 비밀값, 서로 부딪히는 기준 중 무엇을 고를지)이 필요할 때만 묻는다. 답을 받으면 바로 이어서 반복한다.
- 시도 3번마다 한 줄로 진행 상황을 알린다: `시도 n · 통과 기준 j/m · 지금 접근`. evaluator 켜짐이면 `시도 n · 남은 ✗ k개 · 지금 접근`. 알리기만 하고 멈추지 않는다.
- 사용자가 멈추라고 하거나 기준을 바꾸면 그 지시를 따른다.
- 이 지시는 그 일에만 적용한다. 다음 일은 다시 기본 규칙으로 한다.

## 5. 못 미칠 때 보고 (대안 필수)

통과 못 했는데 "거의 됐다"고 포장하지 않는다. 아래를 모두 적는다.

```
요구 수준을 맞추지 못했어요. (시도 n번)

- 최고 결과: 시도 k — 기준 m개 중 j개 통과 (evaluator 켜짐이면 ✗ n개, 갈래별 판정). 현재 작업 폴더에 반영됨 | worktree <경로>에 있음
- 못 맞춘 기준: <기준> — 이유: <검증 근거로 확인한 원인>
- 더 시도해도 안 될 거라고 보는 이유: <같은 원인 반복 / 한계 근거>

대안
1. (추천) <기준을 이렇게 낮추면 지금 결과로 충족>
2. <다른 방식: 무엇을 바꾸면 되는지, 드는 비용>
3. <사용자가 정해야 할 것 / 필요한 자원>
```

- 대안은 최소 2개, 그중 하나를 추천한다. 대안마다 무엇을 포기하거나 더 들이는지 적는다.
- 사용자가 대안을 고르면 그것을 `DECISIONS.md`에 적고, 정해진 기준으로 다시 반복을 시작한다.
- 같은 이유로 막힌 일은 `LESSONS.md`에 적는다.

## 6. 통과 뒤

- evaluator 켜짐이고 ⚠ 항목이 있으면 사용자에게 보여주고 받아들일지 묻는다. 안 받아들이면 그 항목을 ✗로 보고 다시 맡긴다 (시도 횟수는 이어서 센다). 확정한 수치 한계값은 `DECISIONS.md`에 적는다.
- 일이 끝나면(통과 확정 또는 멈춤) 그 롤의 `war-room/.eval/<롤 id>.json`을 지운다. 평가 에이전트가 돌아올 때마다 `running`·`planning`이 남아 있으면 `aborted`로 고친다 (`evaluation.md` 5절).
- 주관 기준이 있으면 사용자에게 보여주고 확인받는다. 사용자가 모자라다고 하면 그 말을 기준에 넣어 다시 반복한다 (시도 횟수는 이어서 센다).
- 통과까지 여러 번 걸렸으면 무엇이 막혔는지 `LESSONS.md`에 적는다.
