# 중·상 검증 (공통)

맡긴 일은 요구 수준에 맞을 때까지 시키고 검증하고 반복하되 끝없이 돌리지 않는다 (`retry.md`). 상은 `verify-high.md`를 더 읽는다.

## 1. 기준 쓰는 법 (맡기기 전)

- 사용자가 말한 수준은 측정할 수 있게만 다듬어 쓴다. 없으면 매니저가 초안을 만들고(재료: 롤의 `완료 기준`, 요청, `DECISIONS.md`) 알리고 진행한다 (`judgment.md` 2절). 기준이 되돌리기 어려운 결정(`judgment.md` 1절)을 담으면 묻는다.
- 기준마다 확인 방법을 붙이고, 확인할 수 없는 기준은 쓰지 않는다. 가능하면 `명령 → 기대 결과`로 쓴다.
  - 객관: 명령·측정으로 판정한다. 예: `pnpm test` → 실패 0건
  - 주관: 사람이 봐야 한다 (디자인, 문구 톤). 통과 뒤 사용자 확인이라고 표시한다
- 평가 롤이 켜져 있으면 그 `완료 기준`만 더한다.
- 중은 성능·크기 확인이 필요하면 측정 명령과 한계값을 기준 하나로 넣는다. 사용자가 정할 것(한계값 미정, 결정 충돌)이 있을 때만 맡기기 전에 묻는다.
- **기준선**: 구현을 맡기기 전에 매니저가 전체 테스트를 돌려 원래 실패하던 목록을 남기고 위임 `## 기준선`과 검증 프롬프트에 넣는다. 구현 뒤에 뜬 목록은 쓰지 않는다. 중은 이 목록에 없던 새 실패를 확인하는 데 쓴다. 명령은 `time`으로 재서 2분 이상 걸린 것에 표시한다 (3절). 2번째 시도부터 같은 기준선이다.

## 2. 누가 판정하나

- **자기 검토 금지: 구현한 에이전트와 매니저는 자기 결과를 판정하지 않는다.** 예외는 판단이 아니라 명령 결과 비교나 자기 기록 점검인 것뿐이다: 하 등급 기계 검사, 중 명령 판정, 정형 릴리즈 확인(`verify-high.md` 7절), 이어받기 점검.
- **중 명령 판정**: 요구 기준이 전부 `명령 → 기대 결과`이고 기대 결과가 판단 없이 비교되면(출력 없음, 숫자, 종료 코드, 고정 문자열) 매니저가 명령을 돌려 판정한다. 에이전트·스냅숏은 없다. 이어서 `git diff`로 범위와 등급 올림 신호(검증 신호·무조건 상)를 본다. 결정 점검은 STATUS `점검할 결정`에 남기고 보고에 적어 사용자가 보는 것으로 대신한다.
- **중 에이전트 판정**: 기준 하나라도 읽고 판단하는 것이면 `armory:evaluator`(model `haiku`) 한 번이 모든 기준을 판정한다 (평가 롤 켜짐·꺼짐 무관). 에이전트를 피하려고 판단 기준을 명령으로 억지로 바꾸지 않는다. 요청의 핵심이 읽어 봐야 아는 것(규칙의 뜻, 문장, 설계)이면 판단 기준이다. 스킬·롤 문서의 규칙 뜻이 바뀌는 일은 판단 기준이 반드시 하나다.
- 검증·기준 검토 에이전트는 사용 가능한 종류에 있으면 읽기 전용 `armory:evaluator`다. 없을 때만 `general-purpose`로 되돌리고 알린다.
- 에이전트에게는 요구 기준, 확인 방법, 바뀐 파일만 준다 (구현 에이전트의 "잘 됐다" 설명은 주지 않는다). 확인 방법을 직접 실행하지 않은 기준은 통과가 아니다 (예외는 3절).
- 띄우기 직전·직후 스냅숏을 비교한다 (4절).

## 3. 오래 걸리는 명령 (중 에이전트·상 공통)

- **대상**: (1) 프로젝트별 규칙(`roles/manager.md`·`roles/evaluator.md`의 `# 프로젝트별 규칙`)이 지정한 명령(e2e, 전체 빌드 등), (2) 기준선을 잴 때 `time`으로 2분 이상 걸린 명령. 규칙이 먼저다. 그 밖의 명령은 검증 쪽이 직접 돌린다.
- **매니저가 돌린다**: 구현이 돌아오면 그 명령을 직접 한 번 돌린다. 구현 롤의 보고 출력은 쓰지 않는다. 시도마다 새로 돌려 다시 쓴다.
- **기록**: `war-room/.eval/<롤 id>.long-run.txt`에 명령마다 `명령 · 종료 코드 · 출력 끝부분 · 작업 상태 해시`를 남긴다. 해시는 명령이 끝난 직후 아래 명령으로 계산한다. 커밋하지 않는다.
- **다시 돌리지 않는 때**: 해시를 다시 계산해 기록과 같고 기록의 종료 코드·출력이 기준에 맞을 때다. 아니면 직접 돌린다. 매니저는 보고의 `재실행 생략` 줄을 한 번 읽는다.
- **항상 직접 돌리는 일**: 정형이 아닌 릴리즈·배포·push, 보안·권한, 파일·데이터 삭제·마이그레이션이 든 일은 기록 없이 검증 에이전트가 직접 돌린다.
- **해시 명령** (`war-room/` 문서는 빼고 변경·스테이징·추적 안 되는 파일을 합친다. 어느 폴더에서나 같다):

```bash
( cd "$(git rev-parse --show-toplevel)" && { git status --porcelain -- . ':(top,exclude)war-room'; git diff -- . ':(top,exclude)war-room'; git diff --cached -- . ':(top,exclude)war-room'; git ls-files --others --exclude-standard -- . ':(top,exclude)war-room' | while IFS= read -r f; do shasum -- "$f"; done; } | shasum )
```

## 4. 읽기 전용 확인: 평가 전후 스냅숏

평가·검증 에이전트를 띄울 때마다 한다 (하·중 명령 판정은 에이전트가 없어 없다). 에이전트는 Bash로 파일을 쓸 수 있으므로 띄우기 직전에 스냅숏을 남기고 돌아오면 비교한다.

```bash
cd "$(git rev-parse --show-toplevel)" && mkdir -p war-room/.eval
snap() {
  git status --porcelain | grep -v ' war-room/\.eval/'
  git diff | shasum
  git diff --cached | shasum
  git ls-files --others --exclude-standard | grep -v '^war-room/\.eval/' | while IFS= read -r f; do shasum -- "$f"; done
}
snap > war-room/.eval/<롤 id>.snapshot      # 평가 직전
snap | diff - war-room/.eval/<롤 id>.snapshot  # 직후, 출력 없어야 함
```

- `.eval/`은 비교에서 빼고, 무시 파일(`--ignored`)은 부산물로 거짓 무효가 나서 넣지 않는다.
- 하나라도 다르면 그 판정은 무효다. 알리고 되돌릴지 정한 뒤 다시 띄운다.
- 순서: 구현 → STATUS `진행 중` 줄 → 스냅숏 → 판정 → 스냅숏 비교 → (통과하면) 문서 갱신. 문서 변경이 판정 중 변경으로 잡히지 않게 비교를 문서 갱신보다 앞에 한다.
- 병렬이면 모든 구현이 돌아온 뒤 한 번에 뜬다. 작업 세션이면 그 워크트리에서 뜬다 (`multi-session.md`). 무시 경로·저장소 밖 쓰기는 못 잡아 프롬프트 규칙에 맡기고, 별도 worktree 평가는 쓰지 않는다.

## 5. 통과 뒤

- 스냅숏 비교가 같은지 본 뒤 STATUS·DECISIONS·LESSONS(여러 번 걸렸으면 막힌 것)를 갱신하고 이어받기 점검을 하고, 요청이 있으면 구현과 문서를 한 커밋으로 묶는다 (`state-docs.md` 5절).
- 일이 끝나면(통과 확정 또는 멈춤) 그 롤의 `.eval/<롤 id>.json`·`.snapshot`·`.long-run.txt`를 지운다 (`verify-high.md` 6절).
- 주관 기준은 사용자에게 보여주고 확인받는다. 모자라다고 하면 그 말을 기준에 넣어 반복한다 (시도 횟수는 이어서 센다).
