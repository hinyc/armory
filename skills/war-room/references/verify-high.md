# 상 등급 검증 (verify.md에 더해 읽는다)

기준 검토 → 구현 → 독립 평가 순서이고 구현 쪽 말은 근거가 아니다. 정형 릴리즈(7절)는 기준 검토·평가를 생략한다.

## 1. 흐름

```
배정 → 기준 검토 → 매니저: 기준선·변경 전 수치·한계값·볼 갈래 (정할 것은 확인)
  → ② 담당 롤 작업(시도 n, 커밋 없음) → 오래 걸리는 명령 기록(verify.md 3절)
  → STATUS 진행 중 줄 → 스냅숏(verify.md 4절) → ③ 평가 → 스냅숏 비교
     ├ 통과 → ⚠ 있으면 사용자 확인 → 문서 갱신 → 이어받기 점검 → 커밋(요청 시)
     └ 실패 → retry.md → ②
```

- 평가 에이전트는 구현 뒤 시도마다 새로 한 번(③)만 띄운다 (계획 ①은 없다). 읽기 전용 `subagent_type: armory:evaluator`, `description: evaluator: <작업 요약>`, model은 롤 파일 `model`(기본 `sonnet`. 비용은 롤 파일 값만 내려 줄인다). 에이전트 수는 기준 검토 1 + 시도마다 ③ 1이다.
- 평가 롤이 켜진 경우의 흐름이다. 꺼짐·없음, QA 롤, 병렬은 `eval-edge.md`.
- 매니저가 직접 처리한 일도 같은 흐름이다. 예외: 답만 하는 질문과 문서 상태 갱신만 하는 일은 바뀌는 코드·동작이 없어 평가하지 않는다. 한 파일 몇 줄이어도 평가한다. 2번째 시도부터 같은 기준선·볼 갈래로 ③만 새로 띄운다.
- STATUS `진행 중` 줄만 시도마다 스냅숏 전에 고친다 (`state-docs.md` 5절).
- 뒤집는 결정은 ③ 프롬프트의 `이번 일이 뒤집는 결정` 줄에 적는다 (히스토리 ✗로 세지 않고 결정 점검에서 본다). 뒤집는 DECISIONS 항목은 통과 뒤에 쓴다.

## 2. 기준 검토 (맡기기 전, 새 에이전트 한 번)

기준이 틀리거나 빠지면 구현과 검증이 둘 다 통과하므로 상은 맡기기 전에 기준을 따로 검토한다 (중 이하는 하지 않는다).

- 평가 롤·QA 롤과 무관하게 `armory:evaluator`(model `haiku`)로 띄우고 진행 파일은 쓰지 않는다 (플러그인이 없을 때만 `general-purpose`, 알린다). 받아들인 추가 기준의 변경 전 값은 매니저가 명령으로 잰다.
- 묻는 것: "빠진 경우(예외, 경계값, 다른 롤 영향, 실패 경로)가 무엇인가". 매니저는 `## 읽을 것`에 파일을 5개 이내로 지정한다.

- `기준에 빠진 것`은 하나씩 셋 중 하나로 처리한다. 받아들임·거절은 매니저가 정하는 결정이라 `정한 것:`·`점검할 결정` 대상이다.
  - 받아들임: 요청 범위 안이고 확인 방법을 붙일 수 있으면 기준에 넣는다.
  - 보류: 범위를 넓히거나 사용자만 정할 수 있는 것이면 묻는다 (`judgment.md` 1절 7·8번). 답이 올 때까지 맡기지 않고, 나중에 정하겠다고 하면 `## 알려진 예외`에 "미정"으로 적고 맡긴다.
  - 거절: 범위 밖이거나 확인할 수 없는 것은 한 줄 이유와 보고에 적고 넘어간다.

## 3. 볼 갈래와 수치 준비 (매니저, 맡기기 전)

- ③은 기준·히스토리·부작용을 항상 보고, 개념은 conceptpowers가 켜져 있을 때, 수치는 수치 기준이 있을 때만 본다. 매니저가 `## 볼 갈래`에 갈래와 이유를 적고 뺀 갈래는 `na`(해당 없음: 이유)로 적는다.
- 수치: 이번 변경과 관계있는 것(응답·빌드 시간, 번들·파일 크기, 메모리, 특정 출력값 등)만 골라 위임 `## 요구 기준`에 넣고, 변경 전 값은 매니저가 명령으로 재서 위임과 ③의 `## 기준선`에 넣는다.
- **한계값 출처 순서**: (1) 사용자가 말한 값 → (2) 롤 문서나 `DECISIONS.md`에 적힌 값 → (3) 둘 다 없으면 매니저가 초안(변경 전 값에 여유를 둔 값)을 내고 맡기기 전에 사용자에게 묻는다. 앞 출처가 있으면 뒤는 보지 않는다. 확정한 값은 `DECISIONS.md`에 적어 다음 평가가 (2)로 쓴다.
- 위임 프롬프트에도 한계값과 기준선을 넣어 구현이 평가 항목을 알고 시작하게 한다.

## 5. 판정 뒤 처리

- ✗가 하나라도 있으면 실패다. `retry.md` 표대로 다시 맡기고 실패 원인 칸에 갈래를 적는다 (예: "히스토리: DECISIONS 2026-11-05 위반").
- ✗ 없고 ⚠만 있으면 통과다. 보고 뒤 사용자에게 ⚠ 항목을 보여주고 받아들일지 묻는다. 안 받으면 ✗로 보고 다시 맡긴다 (시도 횟수는 이어서 센다). 확정한 수치 한계값은 `DECISIONS.md`에 적는다.
- 진척 수·최고 결과는 다섯 갈래 전체의 ✗ 개수로 센다 (`retry.md`).
- 통과하면 스냅숏 비교를 확인한 뒤 `verify.md` 5절대로 갱신한다. `재실행 생략` 줄은 매니저가 한 번 읽는다.

## 6. 진행 파일 정리

- 평가 에이전트가 돌아올 때마다(정상·오류·중단 모두) 그 롤의 `war-room/.eval/<롤 id>.json`의 `state`가 아직 `running`(예전 파일이면 `planning`도)이면 `aborted`로 고친다. 일이 끝나면 진행 파일·스냅숏·오래 걸리는 명령 기록을 지운다 (`verify.md` 5절).

## 7. 정형 릴리즈 (기준 검토·평가 생략)

등급은 상 그대로이고 사용자 승인도 그대로 필요하다. 조건 셋이 모두 맞을 때만 쓴다.

1. 릴리즈에 들어갈 변경이 각자 검증을 통과했고, 사용자 요청으로 매니저가 이미 커밋했다.
2. 이번 작업은 버전 올림·릴리즈 노트·커밋·push·태그·릴리즈뿐이다.
3. 마이그레이션·보안·권한 변경이 없다.

절차: 사용자 승인 → 매니저가 STATUS에 "릴리즈 진행"을 적고 파일이 실제로 바뀌었는지 `git status --porcelain -- ':(top)war-room/STATUS.md'`로 확인 → 릴리즈 담당 롤 에이전트 하나가 버전 올림부터 릴리즈까지 한다 (커밋에 문서 변경도 넣는다. `state-docs.md` 5절) → 매니저가 아래 명령으로 확인한다. 기준 검토·평가는 없다. 릴리즈 노트는 보고에 붙인다.

매니저 확인 명령 (저장소 루트에서 돌린다. git 명령은 하위 폴더에서도 같다. 어긋나면 STATUS를 실제 결과로 고치고 알린다):
- 매니페스트 버전 일치: 매니페스트마다 `grep -n '"version"'`로 읽어 모두 태그 버전과 같다
- 프로젝트 검사 명령·전체 테스트가 기준선과 같다
- 원격 브랜치 = HEAD: `git rev-parse HEAD`와 `git ls-remote origin refs/heads/<브랜치>`의 해시가 같다
- 원격 태그 해시 = HEAD: `git ls-remote origin 'refs/tags/<태그>*'`의 해시(주석 태그는 `^{}` 줄)가 같다
- 릴리즈가 draft가 아님: `gh release view <태그> --json isDraft,url` → `isDraft`가 false
- 커밋 작성자·커미터: `git log -1 --format='%an <%ae> | %cn <%ce>'`가 사용자 설정과 같다
- 작업 폴더가 깨끗함: `git status --porcelain` 출력 없음

조건이 하나라도 안 맞으면 기존 상 절차(준비 → 평가 → 문서 → 승인 → 릴리즈, `state-docs.md` 5절)이고, 릴리즈·push는 검증 에이전트가 직접 돌린다.
