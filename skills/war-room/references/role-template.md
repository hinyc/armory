# 롤 파일 형식

`war-room/roles/<id>.md`. `<id>`는 kebab-case이고 파일 이름과 `name`이 같아야 한다.

```markdown
---
name: frontend
description: 화면 컴포넌트·스타일·라우팅을 맡는다
scope:
  - src/components/**
  - src/pages/**
model: sonnet
skills:
  - screen-spec
refs:
  - docs/design-system.md
---

# 역할

이 프로젝트의 화면 쪽 구현을 맡는다. (한두 줄)

# 하는 일

- 새 화면·컴포넌트 추가
- 스타일·레이아웃 수정

# 하지 않는 일

- API 응답 형식 변경 → backend 롤
- 배포 설정 → 매니저에게 넘긴다

# 일하는 방식

- 이 프로젝트에서 따를 규칙, 쓰는 명령, 주의할 점

# 완료 기준

- `pnpm test`, `pnpm lint` 통과
- 바뀐 화면을 직접 띄워 확인
```

| 필드 | 뜻 | 필수 |
|---|---|---|
| `name` | 롤 id. config의 `roles` 키와 같다 | 예 |
| `description` | 매니저가 배정할 때 보는 한 줄. 무엇을 맡는지 구체적으로 | 예 |
| `scope` | 담당 경로 glob 목록. 배정과 "범위 밖 수정" 검토에 쓴다 | 아니오 |
| `model` | `sonnet` `opus` `haiku`. 없으면 메인 세션과 같은 모델 | 아니오 |
| `skills` | 이 롤이 일할 때 쓰는 스킬 이름 | 아니오 |
| `refs` | 일하기 전에 읽을 문서 경로. 매번 다시 찾던 참고 자료를 여기에 모은다 | 아니오 |

## 잘 쓴 롤의 조건

- `description`만 읽어도 다른 롤과 겹치지 않는다. 겹치면 `하지 않는 일`로 경계를 적는다.
- 프로젝트에서 실제로 반복되는 일 단위로 나눈다. 일이 안 오는 롤은 만들지 않는다.
- 롤 개수에 제한은 없다. 프로젝트 규모(반복되는 일의 종류, 영역 수)에 맞춰 필요한 만큼 둔다. 다만 담당 경로나 일의 종류가 겹치는 롤은 합친다. 한 일이 롤 사이를 자주 오가면 너무 잘게 나눈 것이므로 합친다.
- 비밀값·토큰은 적지 않는다.
- 작업하며 알게 된 것은 바로 넣지 않는다. `LESSONS.md`에 쌓았다가 사용자 승인을 받고 해당 절에 넣는다.
