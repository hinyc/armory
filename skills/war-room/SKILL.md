# War Room (롤 에이전트 관리)

## Overview

프로젝트 루트 `war-room/`에 롤(역할)을 정의해 둔다. 일을 받으면 매니저가 담당 롤을 찾아 그 롤의 에이전트에게 맡기고, 결과를 확인하고, 현재 상황·결정·교훈 문서를 정리한다.

> **일을 받으면 스킬보다 담당 롤을 먼저 찾는다.** 담당 롤이 있으면 그 롤이 일을 시작하고, 필요한 스킬은 그 롤이 쓴다.
>
> 파일 읽기·계획·다른 스킬보다도 먼저 한다. war-room이 켜진 프로젝트에서는 armory의 `war-room-guard` mod가 이 지침("먼저 담당 롤을 찾고 배정 한 줄을 알린다")을 요청마다 시스템 프롬프트 끝의 `# war-room` 절에 넣는다. 답만 하면 되는 질문과, 롤·검증·조사·설계 등 서브에이전트로 실행 중일 때는 따르지 않는다.
> - mod는 세션 작업 폴더에서 위로 올라가며 처음 만나는 `war-room/config.json`을 쓴다. 하위 폴더에 자체 war-room이 있으면 그쪽이 먼저 잡힌다.
> - `enabled: false`나 `roles.manager: false`면 지침이 빠진다. JSON이 깨졌으면 지침은 들어가고, 스킬이 아래 config 규칙대로 오류를 알린다.

```
war-room/
├─ config.json        # 전체·롤별 on/off
├─ roles/
│  ├─ manager.md      # 기본 롤. 배정·검토·문서 정리
│  ├─ evaluator.md    # 기본 롤. 평가 계획·평가 실행 (끄기·삭제 가능)
│  └─ <id>.md         # 사용자가 프로젝트에 맞게 추가
├─ STATUS.md         # 현재 상황·진행 중·다음 할 일 (덮어쓰기)
├─ DECISIONS.md      # 결정 로그 (쌓임)
├─ LESSONS.md        # 시행착오·롤 문서 개선 후보 (반영하면 비움)
├─ archive/          # 넘친 완료 목록·지난 결정·처리한 교훈
└─ .eval/            # 평가 진행 파일 (커밋 안 함, 일이 끝나면 지움)
```

작업마다 로그를 남기지 않는다. 무엇이 바뀌었는지는 git 이력이 맡고, 이 폴더는 **지금 상태·결정·교훈**만 관리한다.

- 처음에는 기본 롤 `manager`와 `evaluator`만 있다. 일을 맡을 롤은 사용자가 프로젝트에 맞게 추가한다.
- 매니저는 메인 세션이 맡는다. 나머지 롤은 Agent 도구로 띄운 서브에이전트가 맡는다.
- `.claude/agents/`는 쓰지 않는다. 롤 정의는 모두 `war-room/roles/`에 둔다.

## config.json

```json
{
  "enabled": true,
  "maxAttempts": 3,
  "suggestRoles": true,
  "roles": {
    "manager": true,
    "evaluator": true,
    "frontend": true,
    "backend": false
  }
}
```

| 값 | 뜻 |
|---|---|
| `enabled` | 전체 스위치. `false`면 배정·문서 갱신 없이 평소처럼 직접 일하고, mod의 시스템 프롬프트 지침도 빠진다 |
| `maxAttempts` | 한 일에 시도할 최대 횟수 (기본 3). 사용자가 일마다 따로 정할 수 있고, "될 때까지" 같은 뜻의 지시가 있으면 무시한다 |
| `suggestRoles` | 롤 제안(새 롤·분리·기존 롤 갱신) 스위치 (기본 `true`). `false`면 신호를 쌓지도 묻지도 않는다 |
| `roles.<id>` | 롤 스위치. `false`면 배정 후보에서 뺀다. 롤 파일은 지우지 않는다 |

- on/off 값이 없으면 `true`로 본다. 롤을 추가할 때 config에 `true`로 넣는다.
- `roles/`에 파일은 있는데 config에 없는 롤은 켜진 것으로 보고, config에 `true`로 추가했다고 알린다.
- config에는 있는데 파일이 없는 롤은 배정하지 않고 경고한다.
- `manager`를 `false`로 두면 `enabled: false`와 같게 처리하고 그렇다고 알린다.
- JSON 형식이 틀리면 멈추고 어디가 틀렸는지 알린다. 추측해서 고치지 않는다.

## 설치

1. 프로젝트 루트를 확인한다 (`git rev-parse --show-toplevel`, 없으면 현재 폴더).
2. 이 스킬의 `template/`을 `<루트>/war-room/`으로 복사한다. 이미 있는 파일은 덮어쓰지 않는다.
   - `config.json`, `roles/manager.md`, `roles/evaluator.md`, `STATUS.md`, `DECISIONS.md`, `LESSONS.md`, `archive/.gitkeep`
   - 프로젝트 `.gitignore`에 `war-room/.eval/`가 없으면 한 줄 추가한다 (평가 진행 파일은 커밋하지 않는다).
3. 프로젝트 규모(반복되는 일의 종류, 영역 수)에 맞춰 필요한 만큼 롤 후보를 제안한다. 개수 제한은 없다. 겹치는 후보는 합치거나 뺀다 (`references/role-discovery.md`).
   - 이 프로젝트의 이전 세션·메모리·CLAUDE.md·git 이력이 있으면 수집 sonnet → 제안 opus 서브에이전트 순서로 읽기 전용으로 반복된 일의 사실을 모아 후보를 만든다. 메인 세션은 jsonl을 직접 읽지 않는다.
   - 중복 배제: 맡는 일이나 담당 경로가 겹치는 후보는 하나로 합친다. 합칠 수 없으면 `하지 않는 일`로 경계를 적는다. 경계를 적은 뒤에도 두 후보의 scope에 같은 경로가 남으면 근거가 약한 쪽(근거 출처 종류 수, 같으면 횟수가 적은 쪽)을 뺀다. `war-room/roles/`에 이미 있는 롤과 겹치는 후보도 뺀다.
   - 롤마다 이름, 맡을 일 한 줄, 담당 경로, 근거(출처와 횟수)를 보여준다. 원문·비밀값은 옮기지 않는다.
   - 이전 기록이 없으면 "이전 기록 없음, 구조만 보고 제안"이라 밝히고 수집은 건너뛴 채 opus가 폴더 구조·빌드 설정·README만 본다.
4. 사용자가 고른 롤만 만든다. 고르지 않으면 기본 롤(`manager`, `evaluator`)만 둔다.
5. `roles/manager.md`의 "프로젝트별 규칙"에 넣을 것(테스트 명령, 커밋 규칙)이 있는지 묻는다. 수치 측정 명령은 `roles/evaluator.md`에 적는다.

`war-room/`은 커밋해서 팀과 같이 쓰는 것을 기본으로 한다.

## 롤 관리

- **추가**
  - `references/role-template.md` 형식으로 `roles/<id>.md`를 만들고 config `roles`에 `"<id>": true`를 넣는다.
  - 사용자가 말한 것과 코드에서 확인한 것만 적는다. 명령·경로는 실제로 있는지 확인한다.
  - 기존 롤과 맡는 일이 겹치면 양쪽 `하지 않는 일`에 경계를 적는다.
- **끄기·켜기**: config 값만 바꾼다. 롤 파일은 그대로 둔다.
- **삭제**: 사용자가 삭제라고 말할 때만 파일을 지우고 config에서 뺀다. DECISIONS·archive의 지난 항목은 그대로 둔다.
- **`manager` 롤**은 지우지 않는다. 내용(프로젝트별 규칙)은 고칠 수 있다. **`evaluator` 롤**은 끄거나 지울 수 있다.

## 배정

일을 받을 때마다 아래 순서로 한다.

1. **설정 읽기**
   - `war-room/config.json`을 읽는다. `enabled: false`면 여기서 멈추고 평소처럼 일한다.
   - `roles/manager.md`를 읽는다. 매니저는 이 파일의 규칙을 따른다.
   - `STATUS.md`를 읽어 진행 중인 일과 이어지는지 본다. 관련 있으면 `DECISIONS.md`에서 해당 결정을 찾아본다.
2. **담당 찾기** (다른 일보다 먼저. 파일을 읽거나 계획을 세우거나 다른 스킬을 쓰기 전에 한다)
   - 켜진 롤 파일의 앞부분(`description`, `scope`)과 `하는 일`·`하지 않는 일`을 읽는다.
   - 요청을 그 범위와 맞춰 본다. 결과는 셋 중 하나다.
     - 롤 하나가 맡는다
     - 여러 롤에 걸친다 → 롤별로 나눈다
     - 맞는 롤이 없다 → 매니저가 직접 처리한다
   - 코드 설명·상태 조회처럼 답만 하면 되는 질문은 배정·문서 갱신 없이 바로 답한다.
3. **요구 수준 정하기**
   - 사용자가 말한 수준이 있으면 그것을, 없으면 매니저가 기준 초안을 만든다.
   - 작은 일이 아니면 시작 전에 기준을 확인받는다.
   - 기준마다 확인 방법(명령·측정, 또는 사람이 볼 것)을 붙인다.
   - evaluator 켜짐이면 기준을 정한 뒤 평가 롤이 평가 계획(항목 초안·변경 전 수치)을 만든다. 사용자가 정할 것이 있을 때만 확인받는다 (`references/evaluation.md` 1절 ①).
   - evaluator 꺼짐(`false`)이거나 롤 파일이 없으면(기존 설치. 키는 `true`·없음 모두) 평가 계획 없이 기존 검증 방식으로 하고 파일 없음은 경고한다. 파일 없음이면 처음 안 그 배정에서 한 번 "평가 롤을 추가할 수 있어요"라고 알리고(그 배정은 기존 방식으로 마친다), 승인하면 템플릿에서 복사하고 거절하면 `DECISIONS.md`에 적고 다시 묻지 않는다 (같은 문서 0절).
   - 자세한 방법은 `references/verify-loop.md` 1절.
4. **알리기**: 시작 전에 한 줄로 알린다. 예: `→ frontend 롤에 맡깁니다 (로그인 폼 수정, 기준 3개, 최대 3회)`
5. **맡기기**: Agent 도구로 롤 에이전트를 띄운다.
   - `subagent_type`: `general-purpose`
   - `model`: 롤의 `model`. 없으면 넘기지 않는다
   - `description`: `<롤 id>: <작업 요약>`
   - `prompt`: 아래 "롤 에이전트에게 주는 프롬프트"
   - 여러 롤에 나눴을 때
     - 같은 파일을 건드리지 않으면 한 메시지에서 동시에 띄운다.
     - 앞 롤의 결과가 필요하거나 같은 파일을 건드리면 순서대로 띄운다.
   - 작업이 커밋·push·릴리즈로 끝나면, 맡기기 전에 7번 문서 갱신을 먼저 한다 (7번 참고).
6. **검증 → 반복** (`references/verify-loop.md`)
   - 구현한 에이전트가 아닌 에이전트가 판정한다. evaluator 켜짐이면 평가 롤이 다섯 갈래(기준·히스토리·부작용·개념·수치)로 판정하고 (`references/evaluation.md`), 꺼짐·없음이면 검증 에이전트가 기준별로 판정한다.
   - 평가 에이전트가 돌아올 때마다 진행 파일(`.eval/<롤 id>.json`)의 `running`·`planning`을 `aborted`로 고치고, 일이 끝나면 지운다.
   - 실패하면 원인에 맞게 다음 시도를 맡긴다(같은 롤의 새 에이전트, 다른 접근, 다른 롤). 통과할 때까지 반복한다.
   - 멈출 때
     - 시도 상한에 닿았을 때
     - 두 번 연속 나아지지 않을 때
     - 시도로 풀 수 없는 한계일 때
     - 너무 오래 걸릴 때 (사용자에게 묻는다)
   - 사용자가 "될 때까지", "무조건 완성해"처럼 횟수·시간과 상관없이 결과를 내라는 뜻으로 말하면 (문구가 아니라 뜻으로 판단) 상한·멈춤 조건을 무시하고, 막히면 접근을 바꿔 결과가 나올 때까지 반복한다 (끝까지 모드).
   - 멈추면 **최고 결과로도 수준에 못 미친다고 분명히 말하고, 대안을 2개 이상 낸다.**
   - 주관 기준과 평가의 ⚠ 항목은 통과 뒤 사용자에게 확인받는다.
7. **문서 갱신** (아래 "상태 문서") (커밋·릴리즈로 끝나는 일은 5번 전에 한다)
   - `STATUS.md`를 다시 쓴다. 이번 작업에서 결정이 있었으면 `DECISIONS.md`에 추가한다.
   - 여러 번 시도했거나 못 미쳐 멈춘 일, 롤이 막혔던 일이나 다음에 알아야 할 것을 보고했으면 `LESSONS.md`에 추가한다.
   - 커밋·push·릴리즈처럼 되돌리기 어려운 단계로 끝나는 일은 이 갱신을 **롤에 맡기기 전(5번 전)에** 한다. 뒤에 고치면 커밋되지 않은 변경이 남아 "작업 폴더에 남은 변경 없음" 같은 완료 기준과 부딪힌다.
     - 매니저가 `STATUS.md`(최근 완료에 이 일을 결과 예정으로 적음)·`DECISIONS.md`·`LESSONS.md`를 미리 갱신하고, 작업 절에 커밋을 적어 롤이 그 변경을 같은 커밋에 넣게 한다.
     - 검증·평가 결과처럼 커밋 전에는 알 수 없는 내용은 적지 않는다.
     - 실패하면 `STATUS.md`를 실제 결과로 고쳐 쓴다. 이 변경은 다음 커밋에 들어간다 (실패한 일이라 완료 기준과 부딪히지 않는다).
8. **보고**: 사용자에게 결과를 알린다. 누가 했는지, 몇 번 만에 통과했는지, 무엇이 바뀌었는지, 남은 일을 적는다.

맞는 롤이 없어 직접 처리했을 때도 6·7번을 한다. 담당은 `manager`로 적는다.

### 롤 제안 (새 롤·분리·갱신) (`references/role-split.md`)

7번 때 반복 신호를 확인하고 `STATUS.md`의 `## 롤 후보`에 `[새 롤]`·`[분리 · 롤]`·`[갱신 · 롤]`로 구분해 쌓는다. 기준을 넘으면 8번 보고 **뒤에** 초안을 보여주며 한 번 묻는다. 승인 없이 롤 파일을 만들거나 고치지 않는다.

- **새 롤·분리 신호**: 자주, 길게, 참고할 것이 많음, 롤이 너무 큼.
- **기존 롤 갱신 신호**: 같은 지시 반복, 같은 맥락 반복, 범위 밖 반복, 같은 확인 반복. 성공해도 반복되면 센다.
- **고르는 순서**: 걸치는 롤 수로 갈래를 정한다 (하나면 갱신, 없으면 새 롤, 둘 이상이면 두 안 나란히). 갱신 결과가 너무 커지면 분리로 바꾼다.
- 신호 기준(수치)과 판단 규칙은 `references/role-split.md`에만 둔다.
- 같은 내용이 `LESSONS.md` 반영 후보에도 있으면 하나로 묶어 묻는다.

질문 맨 아래에는 항상 `(이 질문은 war-room/config.json의 "suggestRoles": false로 끌 수 있어요)`를 붙이고, 선택지에 "앞으로 묻지 않기"를 넣는다. 고르면 `suggestRoles`를 `false`로 바꾼다. 갱신 제안은 롤 파일의 어느 절에 무엇을 넣을지 초안을 보여준다.

"지금은 안 함"은 거절로 기록하지 않고 후보에 남긴다. 사용자가 명시적으로 원하지 않는다고 했을 때만 `DECISIONS.md`에 적고 같은 후보는 다시 묻지 않는다 (신호가 2배가 되면 한 번 더).

### 롤 에이전트에게 주는 프롬프트

서브에이전트는 이 대화를 모른다. 필요한 것을 모두 넣는다.

```
너는 이 프로젝트의 <id> 롤이다. 아래 롤 정의를 따른다.

<롤 파일 본문 전체>

## 작업
<사용자 요청 + 매니저가 정리한 범위>

## 요구 기준 (검증·평가 에이전트가 이 기준으로 따로 판정한다)
1. <기준> — 확인 방법: <명령·측정·관찰>

## 지난 시도 (2번째 시도부터)
- 시도 n: <접근> → 실패한 기준과 검증 근거
- 이번에 바꿀 것: <고칠 부분 | 다른 접근>

## 맥락
- 프로젝트 루트: <경로>
- 관련 파일·결정 사항: <매니저가 아는 것>
- 관련 결정: <DECISIONS.md에서 이 작업에 걸리는 항목, 없으면 생략>
- 이 롤의 교훈: <LESSONS.md에서 이 롤 항목, 없으면 생략>

## 규칙
- 담당 범위(scope) 밖 파일은 꼭 필요할 때만 고치고, 고쳤으면 이유를 보고에 적는다.
- 사용할 스킬: <롤의 skills, 없으면 생략>
- 먼저 읽을 것: <롤의 refs, 없으면 생략>
- 커밋·push·배포처럼 되돌리기 어려운 일은 하지 않는다. 필요하면 보고에 적는다. 예외: `## 작업`에 커밋(·push·릴리즈)이 적혀 있으면(사용자 승인) 적힌 것만 하고, 커밋에는 매니저가 미리 갱신한 `war-room/` 문서 변경도 넣는다.

## 보고 형식
- 결과: 완료 | 일부 | 실패
- 바뀐 파일: 경로 목록
- 확인한 것: 돌린 명령과 결과
- 남은 일·막힌 점
- 정한 것: 작업 중 내린 결정과 이유 (없으면 생략)
- 겪은 문제: 막혔던 것과 해결, 롤 문서에 넣으면 좋을 것 (없으면 생략)
```

## 상태 문서

### STATUS.md (덮어쓰기)

작업이 끝날 때마다 통째로 다시 쓴다. 갱신 시각은 `date '+%Y-%m-%d %H:%M'`으로 얻는다.

- **진행 중**: `<롤 id> · 작업 · 시도 n/최대 · 남은 실패 기준`
- **다음 할 일**: 사용자가 말했거나 보고의 "남은 일"에서 나온 것
- **막힌 것**: 사용자 결정이 필요한 것
- **롤 후보**: 새 롤·분리·갱신 신호(`[종류]` 표시). 다시 쓸 때도 이어서 남긴다 (`references/role-split.md`)
- **최근 완료**: `날짜 · 롤 · 한 줄`, 최신이 위. 10개를 넘으면 아래쪽을 `archive/STATUS-YYYY-MM.md`(완료한 달)에 옮긴다

"지금 뭐 하고 있어", "다음 뭐 해" 같은 질문은 이 파일로 답한다.

### DECISIONS.md (쌓임)

- 되돌리기 어렵거나 나중에 이유가 궁금할 결정만 적는다. 작업 결과("버튼 추가함")는 적지 않는다.
- 롤이 정한 것은 사용자에게 보고할 때 같이 알리고 적는다.
- 새 항목은 위에 추가하고, 지난 항목은 고치지 않는다. 결정이 바뀌면 "YYYY-MM-DD 결정을 뒤집음"이라고 새 항목을 쓴다.
- 300줄을 넘으면 지난달 이전 항목을 `archive/DECISIONS-YYYY.md`(해당 연도)로 옮긴다.

### LESSONS.md (반영하면 비움)

- 같은 실수를 막는 데 필요한 것만 적는다. 한 번뿐인 사고는 적지 않는다.
- 비우는 방법
  - "롤 문서 반영 후보"가 쌓이면 사용자에게 보여주고, 승인받은 것을 `roles/<id>.md`의 해당 절(`일하는 방식`, `하지 않는 일`, `완료 기준`)에 넣는다.
  - 반영했거나 더는 맞지 않는 항목은 `archive/LESSONS-YYYY.md`로 옮긴다.
- 항목이 10개를 넘으면 반영을 먼저 제안한다.

### 공통

- 비밀값·토큰·개인정보는 적지 않는다.
- `archive/`는 읽기만 한다. 과거를 물을 때("지난달 뭐 했어", "그때 왜 그렇게 정했어") 찾아본다.

## 하지 않는 것

- `war-room/`이 없는 프로젝트에서 사용자가 묻지 않았는데 설치를 권하기
- 롤 에이전트를 거치지 않고 담당 롤이 있는 일을 매니저가 직접 하기 (사용자가 직접 하라고 했을 때는 예외. STATUS는 갱신한다)
- 롤 파일·config를 사용자 확인 없이 크게 바꾸기 (켜고 끄기는 예외. 롤 문서에 교훈을 넣는 것은 승인을 받는다)
