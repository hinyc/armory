# 커밋 메시지 작성 기법

## 개요

**커밋 메시지는 변경사항을 5줄 이내의 한글로 명확하게 전달하는 문서입니다.**

핵심 원칙: 제목은 전체를 요약하고, 상세내용은 수정사항을 쉽게 파악할 수 있게 작성합니다.

## 구조

```
<타입>: <한글 요약 제목>

- 변경사항 1: 간단한 설명
- 변경사항 2: 간단한 설명
- 변경사항 3: 간단한 설명
```

**필수 요소:**
1. **제목** (첫 줄): 타입 + 전체 변경을 요약하는 한 줄
2. **공백줄** (두 번째 줄): 제목과 상세내용 분리
3. **상세내용** (3-5줄): `- ` 로 시작하는 bullet points, 수정사항별 1줄씩

## 제목 작성법

**형식:** `<타입>: <한글 요약>`

**타입:**
- `feat`: 새 기능
- `fix`: 버그 수정
- `refactor`: 코드 개선
- `perf`: 성능 최적화
- `docs`: 문서 수정
- `test`: 테스트 추가/수정
- `chore`: 빌드, 의존성 등

**제목 작성 팁:**
- 전체 변경을 한 문장으로 요약
- 동사로 시작 (예: "추가", "개선", "변경")
- 마침표 없음
- 50자 이내 (한글 기준)

### ❌ 나쁜 제목
- `fix: 버그` (너무 추상적)
- `refactor: 코드 리팩토링 및 에러 처리 개선 그리고 성능 최적화` (너무 길고 여러 개)
- `chore: 업데이트` (무엇을 업데이트?)

### ✅ 좋은 제목
- `fix: 로그인 폼 에러 메시지 표시 오류 수정`
- `feat: 사용자 역할 요청 기능 추가`
- `perf: API 응답 캐싱으로 로딩 속도 개선`

## 상세내용 작성법

**목표:** 3-5줄 이내에 각 수정사항을 명확하게 표시

**형식:**
```
- 변경 항목 1: 구체적인 변경 내용
- 변경 항목 2: 구체적인 변경 내용
- 변경 항목 3: 구체적인 변경 내용
```

**작성 팁:**
- 각 줄은 하나의 수정사항만 표현
- "무엇을 변경했는가"가 명확해야 함
- 도메인/기능명을 명시 (예: "역할 관리", "인증", "API 응답")
- 기술 용어는 필요한 경우만 사용 (Redux → Zustand 마이그레이션 같은 경우)
- 파일명 대신 기능/컴포넌트 이름 사용

### 예시

**예시 1: UI 수정**
```
fix: API 관리 상태 컬럼 너비 조정

- 상태 컬럼 너비: 80px → 90px로 증가
- 텍스트 표시 영역 확보로 레이아웃 개선
```

**예시 2: 기능 추가**
```
feat: 사용자 역할 요청 기능 추가

- 역할 요청 API 엔드포인트 구현
- 요청 현황 조회 화면 추가
- 승인/거절 상태 관리 로직 완성
```

**예시 3: 버그 수정**
```
fix: 대시보드 필터 초기화 버그 수정

- 필터 리셋 시 상태 값 미업데이트 문제 해결
- useCallback 의존성 배열 수정으로 재렌더링 최적화
- 테스트 케이스 추가 (필터 상태 검증)
```

## 사용 시점

- 수정사항이 2개 이상일 때: 각 항목을 bullet point로 표시
- 1개 수정사항만 있을 때: 상세내용 생략 가능, 제목만 작성
- 코드 리뷰 전: 커밋 메시지를 한 번 더 검토

## 자주 하는 실수

| 실수 | 문제점 | 해결책 |
|------|--------|--------|
| 제목이 너무 길다 | 50자 초과 | 요약을 더 간결하게 |
| 상세내용이 없다 | 변경사항 파악 어려움 | bullet point로 3-5줄 추가 |
| 상세내용이 5줄 초과 | 너무 상세 | 가장 중요한 항목만 표시 |
| 영어로 섞어 쓴다 | 일관성 없음 | 한글로 통일 |
| 마침표 붙인다 | 불필요 | 제목/bullet point 끝에 마침표 제거 |

## 검사 체크리스트

커밋 전에 확인:
- [ ] 제목이 50자 이내인가?
- [ ] 제목이 전체 변경을 요약하는가?
- [ ] 상세내용이 3-5줄 이내인가?
- [ ] 각 줄이 하나의 수정사항만 표현하는가?
- [ ] 한글로만 작성했는가?
- [ ] 제목과 bullet point에 마침표가 없는가?
