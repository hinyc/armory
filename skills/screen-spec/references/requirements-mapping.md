# 요구사항 ↔ 화면 연결 기준

`mapping.json`의 `links`는 `캡처id → [{ req, rationale }]`이다. 문서에서 양방향으로 보인다.
- 캡처 카드에는 요구사항 칩이 붙는다.
- 요구사항 탭에는 구현 화면 목록이 붙는다.

## 연결하는 경우

요구사항을 **충족하는 절차의 각 단계 화면**에 연결한다.
- 입력 화면
- 확인 다이얼로그
- 진행 중 표시
- 성공 결과
- 실패·예외 안내

예: "관리자는 확인 절차를 거쳐 주문을 취소할 수 있어야 한다"
- `orders-list`: 취소 버튼이 있는 시작 화면
- `orders-cancel-confirm`: 확인 절차
- `orders-cancel-done`: 완료 안내

## 연결하지 않는 경우

- **주제나 단어만 겹치는 경우**: 요구사항이 "주문 통계"인데 주문 목록 화면에 연결하지 않는다.
- **화면에 드러나지 않는 의무**: 로그 보관 기간, 암호화 방식, 성능 기준.
- **하위 조항이 실제 의무를 가진 상위 조항**: 소개 문장 역할만 하는 상위 조항에는 연결하지 않고 하위 조항에 연결한다.
- **아직 구현되지 않은 동작**: 화면이 있어도 요구한 동작이 없으면 연결하지 않고 요구사항 `status`를 `planned`나 `partial`로 둔다.

## 근거 (rationale)

- 모든 연결에 한 줄 근거를 쓴다. 그 화면이 요구사항의 **어느 부분을 어떻게** 보여주는지를 쓴다.
  - 좋음: "결제 완료 주문에만 취소 버튼을 보여 취소 대상 제한을 충족"
  - 나쁨: "관련 있음", "주문 화면"
- 근거를 한 줄로 쓰지 못하면 연결하지 않는다.

## 작업 순서

1. 캡처 목록을 표로 뽑는다: id, 섹션, 화면, kind, 제목, 설명. `<OUT_DIR>/data/*.json`에서 만든다.
2. 요구사항을 하나씩 보면서 위 기준으로 캡처를 고른다. 요구사항이 많으면 범위를 나눠 진행한다.
3. 결과를 `mapping.json`에 쓰고 `draft: true`로 둔다. 문서 상단에 "AI 초안 — 검토 필요" 배지가 뜬다.
4. 연결이 없는 요구사항 목록을 따로 보여준다. 화면 누락인지, 화면과 무관한 요구인지 사용자가 판단하게 한다.
5. 사용자가 검토 완료를 말하면 `draft: false`로 바꾼다.

## 요구사항 상태 (status)

| 값 | 의미 |
|---|---|
| `implemented` | 구현됨 |
| `partial` | 일부만 구현됨 (`note`에 빠진 부분) |
| `planned` | 예정 |
| `notApplicable` | 이 시스템에 해당 없음 |
| `unclassified` | 아직 판단하지 않음 (기본값) |

상태는 원문이나 사용자 판단을 따른다. 에이전트가 임의로 `implemented`로 올리지 않는다.
