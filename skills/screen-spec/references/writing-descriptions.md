# 제목 · 설명 작성 규칙

설명은 **이 화면만 보고도 개발자·기획자·QA가 동작을 이해할 수 있게** 쓴다. 근거는 항상 코드다.

## 제목 (title)

- 상태를 가리키는 짧은 명사구로 쓰고, 조건은 괄호에 넣는다.
  - `주문 목록`
  - `주문 목록 (주문 0건)`
  - `주문 목록 (조회 실패)`
  - `주문 취소 확인`
- 같은 화면 안에서 제목만 보고 상태를 구분할 수 있어야 한다.

## 설명 (description)

이 순서로, 해당하는 것만 쓴다.

1. **진입 방법**: 어디서 무엇을 누르면 열리는지, 어떤 조건일 때 이 상태가 되는지
2. **보이는 것**: 무엇을 어떤 순서·기준으로 보여주는지 (정렬, 개수 제한, 기본 필터)
3. **의미**: 색, 아이콘, 배지, 비활성 버튼의 의미
4. **다음 동작**: 각 버튼·행을 누르면 어디로 가거나 무슨 일이 생기는지
5. **갱신**: 자동 새로고침 주기, 실시간 반영 여부
6. **예외**: 서버 오류, 권한 없음, 입력 검증 실패 때의 동작

규칙:
- 사실만 평서문으로 쓴다. "~한다", "~이 보인다".
- 화면 문구(버튼명, 안내 문구)는 앱에 보이는 그대로 따옴표로 쓴다: "다시 시도" 버튼.
- 서버에 따라 달라지는 조건은 밝힌다: "API가 실패하면 …".
- 특정 경우로 찍은 캡처면 밝힌다: `(캡처: 결제 완료 주문 1건 선택)`.
- 다른 캡처를 가리킬 때는 `[[캡처id]]` 또는 `[[캡처id|보일 문구]]`를 쓴다. 문서에서 링크가 된다.
- 문단은 빈 줄(`\n\n`)로 나눈다.
- 코드 이름(컴포넌트, 함수, 상태 변수)은 설명에 쓰지 않는다. 화면을 보는 사람의 말로 쓴다.
- 코드에서 확인하지 못한 내용은 쓰지 않는다. 확인이 필요하면 사용자에게 묻는다.

## 코드에서 찾을 것

| 쓸 내용 | 찾을 곳 |
|---|---|
| 진입 방법 | 라우트 정의, 메뉴 컴포넌트, `navigate()`·링크 호출부 |
| 정렬·개수 | API 요청 파라미터, `sort`·`slice` 호출 |
| 색·배지 의미 | 상태 → 색 매핑 객체, 조건부 className |
| 버튼 동작 | onClick 핸들러, 호출하는 API, 이동 경로 |
| 갱신 주기 | `setInterval`, 쿼리 라이브러리의 `refetchInterval`, 웹소켓 구독 |
| 예외 처리 | `catch`, 에러 바운더리, 응답 코드별 분기 |

## 예시

좋은 예:

```
사이드 메뉴 "주문"을 누르면 열린다. 최근 30일 주문이 최신순으로 20건씩 보인다.

상태 색: 초록=결제 완료, 파랑=배송 중, 회색=취소. 결제 완료 주문에만 "취소" 버튼이 보이고, 누르면 [[orders-cancel-confirm|취소 확인]]이 열린다.

30초마다 목록을 자동으로 다시 불러온다.
```

나쁜 예와 이유:

| 나쁜 예 | 이유 |
|---|---|
| 주문 목록 화면입니다. | 제목을 반복할 뿐 정보가 없다 |
| OrderTable 컴포넌트가 useOrders 훅으로 데이터를 가져온다. | 코드 이름은 화면을 보는 사람에게 의미가 없다 |
| 아마 실시간으로 갱신될 것이다. | 추측이다. 코드로 확인하고 쓴다 |
| 사용자가 편리하게 주문을 관리할 수 있다. | 동작이 아니라 홍보 문구다 |
