# war-room 위임·검증 보강 설계

작성: 2026-11-09 · 상태: 사용자 승인 (2026-11-09) · 검토 에이전트 확인·외부 검토·기준 검토 반영

## 왜 하나

war-room은 매니저(메인 세션) 한 명이 맥락을 들고, 일과 검증은 따로 띄운 에이전트가 맡는 혼합 방식이다. 독립 검증과 병렬 처리는 되지만 다음 빈 곳이 있다.

1. 매니저가 직접 한 일은 매니저가 직접 검증한다 (자기 검토).
2. 검증·평가 에이전트도 파일을 고칠 수 있는 도구를 다 가진다. "고치지 마라"는 프롬프트로만 막는다.
3. 기준은 매니저가 쓰고 구현·검증 둘 다 그 기준을 따른다. 기준이 틀리거나 빠지면 둘 다 통과한다.
4. 넘길 때 정보가 빠진다. 실제로 두 번 다시 시도한 일이 모두 매니저가 맥락을 덜 넣어서 생겼다.
5. 재시도 때 매니저가 쓴 접근 설명이 들어가고, 두세 번 실패해도 기준·설계를 다시 보는 단계가 없다.
6. 매니저가 롤 없는 일을 직접 하면 파일 내용이 매니저 맥락에 쌓여 중요한 결정이 묻힌다. 세션이 끊겼을 때 문서만으로 이어받을 수 있는지 확인하지 않는다.
7. 공유 기억 파일을 누가 쓰는지 정해져 있지 않다. LESSONS는 10개를 넘어야 정리한다.
8. 오타 수정에도 에이전트 3~7개가 돈다.
9. 병렬로 맡긴 두 롤이 같은 형식·이름을 쓰면 충돌한다 (평가 롤 작업 때 타입 파일 충돌이 났다).

## 목표

- 매니저의 실수(기준 누락, 맥락 누락)를 형식과 독립 검토로 막는다. 매니저의 기억력에 기대지 않는다.
- 검토 에이전트는 도구 수준에서 파일을 못 고치게 한다.
- 위험도에 따라 검증 비용을 나눈다.
- 매니저를 가볍게 두고, 문서만으로 이어받을 수 있게 한다.

## 하지 않는 것

- 매니저를 서브에이전트로 바꾸지 않는다 (메인 세션 유지).
- DECISIONS 형식을 번호 체계로 바꾸지 않는다. 결정은 `날짜 · 제목`으로 가리킨다 (기존 설치 호환). 대신 확정된 항목의 제목은 한 번 쓰면 바꾸지 않는다. 같은 날 같은 제목이면 제목 끝에 `(2)`를 붙인다.
- 새 config 키를 만들지 않는다. 위험도 등급은 매니저가 요청마다 정한다.
- 팀이 같이 쓸 때의 문제(통째로 덮어쓰는 STATUS.md의 merge 충돌, 여러 매니저의 동시 갱신)는 다루지 않는다. 지금은 혼자 쓴다 (2026-11-10 확인). 팀원이 war-room을 켠 세션을 같이 돌리기 시작하면 다시 본다.
- armory 플러그인 없이 `war-room/` 폴더만 있는 설치에서 "담당 롤 먼저"를 강제하는 수단은 만들지 않는다. 지금 설치처(armory, ccs-front)는 모두 플러그인이 있다. 플러그인 없는 설치가 생기면 다시 본다.

## 실패로 볼 것

- 등급을 낮게 매겨 위험한 일이 기계 검사만으로 통과하는 것.
- 템플릿 칸이 늘어 프롬프트가 형식만 채우고 내용은 비는 것 ("없음"만 가득).
- 기준 검토가 매번 돌아 작은 일까지 느려지는 것.

## 결정 (모두 매니저 판단, 사용자가 받은 글의 제안을 따름)

### A. 위험도 등급 (항목 8, 그리고 1의 해법)

매니저가 배정 3번에서 등급을 정하고 알리기 줄에 적는다. 예: `→ frontend 롤에 맡깁니다 (로그인 폼 수정, 등급 중, 기준 3개, 최대 3회)`. 사용자가 바꿀 수 있다. 애매하면 높은 쪽.

| 등급 | 어떤 일 | 검증 |
|---|---|---|
| 하 | 동작이 바뀌지 않는 일: 오타·문구, 주석, 한 파일 몇 줄 설정, 롤 문서에 승인된 교훈 넣기, 상태 문서 정리 | 기계 검사만. 명령(테스트·린트·validate·grep)을 돌리고 결과로 판정한다. 매니저가 돌려도 된다 (판단이 아니라 명령 결과라서). 평가 롤을 띄우지 않는다 |
| 중 | 기능 추가·수정, 여러 파일, 동작이 바뀌는 일 | 평가 롤 ③만 (① 계획은 수치 갈래가 필요할 때만). 평가 에이전트 model은 `haiku`. ①이 없으면 매니저가 **구현을 맡기기 전에** 전체 테스트 명령을 돌려 원래 실패하던 테스트 목록(기준선)을 남기고, 위임 칸 `## 기준선`과 ③ 프롬프트에 넣는다. 구현 뒤에 뜬 목록은 기준선으로 쓰지 않는다 (명령 결과라 매니저가 돌려도 된다) |
| 상 | 배포·릴리즈·push, 구조·인터페이스 변경, 데이터 삭제·마이그레이션, 공개 노출, 보안·권한, 여러 롤 병렬 | 기준 검토(C) + 평가 ① + ③, 평가 에이전트 model은 롤 파일 값(기본 `sonnet`), 되돌리기 어려운 단계 전에 사람 승인 |

- **무조건 "상"인 조건** (매니저 판단으로 낮추지 않는다): 릴리즈·push·배포, war-room 지침·롤 파일·config·스킬 절차 수정, 시스템 프롬프트에 들어가는 문구(mod 지침) 수정, 여러 롤 병렬, 바뀌는 파일 5개 이상, 삭제·마이그레이션, 공개 노출, 권한·보안.
- **"하"의 조건** (모두 맞아야 한다): 동작이 바뀌지 않음, 바뀌는 파일 2개 이하, 돌릴 기계 검사가 있음, 위 "상" 조건에 하나도 안 걸림.
- 평가 에이전트는 실제 변경 범위(바뀐 파일 수·종류)를 보고 등급이 낮게 매겨졌으면 보고의 `등급 올림` 칸에 적는다. 매니저는 올린 등급의 검증을 다시 한다 (예: "중"으로 했는데 "상"이면 기준 검토와 사람 승인을 더한다). 매니저가 직접 처리한 "하" 일은 STATUS 최근 완료에 등급과 바뀐 파일 수를 적어 나중에 확인할 수 있게 한다.
- 담당 롤이 있는 일은 "하"라도 그 롤에 맡긴다 (롤 소유 유지, 롤 제안 신호도 그대로). 등급은 검증 방식만 바꾼다. 예외: 승인된 교훈 넣기·상태 문서 정리처럼 G에서 매니저만 쓰는 파일은 매니저가 한다.
- 순서: 담당 찾기(2번) → 등급·기준(3번). 등급은 담당을 바꾸지 않는다.
- "하"라도 기계 검사가 하나도 없으면(돌릴 명령이 없음) "중"으로 올린다.
- 매니저가 롤 없이 직접 한 일도 같은 등급표를 쓴다. "하"가 아니면 평가 롤이 판정한다 (매니저 자기 검토 금지).
- evaluator가 꺼져 있거나 없으면 "중"·"상"은 지금의 임시 검증 에이전트를 쓰되 아래 B의 읽기 전용 에이전트로 띄운다.

### B. 읽기 전용 검증 에이전트 (항목 2)

- armory 플러그인에 에이전트 정의를 둔다: `agents/evaluator.md` → 에이전트 종류 `armory:evaluator`.
  - 도구: Read, Grep, Glob, Bash, Skill. Edit·Write·NotebookEdit·Agent 없음.
  - Skill은 conceptpowers의 개념 점검(review)을 쓰기 위해 둔다. 프롬프트에 "판정용 읽기 스킬만 쓴다. 파일을 바꾸는 스킬은 부르지 않는다"를 넣는다. Bash가 이미 있어 완전한 차단이 아니므로, 아래 git status 확인이 최종 안전장치다.
  - 진행 파일(`war-room/.eval/<롤 id>.json`)은 Bash로 쓴다 (평가 프롬프트에 쓰는 명령 예를 넣는다).
  - Bash로도 파일을 고칠 수 있으므로 완전한 차단은 아니다. 프롬프트의 "코드를 고치지 않는다"와 함께 쓴다. 평가 전후 스냅숏을 비교한다. 구현 결과가 이미 작업 폴더에 있으므로 "바뀐 파일이 없는지"로는 판정하지 않는다.
    - 평가를 띄우기 직전에 매니저가 스냅숏을 남긴다: `git status --porcelain --ignored`, `git diff` 와 `git diff --cached`의 해시, 추적 안 되는 파일 각각의 해시. 저장 위치는 `war-room/.eval/<롤 id>.snapshot` (커밋 안 함).
    - 평가가 돌아오면 같은 방법으로 다시 떠서 비교한다. 진행 파일(`.eval/`) 외에 하나라도 다르면 그 평가는 무효로 하고, 바뀐 내용을 사용자에게 알린 뒤 다시 띄운다.
    - 저장소 밖(홈 설정, 다른 폴더) 변경은 이 비교로 못 잡는다. 이 범위는 프롬프트 규칙("작업 폴더 밖을 쓰지 않는다")에 맡기고 한계로 문서에 적는다. 별도 worktree에서 평가하는 방식은 비용이 커서 쓰지 않는다.
- 배정 6번·evaluation.md의 `subagent_type`을 `armory:evaluator`로 바꾼다. 롤 파일의 `model`과 등급별 model은 Agent 호출의 `model`로 넘긴다.
- armory 플러그인 없이 war-room 폴더만 있는 경우(다른 도구로 설치)는 `general-purpose`로 되돌아가고 그렇다고 알린다.

### C. 기준 검토 (항목 3)

- 기준은 가능한 한 실행 가능한 검사로 쓴다: `확인 방법`에 명령과 기대 결과를 적는다 ("이 명령 → 이 출력"). 사람이 볼 것만 예외로 표시한다.
- 평가·검증 에이전트는 기준을 읽고 넘어가지 않고 확인 방법을 직접 실행한다. 실행하지 않은 기준은 통과로 치지 않는다.
- 등급 "상"은 맡기기 전에 기준 검토를 한다. 평가 ① 계획 에이전트가 맡는다 (매니저와 대화를 공유하지 않는 새 에이전트라 독립적이다).
  - 받는 것: 요청 원문 요지, 목표·범위·범위 밖, 기준, 관련 결정
  - 묻는 것: "이 기준에서 빠진 경우(예외, 경계값, 다른 롤 영향, 실패 경로)가 무엇인가"
  - 보고 칸 `기준에 빠진 것` 추가. 매니저는 받아들일 것을 기준에 넣고, 사용자가 정할 것이면 묻는다.
- evaluator가 없을 때 "상"이면 같은 질문을 읽기 전용 에이전트 하나로 따로 묻는다.

### D. 위임 프롬프트 고정 칸 (항목 4)

롤 프롬프트 템플릿을 아래 칸으로 고정한다. 칸을 빼지 않는다. 비어 있으면 "없음 (확인함)"이라고 쓴다.

```
## 목표          한 문장: 무엇이 되어야 하나
## 범위          할 일
## 범위 밖       하지 않을 일, 건드리지 않을 경로
## 관련 파일     경로
## 요구 기준     번호 · 기준 · 확인 방법(명령 → 기대 결과)
## 알려진 예외   경계값·특수 경우·예외 처리 (매니저가 아는 것)
## 관련 결정     DECISIONS.md `날짜 · 제목` 목록
## 기준선        (중·상) 맡기기 전에 뜬 원래 실패 테스트 목록·변경 전 수치. 구현 뒤에 뜬 값은 넣지 않는다
## 공유 약속     (병렬일 때) 다른 롤과 함께 쓰는 형식·이름·경로 — 글자 그대로
## 지난 시도     (재시도일 때) E 규칙대로
```

보고 형식에 두 칸을 더한다 (필수):
- `가정한 것`: 지시에 없어서 스스로 정한 것
- `모호했던 것`: 두 가지 이상으로 읽힌 지시와 어느 쪽으로 했는지

매니저는 보고를 받으면 검증 전에 이 두 칸을 먼저 읽는다. 기준·범위에 걸리는 가정이면 검증 전에 사용자에게 묻거나 기준을 고친다. 고친 기준으로 평가한다.

평가 ①·③ 프롬프트도 같은 칸 이름을 쓴다 (목표·범위·범위 밖·기준·알려진 예외·관련 결정).

### E. 재시도 때 넘길 것과 상한 (항목 5)

- `## 지난 시도`에는 평가·검증 에이전트가 찾은 실패 내용(실패 기준·갈래, 근거)만 넣는다. 구현 에이전트의 설명·자기 평가는 넣지 않는다. 매니저가 덧붙이는 것은 "이번에 바꿀 것" 한 줄뿐이다.
- 시도 횟수는 STATUS 진행 중의 `시도 n/최대`로 센다 (세션이 바뀌어도 이어서 센다).
- 같은 일이 **2번 실패하면** 3번째를 맡기기 전에 매니저가 "기준·설계 다시 보기"를 한다.
  - 두 실패의 원인이 같은 기준·같은 갈래인가, 기준끼리 부딪히는가, 기준이 모호해 판정이 갈렸는가를 본다.
  - 기준·설계 문제로 보이면 재시도하지 않고 사용자에게 묻는다 (무엇이 왜 막혔는지, 고칠 안 2개).
  - 실행 문제(구현 실수)로 보이면 3번째를 맡기고 이유를 한 줄 알린다.
- 끝까지 모드에서도 이 다시 보기는 한다. 다만 묻지 않고 접근을 바꾼다 (사용자만 정할 수 있는 것일 때만 묻는다).

### F. 매니저를 가볍게 (항목 6)

- 롤 없는 일 중 파일을 여러 개(3개 이상) 읽어야 하는 조사·분석은 읽기 전용 조사 에이전트(`Explore`)에 맡기고 결론만 받는다.
- 롤 없는 일 중 "하"가 아닌 구현은 임시 작업 에이전트(`general-purpose`)에 D 템플릿으로 맡긴다. 담당은 `manager`로 적고 롤 제안 신호("자주")를 센다.
- 매니저가 직접 하는 것: 배정, 기준·등급, 사용자와 대화, 상태 문서, "하" 등급 일.
- **이어받기 점검**: 일이 끝날 때 STATUS를 쓰면서 "새 세션이 STATUS.md와 DECISIONS.md만 읽고 지금 상태와 다음 할 일을 말할 수 있는가"를 본다. 진행 중 항목에 이어받는 데 필요한 것을 적는다: `롤 · 작업 · 등급 · 시도 n/최대 · 남은 실패 기준 · 기준이 적힌 곳(계획·설계 문서 경로)`.
- "상" 등급은 ③을 띄우기 전에 매니저가 STATUS(진행 중·이번 일 결과 예정)와 DECISIONS(이번 일의 결정)를 미리 써 둔다 (커밋으로 끝나는 일과 같은 방식). 미리 쓴 DECISIONS 항목 제목 끝에 `(검증 대기)`를 붙이고, 평가를 통과하면 뗀다. 실패해 결정이 바뀌면 그 항목을 지우고 새로 쓴다 (아직 확정 전이라 "지난 항목은 고치지 않는다" 규칙의 예외). 다음 매니저는 `(검증 대기)` 항목을 확정된 결정으로 읽지 않는다. 그다음 평가 ③이 이어받기 점검도 한다: STATUS·DECISIONS만 읽고 이번 일의 상태와 결정을 말할 수 있는지. 못 하면 기준 실패와 같이 다룬다 (갈래: 히스토리).

### G. 공유 기억 파일 (항목 7)

- `STATUS.md`·`DECISIONS.md`·`LESSONS.md`·`roles/`·`config.json`은 매니저만 쓴다. 서브에이전트는 보고의 `정한 것`·`겪은 문제`·`가정한 것`으로 제안만 한다.
  - 예외: release처럼 커밋하는 롤은 매니저가 미리 고친 문서를 커밋에 넣기만 한다 (내용은 고치지 않는다).
  - 평가 에이전트는 자기 진행 파일(`.eval/<롤 id>.json`)만 쓴다.
- 롤 프롬프트 `## 규칙`에 "war-room/ 문서는 고치지 않는다 (진행 파일 제외)"를 넣는다.
- LESSONS 정리 주기
  - 같은 종류 교훈이 두 번째로 나오면 그 자리에서 롤 문서·SKILL 규칙 반영을 제안한다.
  - 항목이 5개를 넘거나 가장 오래된 항목이 14일을 넘으면 다음 보고 뒤 반영·정리를 제안한다 (지금 "10개"를 바꾼다).
  - 반영한 항목은 archive로 옮기고 LESSONS에서 지운다 (지금과 같음).

### H. 병렬 전 공유 약속 (항목 9)

- 여러 롤을 동시에 맡기기 전에 매니저가 둘 사이의 약속(파일 형식, 필드 이름, 함수·타입 이름과 위치, 경로)을 먼저 정하고 `## 공유 약속` 칸에 양쪽 프롬프트에 글자 그대로 넣는다.
- 약속을 맡기기 전에 정할 수 없으면 동시에 맡기지 않고 순서대로 맡긴다 (먼저 하는 롤이 약속을 만든다).
- 병렬 일은 등급 "상"이다. 롤별 평가가 통과한 뒤 매니저가 전체 검사(테스트·validate)를 한 번 더 돌린다 (지금 evaluation.md 규칙 유지).

## 바뀌는 파일 (예상)

### I. 기준 검토에서 나온 정리 (매니저 판단)

- **두 축을 나눈다**: 평가 롤 켜짐(config `roles.evaluator`, 롤 파일)과 평가 에이전트 종류(armory 플러그인 유무)는 별개다.
  - 플러그인이 있으면 평가 롤이 꺼졌거나 없어도 검증·기준 검토 에이전트는 `armory:evaluator`로 띄운다 (다섯 갈래 대신 기준별 판정).
  - 플러그인이 없으면 `general-purpose`로 되돌리고 그렇다고 알린다.
- **교훈 넣기**: "롤 파일 수정은 무조건 상"의 예외. 사용자가 승인한 문장을 그대로 넣는 롤 문서 수정은 "하"다 (확인: 그 문장이 해당 절에 있는지 grep). 문장을 바꾸거나 새 규칙을 쓰면 "상".
- **"하" 사후 점검**: 매니저가 "하" 일을 끝내면 바로 `git diff --stat`으로 바뀐 파일 수를 센다. 3개 이상이거나 "상" 조건에 걸리면 그 자리에서 등급을 올려 평가한다.
- **병렬과 스냅숏**: 병렬로 맡긴 일은 모든 롤의 구현이 돌아온 뒤 한 번에 스냅숏을 뜨고 평가를 띄운다 (롤별 평가는 동시에 돌려도 된다, 모두 읽기 전용). 문서 미리 쓰기 → 스냅숏 → 평가 순서.
- **실패 횟수**: 평가(또는 검증) 판정 1번이 실패면 1로 센다.
- **끝까지 모드**: 다시 보기 결과가 "기준끼리 부딪힘"이나 "기준이 모호함"이면 사용자만 정할 수 있는 것으로 보고 묻는다.
- **롤 제안 "자주" 신호**: 매니저가 직접 한 일과 임시 작업 에이전트에 맡긴 롤 없는 일을 함께 센다.
- **STATUS 진행 중 형식**은 `template/STATUS.md`에도 넣는다.

## 릴리즈 뒤 검증 (ccs-front)

이 레포는 war-room 자체를 만드는 곳이라 "일반 프로젝트에서 등급 판단이 잘 되는지"를 보여주지 못한다. v0.5.0 릴리즈 뒤 ccs-front(war-room 설치됨, 롤 5개, evaluator 없음)에서 플러그인을 올리고 다음을 한 번씩 시킨다.

| 등급 | 시킬 일 (예) | 보는 것 |
|---|---|---|
| 하 | 문구·오타 수정 한 곳 | 롤 에이전트 1개만 뜨고, 평가 에이전트가 뜨지 않는다. 매니저가 명령(lint·typecheck)으로 판정한다 |
| 중 | 화면 하나의 동작 수정 | 평가 에이전트 1개(haiku)가 뜬다. 기준선(원래 실패 테스트)이 위임 프롬프트에 들어간다 |
| 상 | 여러 롤에 걸치는 일 또는 push | 기준 검토가 먼저 돌고, 되돌리기 어려운 단계 전에 사용자 승인을 묻는다 |

- evaluator 롤 파일이 없는 기존 설치라서 첫 중·상 배정에서 "평가 롤을 추가할 수 있어요"가 **한 번만** 떠야 한다.
- 등급을 잘못 매기거나(하인데 평가가 돎, 상인데 승인 없이 진행) 제안이 반복되면 이 레포 `war-room/LESSONS.md`에 적고 고친다.
- 결과는 ccs-front가 아니라 이 레포 STATUS 최근 완료에 한 줄로 남긴다.

## 이 작업 자체의 등급

이 작업은 스킬 절차·롤·시스템 프롬프트 지침을 바꾸므로 새 규칙의 "상"이다. 새 규칙의 첫 적용 사례로 진행한다: 기준을 실행 가능한 검사로 쓰고, 맡기기 전에 새 에이전트에게 기준 검토를 받고, 기준선을 뜨고, 구현은 고정 칸 프롬프트로 맡기고, 평가는 sonnet, 릴리즈 전 사람 승인. 확인 항목에 "war-room-guard 지침이 '하 등급만 매니저가 직접 한다'와 정확히 맞는다"를 넣는다.
