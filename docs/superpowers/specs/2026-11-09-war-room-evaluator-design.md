# war-room 평가 롤(evaluator) 설계

작성: 2026-11-09 · 상태: 초안 (사용자 승인 전) · 검토 에이전트 확인 반영

## 왜 만드나

지금 war-room은 일이 끝나면 매니저가 임시 검증 에이전트를 띄워 **이번 일에 붙인 기준만** 판정한다. 그래서 "시킨 기능이 돈다"면 통과한다. 다음을 놓친다.

- **히스토리 위반**: 예전에 정한 결정(DECISIONS)이나 교훈(LESSONS)을 거스른다.
- **사이드 이펙트**: 이번 변경이 다른 기능·다른 롤 영역을 깨뜨린다.
- **개념 위반**: 프로젝트가 정한 개념(conceptpowers 개념 문서)을 어긴다.
- **수치 없음**: 결과를 "됐다/안 됐다"로만 말한다. 값이 얼마였고 속도가 얼마인지, 돌긴 돌아도 너무 느린지 모른다.

평가 롤은 이 빈 곳을 메운다. 매니저와 함께 **기본 롤**로 설치되고, 임시 검증 에이전트를 대신한다.

## 목표

1. 일마다 평가 항목을 만들고, 일이 끝난 뒤 실제로 평가해 통과·실패를 판정한다.
2. 평가 항목은 다섯 갈래: 기준 · 히스토리 · 부작용 · 개념 · 수치.
3. 수치는 실제로 재서 숫자로 보고한다. 한계값을 넘으면 실패, 한계값 안에서 나빠지면 알리고 사용자가 정한다.
4. 히스토리·개념 위반은 실패로 처리하고 다시 맡긴다 (기존 verify-loop 재시도 흐름).
5. 평가가 도는 동안 입력창 위 띠(mod)에 이전 평가와 지금 평가 상태를 숫자까지 보여준다. 평가가 끝나면 띠는 사라진다.
6. conceptpowers와 같이 쓰면 개념 점검이 붙고, 없으면 그 갈래만 "해당 없음"으로 건너뛴다. 따로 써도 문제없다.

## 하지 않는 것

- 평가 롤은 코드를 고치지 않는다. 판정만 한다.
- conceptpowers의 reference(원자료)를 읽지 않는다. conceptpowers 원칙이다.
- 노랑(pending)·빨강(red) 개념 위반으로 실패시키지 않는다. 참고로만 알린다.
- 한계값 안의 성능 저하만으로 자동 실패시키지 않는다.
- 평가 항목 초안을 일마다 사용자에게 확인받지 않는다 (사용자가 정해야 할 것이 있을 때만).

## 실패로 볼 것 (안티 목표)

- 평가가 이번 기준만 보고 통과를 주는 것 (지금과 같아지는 것).
- 수치를 한 번만 재서 측정 잡음으로 실패·⚠를 내는 것.
- 띠가 평가가 끝난 뒤에도 남아 있거나, 질문 띠를 가려 버리는 것.
- 평가 롤이 구현 에이전트의 "잘 됐다" 설명을 근거로 판정하는 것.

## 사용자가 정한 것

- 위반(히스토리·개념)은 실패 처리 후 다시 맡긴다.
- 수치: 한계값을 넘으면 실패. 변경 전보다 나빠졌지만 한계값 안이면 알리고 통과 여부는 사용자가 정한다. "X 이하여야 한다"는 한계값을 정하게 한다.
- 개념 근거: conceptpowers 개념 문서와 DECISIONS 둘 다 본다. 개념 문서가 없는 프로젝트도 있다.
- 평가 항목 초안은 사용자가 정해야 할 것(한계값 미정, 결정끼리 충돌 등)이 있을 때만 확인받는다.
- 평가가 시작되면 mod가 이전 평가·지금 평가의 성공·실패 상태를 숫자까지 보여준다. 끝나면 사라진다.

## 흐름

```
요청 → 매니저 배정 ─→ ① 평가 롤: 평가 계획 (항목 초안 + 변경 전 수치 측정)
                         │  사용자가 정할 것 있으면 확인
                         ↓
                    ② 담당 롤 작업 (시도 n)
                         ↓
                    ③ 평가 롤: 평가 실행 (띠 표시)
                         ├ 통과 → ⚠ 있으면 사용자 확인 → 끝
                         └ 실패 → verify-loop 3절대로 다시 맡김 → ② (띠의 "이전"에 이번 결과)
```

- ①과 ③은 각각 새 평가 에이전트다 (`subagent_type: general-purpose`, `description: evaluator: <작업 요약>`, model은 롤 파일의 `model`).
- ①의 결과(평가 계획)는 매니저가 ③에 그대로 넘긴다. ③이 계획에 없는 항목을 발견하면 추가하고 보고에 적는다.
- 매니저 직접 처리한 일도 같은 흐름이다.
- 예외: 답만 하는 질문, 문서 상태 갱신만 하는 일(STATUS·LESSONS 정리)은 평가하지 않는다. (매니저 판단)
- 작은 일(한 파일 몇 줄)도 평가 롤을 띄운다. 다만 수치 갈래는 성능·크기에 영향이 없으면 "해당 없음"으로 둔다. (매니저 판단)

### 여러 롤에 나눈 일 (매니저 판단)
- 평가는 롤마다 따로 한다. 롤마다 ①·③이 따로 돈다.
- 진행 파일도 롤마다 따로 둔다: `war-room/.eval/<롤 id>.json`. 동시에 돌아도 서로 덮어쓰지 않는다.
- 띠는 `running`·`planning` 상태인 파일마다 블록 하나씩 그린다.
- 롤별 평가가 모두 통과한 뒤, 롤 사이 부작용을 보려고 매니저가 전체 테스트를 한 번 더 돌린다 (평가 롤의 부작용 갈래 명령 그대로).

### 이미 검증·QA 롤이 있는 프로젝트 (매니저 판단)
- 평가는 evaluator 롤이 맡는다. verify-loop 2절의 "검증·QA 롤이 있으면 그 롤에 맡긴다"는 "evaluator가 꺼져 있을 때만"으로 바꾼다.
- 사용자가 만든 QA 롤의 `완료 기준`·`일하는 방식`은 evaluator가 기준 갈래에 더해 쓴다 (롤 파일을 `refs`처럼 읽는다).
- 기존 설치에 evaluator를 추가할 때 QA 롤이 있으면, 두 롤의 경계를 `하지 않는 일`에 적자고 함께 제안한다.

## 평가 항목 다섯 갈래

각 항목은 `갈래 · 내용 · 확인 방법 · 판정(✓ ✗ ⚠ – )` 을 가진다. `–`는 해당 없음.

### 1. 기준
- 지금의 요구 기준 그대로 (verify-loop 1절). 사용자가 말한 기준 + 롤의 `완료 기준`.

### 2. 히스토리
- `war-room/DECISIONS.md`: 영향 경로가 바뀐 파일과 겹치거나 주제가 같은 항목을 고른다. 뒤집힌 결정은 최신 것만 본다. 거스르면 ✗.
- `war-room/LESSONS.md`와 `archive/LESSONS-*.md`: 같은 실수를 되풀이하면 ✗.
- `git log` (바뀐 파일마다 최근 커밋 몇 개): 직전 커밋이 일부러 한 변경을 되돌리는지 본다. 되돌림이 이번 요청의 뜻이 아니면 ✗.
- 판정 근거에 항목 날짜·제목 또는 커밋 해시를 적는다.

### 3. 부작용
- 프로젝트 전체 테스트 명령을 돌린다 (명령은 `roles/manager.md` 프로젝트별 규칙에서 읽는다. 없으면 평가 계획에서 찾아 적고, 못 찾으면 "테스트 명령 없음"으로 알린다).
- 바뀐 파일이 내보내는 이름(함수·컴포넌트·설정 키)을 쓰는 곳을 찾아, 이번 변경에 깨질 수 있는 곳을 확인한다.
- 다른 롤의 `scope`에 든 파일이 바뀌었으면 이유가 보고에 있는지 본다. 이유 없이 바뀌었으면 ✗.
- 변경 전에는 통과하던 테스트가 실패하면 ✗.

### 4. 개념 (conceptpowers)
- 켜짐 판단: `docs/conceptpowers/init.json`이 있고 `enabled`가 `true`. 아니면 갈래 전체 `–`.
- conceptpowers의 review 스킬을 쓸 수 있으면 그 스킬로 바뀐 코드에 매핑된 개념을 점검한다 (시너지 경로).
- 쓸 수 없으면 직접 읽는다: `docs/conceptpowers/concepts/data/<그룹>/<개념>.json`. 바뀐 코드에 매핑된 개념(코드의 `@concept` 태그, 매핑 캐시)을 찾는다.
  - `status: green`: `actions.restrict`, `principle.immutableRules`를 어기면 ✗.
  - `pending`·`red`: 어기는 것 같으면 ⚠가 아니라 "참고"로 보고에만 적는다.
- `reference` 폴더는 읽지 않는다.

### 5. 수치
- 평가 계획에서 잴 것을 정한다: 응답 시간, 빌드 시간, 번들·파일 크기, 메모리, 특정 출력값 등. 이번 변경과 관계있는 것만.
- 항목마다: `측정 방법(명령) · 단위 · 한계값 · 변경 전 값`.
- 한계값: 사용자가 말한 값 → 롤 문서나 DECISIONS에 적힌 값 → 없으면 평가 롤이 초안(변경 전 값 기준 여유를 둔 값)을 내고 **사용자에게 확인받는다**. 확정한 한계값은 DECISIONS에 적어 다음 평가가 쓴다.
- 측정은 3번 재서 중앙값을 쓴다 (빌드처럼 오래 걸리면 1번, 이유를 적는다).
- 판정
  - 한계값 초과 → ✗
  - 한계값 안, 변경 전보다 10% 넘게 나빠짐 → ⚠ (통과는 하되 사용자가 정한다)
  - 그 밖 → ✓
- 보고와 띠에 `측정값/한계값`, 나빠졌으면 `(+차이)`를 적는다.

## 종합 판정

- ✗가 하나라도 있으면 실패 → verify-loop 3절 표대로 다시 맡긴다. 실패 원인 칸에 갈래를 적는다 (예: "히스토리: DECISIONS 2026-11-05 위반").
- ✗ 없고 ⚠만 있으면 통과. 보고 뒤 사용자에게 ⚠ 항목을 보여주고 받아들일지 묻는다. 안 받아들이면 그 항목을 ✗로 보고 다시 맡긴다 (시도 횟수 이어서).
- 멈춤 조건·끝까지 모드·못 미칠 때 보고는 verify-loop 그대로. 다만 진척을 세는 수를 바꾼다 (매니저 판단):
  - 진척 = 다섯 갈래 전체의 ✗ 개수. 두 번 연속 ✗ 개수가 줄지 않으면 "나아지지 않는 반복"이다.
  - 최고 결과 = ✗가 가장 적은 시도. 같으면 ✓가 많은 시도, 그것도 같으면 나중 시도.
  - verify-loop 3·4절의 "통과한 기준 수"를 이 수로 바꾼다.

## 평가 보고 형식 (평가 에이전트 → 매니저)

```
- 판정: 통과 | 실패
- 갈래별
  - 기준 ✓ 3/3 — <근거>
  - 히스토리 ✗ — DECISIONS 2026-11-05 "<제목>": <어떻게 어겼나>
  - 부작용 ✓ — `pnpm test` 128 통과, 사용처 4곳 확인
  - 개념 – — conceptpowers 꺼짐
  - 수치 ⚠ — 응답 182ms/300 (변경 전 120, +52%) · 빌드 4.1s/10 (+0.3)
- 실패 원인 추정 (실패일 때)
- 사용자 확인 필요: ⚠ 항목, 주관 기준
- 계획에 없던 항목 추가: (있으면)
```

## 진행 띠 (mod)

### 보이는 것

```
⚖ 평가 · mod-dev · 로그인 폼 수정
  이전 (시도 1) ✗  기준 3/3 ✓ · 히스토리 ✗ DECISIONS 11-05 · 부작용 ✓ · 개념 – · 수치 182ms/300 ✓
  지금 (시도 2) …  기준 ✓ · 히스토리 … · 부작용 · · 개념 – · 수치 ·
```

- 기호: ✓ 통과, ✗ 실패, ⚠ 나빠짐(한계 안), … 진행 중, ○ 아직, – 해당 없음.
- 첫 평가(시도 1)는 "이전" 줄 없음.
- 평가 에이전트가 도는 동안만 보인다. 평가가 끝나면(통과·실패 모두) 사라진다. 다음 시도 평가가 시작되면 다시 나타나고, 방금 결과가 "이전"이 된다.
- 질문 띠와 함께 보인다. 둘 다 있으면 평가 띠를 위, 질문 띠를 아래에 둔다. 서로 가리지 않는다.
- 터미널 폭이 좁으면 갈래 줄을 줄여 쓴다(갈래 기호만, 수치는 첫 항목만). 세부는 mod 개발자가 정한다.

### 데이터: `war-room/.eval/<롤 id>.json`

평가 에이전트가 쓰고 mod가 읽는다. 에이전트 내부를 엿보지 않고 이 파일 하나만 계약으로 쓴다.

```json
{
  "task": "로그인 폼 수정",
  "role": "mod-dev",
  "maxAttempts": 3,
  "previous": {
    "attempt": 1,
    "verdict": "fail",
    "items": [
      { "group": "criteria", "status": "pass", "summary": "3/3" },
      { "group": "history", "status": "fail", "summary": "DECISIONS 11-05" },
      { "group": "side-effects", "status": "pass", "summary": "테스트 128 통과" },
      { "group": "concepts", "status": "na", "summary": "conceptpowers 꺼짐" },
      { "group": "metrics", "status": "pass", "metrics": [
        { "name": "응답", "value": 182, "unit": "ms", "limit": 300, "baseline": 120 }
      ] }
    ]
  },
  "current": {
    "attempt": 2,
    "state": "running",
    "focus": "히스토리 위반 고친 결과",
    "items": [ { "group": "criteria", "status": "pass", "summary": "3/3" },
               { "group": "history", "status": "running" } ]
  },
  "updatedAt": "2026-11-09T13:40:00+09:00"
}
```

- `status`: `pass` `fail` `warn` `running` `pending` `na`. `group`: 위 다섯 갈래 고정 이름 (`criteria` `history` `side-effects` `concepts` `metrics`).
- `current.state`: `planning` `planned` `running` `done` `aborted`.
- ① 평가 계획 때도 파일을 쓴다: `current.state: "planning"`, `focus: "변경 전 측정"`. 띠는 "지금 (계획) … 변경 전 측정 중" 한 줄을 보인다. ①이 끝나면 `state: "planned"`로 두고 띠는 사라진다. 이때는 `previous`로 옮기지 않는다 (계획은 평가 결과가 아니다). (매니저 판단)
- ①은 변경 전 수치와 함께 **전체 테스트도 미리 돌려** 원래 실패하던 테스트 목록을 계획에 적는다. ③은 그 목록에 없던 실패만 부작용 ✗로 본다. (매니저 판단)
- 평가 에이전트(③): 시작할 때 `current`를 만들고(`state: running`, 직전 `current`가 있으면 `previous`로 옮김), 갈래 하나를 끝낼 때마다 그 항목을 고쳐 쓴다. 끝나면 `state: done`과 `verdict`를 쓴다.
- mod: `current.state`가 `running` 또는 `planning`인 파일만 띠를 그린다. 파일이 없거나 형식이 틀리면 아무것도 그리지 않는다 (오류를 띠에 내지 않는다).
- 매니저: 평가 에이전트가 돌아올 때마다(정상·오류·중단 모두) 파일을 열어 `state`가 아직 `running`·`planning`이면 `aborted`로 고친다. 일이 완전히 끝나면(통과 확정 또는 멈춤) 파일을 지운다. (매니저 판단)
- mod 안전장치: `updatedAt`이 30분 넘게 지난 `running`·`planning`은 그리지 않는다. 평가 에이전트는 갈래 하나를 끝낼 때마다 `updatedAt`을 고친다. 30분 넘는 한 갈래(긴 빌드 등)는 그 전에 측정 시작 시각으로 한 번 더 고친다. (매니저 판단)
- `war-room/.eval/`는 커밋하지 않는다. 설치 때 `.gitignore`에 넣는다.
- 갱신 반영은 2초 안. 읽는 방식(시계 폴링, 파일 감시)은 mod 개발자가 정한다.

## 설치·호환

- 새 설치: `template/roles/evaluator.md`가 manager와 함께 복사되고 config `roles.evaluator: true`.
- 기존 설치(evaluator 롤 파일이 없음): 지금처럼 임시 검증 에이전트를 쓴다. 다음 배정 때 한 번 "평가 롤을 추가할 수 있어요"라고 알리고, 승인하면 템플릿에서 복사한다. 거절하면 DECISIONS에 적고 다시 묻지 않는다.
- `roles.evaluator: false`: 평가 롤을 쓰지 않고 임시 검증 에이전트로 돌아간다. 띠도 안 뜬다 (파일을 안 쓰므로).
- `evaluator`는 `manager`처럼 지울 수 없는 롤로 둘지: **지울 수 있게 한다** (끄기·삭제 가능). (매니저 판단)
