# war-room 매니저 판단 (되돌릴 수 있는 결정은 스스로 정하고 나중에 점검) 설계

작성: 2026-11-11 · 상태: 사용자 승인 (2026-11-11, 방향·적용 범위 A·B) · 세부는 매니저 판단

## 왜 하나

1. 지금 규칙은 "작은 일이 아니면 시작 전에 기준을 확인받는다"라서, 되돌리기 쉬운 것까지 사용자에게 묻는다. 사용자가 자리에 없으면 일이 멈춘다.
2. 반대로 매니저가 혼자 정한 것은 어디에도 모이지 않는다. DECISIONS는 되돌리기 어려운 결정만 적는다. 그래서 혼자 정한 판단이 맞았는지 아무도 다시 보지 않는다.

## 목표

- 매니저는 최선의 판단으로 계획을 세우고, 되돌릴 수 있는 결정은 묻지 않고 정해 진행한다.
- 되돌리기 어려운 결정은 지금처럼 사용자에게 묻는다. 둘을 가르는 기준은 목록으로 못 박는다 (판단에 맡기면 경계가 넓어진다).
- 혼자 정한 결정은 기록하고, 정해진 시점에 매니저가 아닌 에이전트(또는 사용자)가 점검한다.
- 점검에서 틀린 판단이 나오면 교훈으로 남겨 같은 판단을 반복하지 않는다.

## 하지 않는 것

- 새 롤을 만들지 않는다. 매니저(메인 세션)의 규칙이고, 점검은 이미 있는 평가·검증 에이전트가 한다.
- 새 config 키를 만들지 않는다.
- 다른 절이 이미 사용자 확인을 요구하는 것(⚠ 수용, 수치 한계값 확정, 주관 기준, 롤 제안·교훈 반영 승인, 되돌리기 어려운 단계 전 승인, 사용자가 정한 등급이 하일 때 올리기)은 바꾸지 않는다. 그대로 묻는다.
- 위험도 등급(하·중·상) 규칙은 바꾸지 않는다. 등급은 검증 비용을, 이 규칙은 누가 정하는지를 다룬다. 상 등급 일 안에서도 되돌릴 수 있는 결정은 매니저가 정한다.

## 실패로 볼 것

- 되돌리기 어려운 결정을 "되돌릴 수 있다"고 분류해 묻지 않고 진행하는 것.
- 점검이 형식만 남는 것 (STATUS에 쌓이기만 하고 아무도 보지 않음).
- 매니저가 자기 결정을 스스로 점검하는 것.

## 규칙

### 1. 결정 나누기

되돌리기 어려운 결정 (사용자에게 묻는다). 하나라도 걸리면 이쪽이다. 애매하면 이쪽이다.

1. 커밋·push·릴리즈·배포 (사용자가 이번 요청에서 시킨 것은 이미 승인됨)
2. 이미 있던 파일·데이터 삭제, 마이그레이션
3. war-room `roles/`·`config.json` 변경 (켜고 끄기는 예외, 기존 규칙)
4. 이미 다른 사람·시스템이 쓰는 형식·인터페이스 변경 (공개 API, 설정 키, 파일 형식, 스킬 트리거 문구)
5. 밖으로 보내는 일 (메시지, 이슈·PR 댓글, 외부 서비스 쓰기)
6. 권한·보안, 돈이 드는 일
7. 요청 범위를 넓히거나, 사용자가 정한 것(사용자가 말한 기준, DECISIONS `정한 사람: 사용자`)을 바꾸는 것
8. 요청이 두 가지 이상으로 읽히고 고른 쪽에 따라 결과물이 크게 달라지는 것

되돌릴 수 있는 결정 (매니저가 정한다). 위 8개에 하나도 걸리지 않는 것. 예: 기준 초안과 확인 방법, 등급 올리기, 롤 나누기·순서, 구현 접근 고르기, 아직 아무도 쓰지 않는 이름·문구, 기준 검토의 받아들임·거절, 재시도 접근.

롤 보고의 `정한 것`·`가정한 것`도 같은 기준으로 나눈다. 되돌리기 어려운 것이면 사용자에게 묻는다.

### 2. 정하고 알리기

- 알리기 줄 다음에 이번 일에서 정한 것을 한 줄로 보여준다: `정한 것: <결정>; <결정>`. 사용자는 보고 끼어들 수 있지만, 매니저는 답을 기다리지 않고 진행한다.
- 기준 초안도 되돌릴 수 있는 결정이다. "작은 일이 아니면 기준을 확인받는다"를 "기준을 알리고 진행한다"로 바꾼다. 예외: 기준이 1절의 되돌리기 어려운 결정을 담으면(범위를 넓힘, 요청 뜻이 갈림) 묻는다.

### 3. 기록

- 하 등급 일: 8번 보고에 `매니저가 정한 것`으로만 적는다. 점검하는 사람은 보고를 읽는 사용자다.
- 중·상 등급 일: STATUS.md `## 점검할 결정`에 결정마다 한 줄 남긴다.
  형식: `날짜 · 작업 · 결정 · 이유 · 되돌리는 법`
- 다시 쓸 때도 이어서 남긴다 (롤 후보 절과 같다). 10KB 넘침 때 자르지 않는다.
- 나중에 이유가 궁금할 결정은 기존 규칙대로 DECISIONS에도 적는다 (`정한 사람: 매니저 판단`).

### 4. 점검

- 언제·누가: 그 일의 평가 ③(평가 롤 꺼짐·없음이면 검증 에이전트)이 한다. 프롬프트에 `## 매니저가 정한 것` 칸을 넣고, 보고에 `결정 점검` 줄을 받는다. 매니저는 자기 결정을 점검하지 않는다.
- 판정: 결정마다 `유지 | 재검토 — 근거`. 재검토인 경우:
  - 그 결정이 이번 ✗·⚠의 원인이다
  - 요청·DECISIONS·LESSONS와 어긋난다
  - 1절의 되돌리기 어려운 결정인데 되돌릴 수 있다고 분류했다
- 결정 점검은 종합 판정(✗ 개수)에 따로 더하지 않는다. 결정 때문에 생긴 ✗는 이미 해당 갈래에서 센다.
- 처리 (매니저):
  - 유지: STATUS `점검할 결정`에서 지운다. 보고에 "결정 n개 점검 통과"로 적는다.
  - 재검토: 8번 보고에 근거와 함께 보여주고 사용자에게 유지·뒤집기를 묻는다. 뒤집으면 고치는 일을 다시 맡긴다 (시도 횟수는 이어서 센다). 판단 실수는 `LESSONS.md`에 `manager` 항목으로 적는다. 같은 종류가 두 번째면 기존 규칙대로 manager.md 반영을 제안한다.
  - 남은 항목: 배정 1번에서 STATUS를 읽을 때, 이미 끝난 일(평가 없이 멈췄거나 세션이 끊김)의 항목이 남아 있으면 이번 보고 때 사용자에게 한 번 보여주고 지운다.
